# Pilot：衝突與重派

[pilot.md](pilot.md) 的 pointer 指到這裡時才讀：`pilot-land.mjs` 印 `STOP conflict` 或 `RESOLVED`，或成員要重派（同一條目衝突、`WORKER <n> STOP findings after two review cycles`）。下文的 `<主 checkout>`、`<stage worktree>` 與其他條目名稱都指 pilot.md 與 [pilot-exceptions.md](pilot-exceptions.md) 的同名條目。

- **Stage conflict.** `pilot-land.mjs` 的衝突只照下列解法自己解，每解一次印 `RESOLVED <n> <解法> <檔案…>`，解完的 staged SHA 一樣要跑 Regression：衝突檔有戳記檔（`scripts/restamp.mjs` 的 `STAMP_FILES`：`scripts/workflow-doc-sync.json`、`docs/agents/workflow-templates.json`）時（兩邊合併前都已各自對照 `docs/workflow/` 並 restamp），其他衝突檔先用下列解法解完，再交給和 `land.mjs` 共用的 `restamp()` 依合併結果重算：`workflow-doc-sync.json` 重產站台後跑 `scripts/check-workflow-sync.mjs --restamp`，`workflow-templates.json` 取兩邊條目的聯集、依合併後的副本重算 sha256（`restamp`，#72、#173；和別的解法一起時 restamp 排最後，印成 `entries+restamp`、`rows+restamp` 這類組合）；每個衝突 hunk 的 base 都是空的、兩邊只是在同一處新增不重疊的段落時，依號碼兩段都留下（`additions`；兩邊各自新增同一個檔、新增的段落有相同的行或同名的條目都不算）；每個衝突 hunk 裡兩邊改的是不同的 `- **<名稱>.**` 條目時各取各的版本，兩邊改過的條目都留下（`entries`，#45）；衝突 hunk 的 base、ours、theirs 三份的行都是 Markdown 表格列（`|` 開頭）時，以第一格為鍵，兩邊改的是不同列就各取各的版本、依原順序排好，新增的列都留下（`rows`，#162；同一列兩邊都改、一邊刪一邊改、兩邊新增同一個鍵、某一份有重複的鍵、留下的列順序變了、各列欄數不同都仍是衝突）；衝突 hunk 裡一邊只改了 base 的某幾行、另一邊只在 base 行之間插入新行（沒改任何 base 行），插入點不在改動的那幾行中間時兩邊都套用（`adjacent`，#175：#131 改了 `pilot-close.mjs` 檔頭一行註解、#143 在那行後面插入兩行；一邊只刪掉 base 行（純刪除不算改動）、兩邊動到同一個 `- **<名稱>.**` 條目（同一條目衝突；插入的新條目切開另一邊正在改的條目也算）、兩邊都改了同一個 base 行、改動或插入碰到表格列（歸 `rows` 判斷）、兩邊的最短 diff 對齊不只一種而合出不同結果（重複行能滑動、拆段插入；hunk 前後各一行一起對齊，對齊動到 hunk 外那一行也算）、換上的行和插入的行相同（非空行或同名條目，合起來會重複）、碰到檔尾沒換行的行都仍是衝突，組合照樣印成 `adjacent+restamp` 這類）。`additions`、`entries`、`rows` 與 `adjacent` 只解三個版本都是 UTF-8 文字的檔案。其他衝突（包括戳記檔和解不了的檔一起衝突）它先 `merge --abort`，印 `STOP conflict <n> <檔>=<來源>:<種類> …`（每個衝突檔一項，#192），stage worktree 是乾淨的：來源是 `member <m>`（本次 stage 依號碼先合入、自己的分支改過這個檔的同批成員）、`integration`（成員開分支之後整合分支改過）或以 + 相連的多個來源（`member <m>+integration`、`member <m>+member <k>`；都看不出來時是 `unknown`，不該發生，照其他衝突變成 gate）；種類是 `entry <名稱>`（Markdown 檔解不了的 hunk 裡兩邊都改的 `- **<名稱>.**` 條目，一邊增刪了條目、條目對不齊時是 hunk 碰到的每個條目，多個以、相連）、`code`（程式檔）或 `other`，例如 `STOP conflict 108 scripts/lib/hosts.mjs=member 79:code docs/agents/pilot.md=integration:entry Pool`。這時讀種類欄判斷是不是同一條目衝突（有檔的來源是 `unknown` 時不算，照其他衝突變成 gate），不再對兩邊跑 diff：至少一個檔是 `entry <名稱>`（skill 的同一條規則也是這種條目），其餘衝突檔只是同一處改動在 `docs/workflow/` 的轉述、產生的 html 與戳記檔。是的話不開 gate，照 Fresh redispatch 重派這個成員，帶上整併後的範圍（另一邊的改動照來源欄去看：`member <m>` 是那個成員的分支，`integration` 是整合分支），並照 Decisions 記一筆（衝突檔、prior 分支與 SHA）。來源含 `member <m>` 時照這個順序做，fresh worker 才從已含 #m 的整合分支開始（先重派的話 fresh worker 從 #m 合入前的整合分支開分支，做完一定再跟 #m 衝突、變成 `refresh-twice`，batch 79-108）：先跑 `node scripts/pilot-batch.mjs <主 checkout> move <key> <n> --state stop` 把它移出原 batch，再重跑 `node scripts/pilot-land.mjs <key>` 讓其餘成員合入整合分支，印 `MERGED` 之後才照 Fresh redispatch 跑 `node scripts/pilot-dispatch.mjs <n> --fresh <n>:<slug> --note <主 checkout>/.scratch/pilot/fresh-<n>.md`（key 是它自己的 `<n>`，就地改寫 `batch-<n>.md`）。來源只有 `integration` 時照 Fresh redispatch 以原 key 重派，重派後原 batch 只剩其他成員，重跑 `pilot-land.mjs <key>` 合入它們。同一個 Issue 重派後又衝突時 `--fresh` 印 `STOP refresh-twice <n>`，這時才開 gate，預設選項是「再重派一次」（帶 `--again`）。其他衝突照舊變成 gate。

- **Fresh redispatch.** 兩種情況重派成員：Stage 判定同一條目衝突，或 Probe 印 `WORKER <n> STOP findings after two review cycles`（SKILL 的 Stops 表「派一個 fresh worker 帶整併範圍」就是這裡，#144、#175 的 coordinator 都得自己推斷，#204）。先照 Dispatch 認領（認領者是前任 coordinator 時帶 `--session`），再在主 checkout 不帶 `--note` 跑 `node scripts/pilot-dispatch.mjs <原 key> --fresh <n>:<slug>` 產生整併範圍草稿（#227：手拼要讀兩份 checkpoint、跑 merge-base、log、diff 和 `comm`，一次重派兩個成員花了 6 次工具呼叫）：它印 `NOTE_DRAFT <主 checkout>/.scratch/pilot/fresh-<n>.md`，不派工（不改名分支、不開關分頁、不留言，不需要 `ORCA_CLI_COMMAND`；草稿已在就覆寫，它的「怎麼整併」已經補過時改印 `STOP <n> draft-filled <path>`、不動它，這時直接帶 `--note` 跑），草稿列出原 Issue 號碼與標題、prior 分支與 SHA（batch checkpoint 那一列的 candidate，空的取分支 tip）、`git merge-base <分支> pilot/integration`、成員與整合分支自 merge-base 以來共同改過的檔（各附兩邊的 `git diff --stat`，`.md` 附兩邊改到的 `- **<名稱>.**` 條目，有條目外的改動時另註明，不印完整 diff），以及 worker checkpoint（`<worktree>/.scratch/issue-run-<n>/state.md`）最後一個含 `review-only` 的行（如 `final review-only round`）到結果行（沒有結果行時到下一個標題）的原文（寫著「checkpoint 沒有 review-only 段，補 worker 分頁尾段」時照抄 worker 分頁尾段）。只讀草稿列出的條目，判斷不了才看那個檔的 `git -C <主 checkout> diff <merge-base>..pilot/integration -- <檔>`；在最後空白的「怎麼整併」補上給 fresh worker 的整併範圍：同一條目衝突寫整合分支那一邊改了什麼、要怎麼整併（衝突來源含同批成員時，這個成員已先移到 `batch-<n>.md`，下面指令的 `<原 key>` 是 `<n>`，見 Stage conflict）；findings STOP 寫剩下的 findings 要怎麼處理。補完再在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <原 key> --fresh <n>:<slug> --note <主 checkout>/.scratch/pilot/fresh-<n>.md`。它不移除 worktree、不刪分支：關掉 worktree 裡每個 terminal，舊分支就地改名成 `issue/<n>-<slug>-prior`，從 `pilot/integration` 開同名新分支，worker 的 `.scratch/issue-run-<n>` 改名成 `issue-run-<n>-prior`，在 Issue 留言（note 加一行 `prior: <分支> @ <sha>`），把成員拆到 `batch-<n>.md`（表頭加一列，原 batch 那列記 `moved batch-<n>`；原 batch 的成員因此全是 moved 時 `current:` 寫成 `closed moved`，同 `pilot-batch.mjs move`。#205 之前留下、成員全 moved 卻還是 `dispatched` 的舊 batch，對任一成員重跑 `pilot-batch.mjs <主 checkout> move <key> <n>` 就補關），再照 Dispatch 開分頁、送出 worker 指令；印 `DISPATCHED <n> <handle>` 與 `PRIOR <n> <prior 分支> <sha>`。`STOP dirty <n>`（worktree 有未提交改動，什麼都沒動）回報人；`STOP <n> overlap <m> …`（要另存成 prior 的分支和開著的 `running`、`done` 成員改到同一處，什麼都沒動）照 Dispatch 的 overlap 處理，等 #m 合入後再重派；`STOP refresh-twice <n>` 照 Stage conflict 開 gate，依先例（G2、G3、G5、G6、G14）直接套用預設「再重派一次」：照 Gates 先 `open` 再立刻 `resolve` 留紀錄，加 `--again` 重跑（另存成 `-prior2`，依序編號）；已經有 `-prior2`、這是第三次重派（SKILL 的 third forced re-stage）時才讓 gate 開著等人（#172）；其他 STOP 修好原因後重跑同一行，每一步都能從中斷處接著做。fresh worker 已經派出、還沒有 commit 時重跑會印 `STOP <n> running <handle>`，不關它的分頁；它有了 commit 之後重跑就是 `STOP refresh-twice`，`--again` 會關掉它的分頁，所以只在它做完（DONE 或 STOP）之後才加。G2–G7 手動重派留下 `-prior` 的 Issue，分支有了自己的 commit 時第一次跑就是 `STOP refresh-twice`。prior 分支不刪。不要再手做 `branch -m`、`switch -c`、搬 checkpoint 或改 `current:`、`integration:` 行。
