# Pilot：ron-skills

給使用者層級的 `/issue-pilot` coordinator 用的專案設定（`/loop /issue-pilot`）。[issue-run.md](issue-run.md) 各段在 pilot 底下照樣適用，這裡只寫 pilot 不同的地方。本 repo 的 pilot 腳本有 Pool 與 Dispatch 認領的 `scripts/issue-pool.mjs`、Bare guard 的 `scripts/pilot-unbare.sh`、Probe 的 `scripts/pilot-probe.mjs`、Dispatch 的 `scripts/pilot-dispatch.mjs`（兩支都是 setup-workflow 正本的副本，Bare guard 用同目錄的 `pilot-unbare.sh`）和 Handoff 的 `scripts/pilot-handoff.mjs`（後兩者要 `ORCA_CLI_COMMAND`，Probe 讀 worker 時也要），Stage、Regression、Integrate 的 `scripts/pilot-land.mjs`（setup-workflow 正本的副本；本 repo 的條目解法與流程站戳記在專屬的 `scripts/pilot-resolve.mjs`，指令以 `--resolver` 帶入，#245），Close 的 `scripts/pilot-close.mjs`（setup-workflow 正本的副本，tracker 專案以 `--repo` 帶入；它再呼叫 `scripts/pilot-counterpart.mjs`，Orca 指令同樣要 `ORCA_CLI_COMMAND`；本 repo 的留言、關單由它交給 `scripts/gh-tracker.mjs`），以及寫存檔的 `scripts/pilot-register.mjs`、`pilot-decision.mjs`、`pilot-request.mjs`、`pilot-hold.mjs`、`pilot-sources.mjs`、`pilot-gate.mjs`，Stage 搬移、暫緩成員的 `scripts/pilot-batch.mjs`，與 Push gate 產生 PR body 的 `scripts/pilot-pr-body.mjs`（都是 setup-workflow 正本的副本，指令與結果行見 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md#canonical-scripts)）；watch 由 coordinator 依下列指令手動做，`status.md` 由 Probe 的 `--status` 重產，沒列出的指令就是沒有。`.scratch/pilot/` 每個檔案（含 batch checkpoint）的路徑、格式與合法值都照 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md)，這裡只寫本 repo 的值。

本檔只留每輪都用的條目；只在某些情況才用到的條目放在 [pilot-after-merge.md](pilot-after-merge.md)、[pilot-conflict.md](pilot-conflict.md)、[pilot-exceptions.md](pilot-exceptions.md) 與 [pilot-retro-collect.md](pilot-retro-collect.md)，本檔的同名條目是一行 pointer，寫明什麼情況要讀哪份檔；沒遇到那個情況就不讀（#166：整份 63 KB 每任 coordinator 都重付，多數條目一任都用不到）。

- **Coordinator checkout.** 下文的 `<主 checkout>` 是 coordinator 所在 repo 的主 checkout，依機器不同（WSL、macOS 的路徑都不一樣），不寫死：coordinator 在主 checkout 時是 `git rev-parse --show-toplevel`；session 開在 linked worktree 時是 `git rev-parse --path-format=absolute --git-common-dir` 的上一層（兩種情況都可以用後者）。執行時代入實際的絕對路徑。`.scratch/pilot/` 放在主 checkout，不 commit。Orca 指令一律寫成 `"$ORCA_CLI_COMMAND"`（每台機器設成自己的 Orca CLI：WSL 是 PATH 上的指令名，macOS 是 Orca.app 內 `orca` 的絕對路徑）；沒有這個環境變數就回報人，不猜指令名。

- **Bare guard.** 見 [pilot-exceptions.md](pilot-exceptions.md)：Probe、Dispatch、Stage、Close 的腳本都自己跑它（還原時印 `UNBARE`）；腳本 exit 非 0、或主 checkout 還沒有 `scripts/pilot-unbare.sh` 時才讀。

- **Permissions.** 見 [pilot-exceptions.md](pilot-exceptions.md)：coordinator 腳本被 auto mode 擋下，或要加新的 coordinator 腳本時才讀。

- **Sessions.** Entry 成為 coordinator 時在主 checkout 跑 `node scripts/pilot-register.mjs <主 checkout> --name <ListAgents 印的 session 名稱> --loop yes|no --sources-file docs/agents/pilot-sources.txt`（pid、session 取 `$CLAUDE_PID`、`$CLAUDE_CODE_SESSION_ID`），之後每輪 Reconcile 一開始、跑 Probe 之前也跑同一條（只在 Entry 確認沒有別的 coordinator 活著之後跑，它會直接覆寫 `coordinator`）：它寫 `coordinator`（pid 不變時保留 `since`）、`sessions.md` 的 start 行只附加一次，最後記錄 Sources 的清單檔；印出的 `SOURCE_CHANGED`、`SOURCE_MISSING` 照 Sources 處理；`STOP retired` 表示這個 session 已交接出去，照 Entry 什麼都不做；`STOP sources-file <path>`（exit 4，什麼都沒寫）表示主 checkout 沒有清單檔（例如還在 #240 之前的 `main`），回報人，這一輪不做其他事。不手寫 `coordinator` 與 start 行，也不把來源逐個抄成位置參數（#240：session 76bb4905 漏抄了 4 個 `pilot-*.md`）。

- **Sources.** 來源清單在 `docs/agents/pilot-sources.txt`（一行一個，相對主 checkout 或絕對路徑，`~` 由腳本展開；空行與 `#` 開頭的行略過），這裡不再逐一列檔名。adapter 新增 coordinator 要讀的檔（例如 Pilot 段新連到一份 `pilot-*.md`）時，在同一個 commit 裡往清單檔加一行；下一輪 Sessions 指令就對它印 `SOURCE_CHANGED`。來源檢查就是每輪的 Sessions 指令：它讀清單檔，最後以 `pilot-sources --record` 記錄這份清單，印出的每行 `SOURCE_CHANGED <path>`、`SOURCE_MISSING <path>` 就重讀那個檔案，沒有這兩種行就是都沒變；`SOURCE_CHANGED` 下面有縮排行（`  entry <名稱>`、`  heading <標題>`、`  outside`，快照存在 `.scratch/pilot/source-snapshots/`）時只重讀列出的條目、標題底下的段落或第一個標題前的內容，不必再 `git log`、`git show` 找改了什麼；長條目的縮排行底下還有再縮排的片段行（`    …<前文>[-<刪除>-]{+<新增>+}<後文>…`，詞級 diff）時讀片段就好，不重讀整個條目、也不再自己跑 `git diff --word-diff`；片段行是 `    (diff <n> chars, reread)` 時才重讀整個條目（#236、#239）；沒有縮排行（沒有舊快照，或只改了空行、單位的順序）就重讀整份；pointer 指去的那幾份只有這個 session 讀過時才重讀，沒讀過的等 pointer 指到時再讀；但第一輪與 compaction 之後仍照 SKILL 的 Sources 全部重讀（pilot.md 以外的 `pilot-*.md` 仍等 pointer 指到才讀），記錄可能是前任 session 留下的。同一輪不要再單獨跑 `node scripts/pilot-sources.mjs <主 checkout> --record …`：記錄已經被 Sessions 指令改寫，它什麼都印不出來，改過的檔案就漏讀了；只有那一輪沒跑 Sessions 指令時才單獨跑它。

- **Decisions.** `decisions.md` 只用 `node scripts/pilot-decision.mjs <主 checkout> --decision <決定> --reason <理由> --evidence <證據> --result <結果>` 附加，不手寫表格列；欄位不能有 `|`。Probe 或任何讀取發現表格散掉（`pilot-unbare.sh` 在檔案不存在時只附加列）時跑 `node scripts/pilot-decision.mjs <主 checkout> --repair`，`MALFORMED` 的行回報人。

- **Requests.** 見 [pilot-exceptions.md](pilot-exceptions.md)：Probe 印 `REQUEST` 時讀。

- **Gates.** 見 [pilot-exceptions.md](pilot-exceptions.md)：要開或解 gate（Probe 印 `GATE`、`GATE_MALFORMED`，或任何條目寫「變成 gate」）時讀。

- **Defaults for `preferences.md`.** 整台機器同時跑的 worker 合計最多 4 個（`$PILOT_MACHINE_WORKER_CAP`，寫在 `~/.zshrc`，沒設時 4），含 investing 等其他 repo 的 pilot／cycle，fresh 重派也算在內；合計讀全機帳本（Probe 的 `--capacity` 寫入、Dispatch 的 `--capacity` 檢查）；還沒寫帳本的 repo（investing 的對應單合入前）不在帳本裡，派工前另把它在跑的 worker 加進來（investing 讀 `$INVESTING_DATA_ROOT/.local/agent-notes/cycle/state.md` 的 Batch in flight 裡「開跑」的子代理），合計加上這批人數超過上限就不 Pick、不 Dispatch。依據：這台 10 核機器上 `bin/check` 的 `node --test` 開 `availableParallelism()-1` = 9 個並行程序，同時 8 個 worker 時 1 分鐘 load 約 90，Regression 的計時測試失敗；2–4 個時都通過（#178）。每批最多 2 個 Issue；worker 指令見 Dispatch；只有 coordinator 合進 batch 與整合分支；push、開 PR、合進 `main` 都由 coordinator 照 Push gate 做，不交給人（worker 不 push、不開 PR）；每個 session 合入 2 批或遇到 compaction 就 handoff。

- **Integration branch.** 本機 `pilot/integration`，第一次用時從 `main` 開（`git branch pilot/integration main`）。push、開 PR、合進 `main` 和之後跟上 `origin/main` 都見 Push gate。要讓它跟上 `origin/main` 時（例如 retro 分支直接落地進 `main` 之後、下一次 Stage 之前）在主 checkout 跑 `node <stage worktree>/scripts/pilot-land.mjs sync-main --check-command 'bin/check --upstream' --resolver scripts/pilot-resolve.mjs`（見 Push gate 第 3 步）：切分支與快轉都在 `<stage worktree>` 做，主 checkout 不切分支，也不再手打 `merge --ff-only`。

- **Stage worktree.** 下文的 `<stage worktree>` 是 `git -C <主 checkout> worktree list --porcelain` 裡分支（`branch refs/heads/…` 行）為 `pilot/integration` 或 `pilot/stage-*` 的那個 worktree，取它的 `worktree ` 行的路徑；找不到就是還沒建，照 Stage 用 Orca 建好後再找一次。Stage、Regression、Integrate 全在這裡做，`pilot/integration` 也只在這裡前進。主 checkout 一直停在 `main`，coordinator 在主 checkout 只做 fetch、讀狀態、快轉 `main`（`git -C <主 checkout> merge --ff-only origin/main`）：在主 checkout 切到還沒合入的分支，工作樹會帶出那個分支的 `.claude/settings.json`，在主 checkout 跑的 session 會即時載入它的 hook（#21）。

- **Scripts ahead.** 見 [pilot-exceptions.md](pilot-exceptions.md)：Probe 印 `ADAPTER_AHEAD` 那一輪要跑整合分支才有的腳本時讀。

- **Pool.** `node scripts/issue-pool.mjs`（setup-workflow 正本的副本）把開著的 Issue 逐張分桶印成 `<桶> #<n> <標題>`，`ready` 桶已經排好序（`retro` label 的先、`priority` label 的先、直接或間接 block 最多開著的單的先、號碼小的先），照印出的順序挑，略過已經在某個開著的 batch checkpoint 裡的 Issue。分桶行之後的 `NO_CATEGORY <n>` 是開著、有 triage 狀態 label 卻沒有分類 label（[triage-labels.md](triage-labels.md#分類-label)）的單，母單與 `retro-candidates` 不算：照 `/triage` 補上一個分類 label（留言開頭放 AI 聲明、寫判斷理由），判斷不了就回報人；它不影響挑單，`ready` 桶照挑（#142：#130、#124、#123 只掛 `ready-for-agent` 與 `retro`，triage 的三個桶都沒列到）。帶 `retro` label 的 ready Issue 先挑：它是 `/retro-collect` 判定太大、交給 worker 的 retro 候選；候選清單本身掛 `retro-candidates`，留給 `/retro-collect`，不進池子。`ready` 桶就是[池子](../../GLOSSARY.md)：標 `ready-for-agent`，不是母單、沒有開著的 `blocked_by`、沒被[認領](../../GLOSSARY.md)，也沒有 `ready-for-human`、`needs-info`、`needs-triage`、`retro-candidates`（這些各有自己的桶，桶的優先序寫在腳本檔頭）；`stale`（認領超過 24 小時沒有新留言或新指派）不會自動釋放，回報人決定要不要取消指派。有 sub-issue 的是母單（`parent` 桶）：母單只分組、不派工也不驗收，pilot 一律挑它的子單（`/to-spec` 會給母單掛 `ready-for-agent`，不排除就會跟子單重複派工）。人手動跑 `/issue-run <母單>` 時仍照上游展開子單。`needs-triage` 的先照 [Readiness](issue-run.md#readiness) 補齊，變成 `ready-for-agent` 才挑。`/triage` 設了 `disable-model-invocation`，Skill tool 叫不動，coordinator 改讀 `~/.claude/skills/triage/SKILL.md` 自己照做：每則留言開頭放 AI 聲明，一個類別 label 加一個狀態 label；輸入都拿得到、範圍與驗收清楚才標 `ready-for-agent`，同時照同目錄的 `AGENT-BRIEF.md` 留一則 agent brief（#116 只留了 triage 理由，worker 拿到的只有 Issue 本文）；要拷問或要人決定的單標 `needs-info` 或 `ready-for-human`，交給人跑 `/triage`。挑到的單本文寫了依賴、而依賴是在本文寫成之後才關閉的，派工前先讀那張依賴的合入 diff，確認本文的做法與驗收還成立；不成立就照 Readiness 先 refine，牽涉產品取捨就開 gate，不要派出去讓 worker 撞上（#219：#56 合入時把來源檢查移到 `pilot-register`，#119 本文的做法跟著失效，coordinator 只確認依賴已關閉就派，worker STOP 後開了 G16 再重派）。Probe 印 `STAGEABLE` 的 batch，而且它的成員和整合分支或同批成員有 `OVERLAP` 時，這一輪的 Pick 延到 Land 之後：還沒 stage 的 done 成員日後衝突重做，`pilot-dispatch.mjs --fresh` 的 overlap 檢查會撞上剛派出的新單，只能 `blocked-by` 到它、延後一整輪（#218：同一輪已印 `WORKER 193 DONE` 與 `OVERLAP 178 193`，卻先派了 batch 107-130，之後 #193 重派印 `STOP 193 overlap … 130 …`）。同一母單的 ready 子單都要改同一份註冊檔（`docs/agents/workflow-templates.json`、Templates 表、`skills/engineering/issue-pilot/PILOT-STORE.md` 的 Canonical scripts 表、`skills/engineering/setup-workflow/SKILL.md`）時，不放進同一批，其中一張還沒合入時也不派另一張：只派池子順序最前的一張，其餘照 Decisions 記一筆、等它合入再派。`rows`、`restamp` 解不了這類衝突，後合的成員在 Stage 會印 `member <m>:other`、要移出去重做（#258：#245、#246 同批，#246 約 21 分鐘的工作重做；#240、#244 同批，#240 重派撞上 #244）。

- **Batch.** 批次 checkpoint 是 `.scratch/pilot/batch-<key>.md`，由 Dispatch 建立；請求分支的 `batch-req-<行號>.md` 由 `pilot-land.mjs --branch` 建立（見 Requests）。各 Issue 自己的 checkpoint 仍在 `.scratch/issue-run-<n>/state.md`（在它的 worktree 裡）。

- **Brief check.** 沒有指令。worker 的 brief 就是 `/issue-run <n> --worker <checkpoint>` 加上 Issue 本文；tooling fix unit 的 brief 由 coordinator 寫在 `.scratch/pilot/briefs/`，派出去前自己核對契約列的每一節都在。

- **Dispatch.** 派工前先在主 checkout 對每個成員跑 `node scripts/issue-pool.mjs claim <n>`（session 取 `$CLAUDE_CODE_SESSION_ID`）：印 `CLAIMED <n>` 才派（同一個 session 重派會再認領一次，順便更新 `stale` 的時間）；認領者是這台機器上先前的 coordinator session（handoff 之前派的，`.scratch/pilot/sessions.md` 有它的 handoff 行），而 claim 的是現任 coordinator 時，腳本直接以那個 session 接手，印 `CLAIMED <n> takeover <session>`，照樣派；`STOP <n> claimed <機器>／<session>` 表示別的機器或 session 已經在做，這個成員不派、從這一批拿掉；`STOP <n> claimed <登入名>` 是有人手動指派（沒有認領留言，或指派換了人），回報人。認領之後 `pilot-dispatch.mjs` 對它印 `STOP`（`not-claimed` 除外）、這個成員不再重派時，用 `node scripts/gh-tracker.mjs edit <n> --remove-assignee @me` 放掉認領，免得其他機器要等它變成 `stale`。接著在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <key> <n>:<slug>... --capacity`（成員依號碼順序，如 `node scripts/pilot-dispatch.mjs 23-46 23:pilot-probe 46:pilot-dispatch --capacity`；`--fresh` 重派也帶 `--capacity`，只寫草稿、不派工的 `--fresh`（沒帶 `--note`）不帶；腳本 540 秒內必定結束）。它先合計全機帳本、加上這次要派的人數（`--fresh` 是 1）比 Defaults 的上限：超過就只印 `STOP capacity <合計>/<上限>`、exit 4，不寫 checkpoint、不建 worktree、不開分頁，這一批留到下一輪（放掉認領，免得別台機器要等它變成 `stale`），不超過時先印 `CAPACITY ok <合計>/<上限>`；帳本 ron-skills 那一列是 Probe 寫的，所以派工前要先跑過這一輪的 Probe，同一輪要再派一批時也先重跑 Probe，剛派出的成員才算進去。每個成員依序做：先讀 Issue 最近一則認領留言（格式與接手規則同 `issue-pool.mjs claim`），不是這個 session 的就印 `STOP <n> not-claimed`、成員行記 `stop`，不開 worktree、不開分頁（session 取 `$CLAUDE_CODE_SESSION_ID`，其次 `$ORCA_TERMINAL_HANDLE`，同 claim 的預設；claim 以 `--session` 帶前任 coordinator 認領的，靠 `sessions.md` 的接手規則算這個 session 的，帶其他 session 的不算；#165：claim 印了 `STOP` 卻在同一行用 `;` 接著跑 dispatch，照樣派出）；接著 `scripts/orca-worktree-create.mjs`（setup-workflow 正本的副本）建 worktree `issue-<n>`、分支 `issue/<n>-<slug>`、base `pilot/integration`，接著 Bare guard（時機 `dispatch #<n>`），以目錄存在、`git worktree list` 裡有這個分支判斷 worktree 建好（不信 create 回傳的 `ok`），再 `"$ORCA_CLI_COMMAND" terminal create --title '#<n>' --command claude`，最後用 orca-session-send 送出 `/issue-run <n> --worker <主 checkout>/.scratch/pilot/batch-<key>.md`。所有子行程的 stdin 都接 `/dev/null`。它會寫 batch checkpoint 的表頭（已存在就不動）和每個成員一行（重跑時同一個 Issue 的那行就地換掉），每個成員印一行 `DISPATCHED <n> <handle>`，或 `STOP <n> <原因>`（成員行的 state 記成 `stop`，原因只在這一行，要留就記進 `decisions.md`）；Bare guard 還原時另印 `UNBARE <主 checkout>`。exit 0 全部派出、4 有成員 STOP。`STOP <n> not-claimed` 照 claim 的 `STOP <n> claimed …` 處理：先跑 claim 看是誰，別的機器或 session 在做就從這一批拿掉、不放掉指派（同一個帳號，`--remove-assignee @me` 會拿掉對方的），`CLAIMED` 了才用同一個 key 只帶它重跑；`STOP <n> claim-check …` 是讀不到 Issue 留言，修好 gh 後重跑。認領之後、開 worktree 之前，成員本機已有分支（重跑）時，腳本照 Probe 的 `OVERLAP` 同一套比法（`pilot-probe.mjs` 共用）比對它和開著的 batch 裡其他 `running`、`done` 成員，改到同一個檔或同一個 `- **<名稱>.**` 條目就印 `STOP <n> overlap <m> <檔案>[:<條目>]…`（多個成員以 `, <m> …` 接著列），不關、不開分頁，分支與成員行都不動（比對本身失敗是 `STOP <n> overlap-check …`，成員行記 `stop`，修好 git 後重跑；#174：重派 #94 時 #134 正在改同一個 **Probe.** 條目，之後 stage 衝突整個重做）：用 `node scripts/gh-tracker.mjs blocked-by add <n> <m>`（[issue-tracker.md](issue-tracker.md#wayfinding-operations)）讓後做的 #n 等 #m 合入，放掉 #n 的認領，從這一批拿掉；只有兩邊確定不會衝突（例如 #m 已確定不合入）時才加 `--allow-overlap` 重跑。還沒派過的成員沒有分支可比。STOP 的成員修好原因後用同一個 key 只帶它重跑（worktree 已在就不再 create，先關掉 worktree 裡每個舊分頁再開新的，不必再從 checkpoint 撈 handle 手動 `terminal close`；成員行還是 `running`、它的分頁也還開著時印 `STOP <n> running <handle>`，什麼都不動，表示 worker 還在跑，重跑只帶 STOP 的成員）；`create` 開頭的 STOP 先到 Orca 查 worktree 是不是還在背景建立，不要直接重跑。不要自己手寫 `"$ORCA_CLI_COMMAND" worktree create`、`terminal create` 或裸 `terminal send` 的迴圈：Orca CLI 會吃掉 stdin，`while read` 只派到第一個成員；裸 `terminal send` 會回 accepted，文字卻停在輸入框沒提交。

- **Fresh redispatch.** 見 [pilot-conflict.md](pilot-conflict.md)：Stage 判定同一條目衝突，或 Probe 印 `WORKER <n> STOP findings after two review cycles` 時讀。

- **Scope supplement.** 見 [pilot-exceptions.md](pilot-exceptions.md)：Dispatch 之後要給 worker 補範圍時讀。

- **Watch.** `"$ORCA_CLI_COMMAND" terminal read --terminal <handle> --screen --json | jq -r '.result.terminal.tail[-40:][]'`（JSON 其餘大多是每行的 `trailingSpaces` 中繼資料，只取 `tail`；worker 的摘要和結果行都在這 40 行裡）：畫面最後一行是 `DONE <n> <sha>` 或 `STOP <n> <cause>` 就是做完了；`status: exited` 但沒有這行就是卡住。stuck-after 預設 90 分鐘，等累積了實際跑的時間再調。沒有背景 watcher 指令：worker 還在跑時，coordinator 每次被叫醒都 read 一次，以 1200 秒排下一次喚醒。

- **Agent rows.** 記在 batch checkpoint 的成員行（見 Batch）；worker 自己開的 subagent 不另外記。

- **Probe.** Reconcile 時在主 checkout 跑 `node scripts/pilot-probe.mjs <主 checkout> --apply --status --capacity ron-skills`（讀 running 成員要 `ORCA_CLI_COMMAND`，沒有時其他檢查照跑），整份輸出照行處理，不再手動拼 Bare guard、`git status`、Watch 與 fetch，也不用 sed、`node -e` 或 heredoc 改 batch checkpoint 與 `status.md`：`--apply` 把 `WORKER` 的 DONE、STOP 寫回成員列、把已進 `origin/main` 的 `merged` 寫成 `pushed`，`--status` 最後重產 `.scratch/pilot/status.md`（格式見 PILOT-STORE.md），兩者都不改其他輸出行；`--capacity ron-skills` 把這一輪還在跑的成員數寫進全機帳本 ron-skills 那一列（`scripts/pilot-capacity.mjs`，setup-workflow 正本的副本；帳本 `$PILOT_WORKERS_LEDGER`，預設 `~/.local/state/pilot-workers.tsv`，超過 2 小時沒更新的列不算），所有 repo 合計超過上限時最後印 `OVER_CAP <合計> <上限>`：這一輪不 Pick、不 Dispatch（fresh 重派也不做），只回報、不停掉已在跑的 worker；Report 時要重產 `status.md` 就再跑同一條。它會先跑 Bare guard（時機 `probe`，還原時印 `UNBARE`），沒事的項目不印；常見的行與處理：`DIRTY <status>`（主 checkout 有改動）先回報人，不 merge；`NOT_MAIN <分支>` 回報人，不 stage、不 merge，也不替人切回；`HOLD` 不做 Integrate；`REQUEST`、`GATE` 是 `requests.md`、`gates.md` 還開著的列，照 Requests、Gates 只打開對應那幾列處理；`WORKER <n> DONE <sha>`、`WORKER <n> STOP <cause>` 已由 `--apply` 記進 batch checkpoint 的 state 與 candidate（STOP 的原因只在這一行，要留就記進 `decisions.md`），`WORKER <n> STUCK …`（terminal 已結束卻沒有結果行、超過 stuck-after、讀不到 terminal、沒有 `ORCA_CLI_COMMAND`、checkpoint 的 started 或 stuck-after 寫壞）回報人，`WORKER <n> RUNNING <分鐘>` 不動；`OVERLAP <n> <m 或 integration> <檔案數> files [**<條目>.**…]` 是兩個開著的成員分支改到同一個檔案（`.md` 的改動都在 `- **<名稱>.**` 條目裡時細到條目），或成員改的地方 `pilot/integration` 自它的 base 以來也改過（#123），同一對只印一行，列出兩邊都改的檔案數與重疊的條目（條目不帶檔名，名稱可能有空格，以 `**`…`.**` 切分）；coordinator 不要濾掉 `OVERLAP` 行（#176：每檔一行時一輪幾十行，coordinator 用 `grep -v '^OVERLAP'` 連成員之間的重疊一起丟掉）。腳本只回報、不改派工或 stage 的順序：派下一批之前先排好順序，或用 `node scripts/gh-tracker.mjs blocked-by add <後做的> <先做的>`（[issue-tracker.md](issue-tracker.md#wayfinding-operations)）讓後一張等前一張合入；兩邊都已經 done 時先 stage 先進的那一個（`integration` 那一組就是這個成員），另一個等它合入後重派或在新的整合分支上重做衝突的條目；`STAGEABLE <key>`（每個沒移走的成員都 done）做 Stage；`MOVE <key> <n…>`（有 done 也有 stop、parked 的成員）照 Stage 先把列出的成員移走，下一輪就是 `STAGEABLE`；`PARKED <key> <n…>`（沒有 done 成員）不 stage，stop 的照 SKILL 處理 worker STOP 的方式、parked 的等 `UNPARK`；`UNPARK <n>`（暫緩到 #m 的成員，#m 已以 done 留在 closed 的 batch）跑 `node scripts/pilot-batch.mjs <主 checkout> unpark <n>` 改回 done，下一輪 `batch-<n>` 印 `STAGEABLE` 照常 stage（衝突照 Stage conflict 的解法）；`current:` 是 `merged <sha>` 或 `pushed <sha>` 的 batch 印 `IN_MAIN <key>`、`RESUME_PUSH <key>` 或 `NOT_IN_MAIN <key>`（腳本已 `git fetch origin`）：`gates.md` 裡這個 batch 還有開著的列就跳過，等 gate 解除；`IN_MAIN` 做 Close，`RESUME_PUSH` 從 Push gate 第 1 步接著做，`NOT_IN_MAIN <key>` 重跑 Push gate（各行的成因見 Probe lines）。`POOL_EMPTY`、`POOL_READY <n>...`、`POOL_FAILED <錯誤>` 是池子摘要（每輪一行，#240）：分桶與排序和 Pool 的 `issue-pool.mjs` 相同、已略過開著的 batch checkpoint 裡的 Issue；`POOL_EMPTY` 時閒置輪不必再跑 `issue-pool.mjs`（Pick 沒有單可挑），`POOL_READY` 時照 Pool 跑 `issue-pool.mjs` 挑單（`NO_CATEGORY` 只在它的輸出裡），`POOL_FAILED` 時照 Pool 跑 `issue-pool.mjs`，它也失敗就回報人。其他行（`ADAPTER_AHEAD`、`GATE_MALFORMED`、`DEPS_PROSE`、`DEPS_PROSE_FAILED`、`APPLY_MISS`、`RESTAGE`、`NOT_IN_MAIN <key> <原因>`、`FETCH_FAILED`、`PUSH_PARKED`、`PARENT_LABEL`、`PARENT_REOPEN`、`PARENT_APPLY_FAILED`）照 Probe lines 處理。腳本 exit 非 0 時先照 Bare guard 單獨跑 `scripts/pilot-unbare.sh`（時機 `probe`），把 stderr 回報人，這一輪不 stage、不 merge（只有 `APPLY_MISS`、`PARENT_APPLY_FAILED` 而 stderr 是空的時照 Probe lines 處理，不必跑 Bare guard）。

- **Probe lines.** 見 [pilot-exceptions.md](pilot-exceptions.md)：Probe 印了 Probe 條目沒處理的行（如 `ADAPTER_AHEAD`、`DEPS_PROSE`、`RESTAGE`、`PUSH_PARKED`）時讀。

- **Hold flag.** Integrate 前一步檢查 `.scratch/pilot/hold`，存在就不 merge；Probe 這時印 `HOLD`。設、清、看 hold 都用 `node scripts/pilot-hold.mjs <主 checkout> set <原因>`、`clear`、`show`，不手寫檔案。

- **Stage.** Stage、Regression、Integrate 由一個指令做完：在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-land.mjs <key> --check-command 'bin/check --upstream' --resolver scripts/pilot-resolve.mjs`（`bin/check --upstream` 約一分多鐘），不要再手打 git 指令或用 sed 改 checkpoint。要重新 stage（不是 `RESUME`）時它先讀 1 分鐘 load，超過 `$PILOT_LOAD_MAX`（寫在 `~/.zshrc` 的 30，沒設時 3 × 核心數）就印 `STOP load <load> <門檻>`、exit 4，stage worktree、stage 分支、checkpoint 與 `pilot/integration` 都沒動：這是負載關卡，不是 flake，不記重跑次數、不開 gate，下一輪重跑同一行就接著做（#178）。跑之前，Probe 印 `MOVE <key> <n…>` 時先把列出的成員移到自己的 batch：stop 的跑 `node scripts/pilot-batch.mjs <主 checkout> move <key> <n> --state stop`（新 batch 的成員行記 stop、清掉 candidate，舊行記 `moved batch-<n>`；全員移走時 `current:` 自動寫成 `closed moved`），不手抄表頭與成員行；不移的話，Close 會對這張還沒合入的 Issue 留證據、關單、移除 worktree（retro a6）。done 成員要等別的 Issue 先合入（例如兩張改同一列）時，跑 `node scripts/pilot-batch.mjs <主 checkout> park <key> <n> --after <m> --reason <原因>`：state 記 `parked after #<m>`、candidate 保留，不要寫成 stop。結果行與 STOP 見 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md#canonical-scripts)。腳本看到還有 `running` 或 `stop` 成員就印 `STOP member <n> <state>`，不 stage。它全在 `<stage worktree>` 做：stage worktree 還不存在時經 `scripts/orca-worktree-create.mjs` 跑 `"$ORCA_CLI_COMMAND" worktree create --name pilot-stage --base-branch pilot/integration --branch pilot/stage-<key>`（不帶 `--repo`、`--agent`），之後跑 Bare guard（時機 `stage #<key>`），沒有 `ORCA_CLI_COMMAND` 時印 `STOP no-stage-worktree`；已存在時工作樹要乾淨，不是就印 `STOP dirty <worktree>`，回報人。接著把 `pilot/stage-<key>` 重設到 `pilot/integration` 的 tip（同 key 的舊分支也從頭來），依號碼 `merge --no-ff` 每個 `done` 成員，把 staged SHA 和那個 tip 寫成 `current: staged <sha> onto <tip>`，印 `STAGED <key> <sha> onto <tip>`。衝突時它照 Stage conflict 的解法自己解，每解一次印 `RESOLVED <n> <解法> <檔案…>`，解完的 staged SHA 一樣要跑 Regression；解不了的先 `merge --abort`（stage worktree 是乾淨的），印 `STOP conflict <n> <檔>=<來源>:<種類> …`，照 Stage conflict 判斷重派這個成員還是開 gate。

- **Stage conflict.** 見 [pilot-conflict.md](pilot-conflict.md)：`pilot-land.mjs` 印 `RESOLVED` 或 `STOP conflict` 時讀。

- **Regression.** `pilot-land.mjs` 在 `<stage worktree>` 的 staged SHA、工作樹乾淨時跑 `<stage worktree>/bin/check --upstream`，exit 0 才算過；只對那個 SHA 有效。完整輸出在 `<主 checkout>/.scratch/pilot/reg-<key>.log`，結果追加成 `regression: <sha> exit <code>`，通過時後面附 `bin/check` 最後一行 `CHECK_PASS tests <a>+<b>+<c>`（各組測試的數目：tests、setup-workflow 正本、以 macOS 樣本重跑用到假 Orca 的測試；只看尾段的 `ℹ tests` 會只拿到最後一組）。沒過印 `STOP regression <exit>`，`pilot/integration` 不動：讀 log 找原因，修好後重跑同一行指令，它會重新 stage、重跑。

- **Integrate.** `pilot-land.mjs` 在 Regression 通過後先看 hold flag，存在就印 `STOP hold`；再比對 `pilot/integration` 現在的 tip 和 `current:` 記下的 `onto <tip>`，不同就印 `STOP drift`：stage 之後整合分支前進了，這個組合沒驗過。比的是 stage 當下記的 tip，不數 parent（batch-40-51 用 `$SHA^1` 誤判兩個成員的 batch），也不是 dispatch 時 `integration:` 行的 SHA（Push gate 的 `land.mjs` 會把 `pilot/integration` 推進到 PR 的 merge commit）。兩種 STOP 都不動 `pilot/integration`，下一輪重跑同一行指令：tip、成員組合與各成員分支都沒變、staged SHA 的 Regression 已經通過時直接從這一步繼續（印 `RESUME <key> <sha>`，不重跑 Regression），tip 變了就從新的 tip 重新 stage。都沒有才在 `<stage worktree>` 切回 `pilot/integration`、`merge --ff-only pilot/stage-<key>`、`branch -d pilot/stage-<key>`，把 `current:` 寫成 `merged <sha>`，最後一行印 `MERGED <key> <sha>`（已經 `merged` 時重跑只再印一次）。checkpoint 寫回後腳本會再讀一次，沒寫進去就印 `STOP checkpoint …`。stage worktree 停在 `pilot/integration` 等下一批，不移除。exit 0 是 `MERGED`、4 是 STOP、2 是用法錯誤。

- **Push gate.** 見 [pilot-after-merge.md](pilot-after-merge.md)：Stage 印 `MERGED`，或 Probe 印 `RESUME_PUSH`、`NOT_IN_MAIN` 時讀。

- **Close.** 見 [pilot-after-merge.md](pilot-after-merge.md)：Push gate 印 `LANDED`，或 Probe 印 `IN_MAIN` 時讀。

- **Handoff.** 見 [pilot-after-merge.md](pilot-after-merge.md)：Defaults 的 handoff 條件達到（合入 2 批或 compaction）時讀。
