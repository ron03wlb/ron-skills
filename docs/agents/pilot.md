# Pilot：ron-skills

給使用者層級的 `/issue-pilot` coordinator 用的專案設定（`/loop /issue-pilot`）。[issue-run.md](issue-run.md) 各段在 pilot 底下照樣適用，這裡只寫 pilot 不同的地方。本 repo 的 pilot 腳本有 Pool 與 Dispatch 認領的 `scripts/issue-pool.mjs`、Bare guard 的 `scripts/pilot-unbare.sh`、Probe 的 `scripts/pilot-probe.mjs`、Dispatch 的 `scripts/pilot-dispatch.mjs`（兩支都是 setup-workflow 正本的副本，Bare guard 用同目錄的 `pilot-unbare.sh`）和 Handoff 的 `scripts/pilot-handoff.mjs`（後兩者要 `ORCA_CLI_COMMAND`，Probe 讀 worker 時也要），Stage、Regression、Integrate 的 `scripts/pilot-land.mjs`，Close 的 `scripts/pilot-close.mjs`（它再呼叫 `scripts/pilot-counterpart.mjs`，Orca 指令同樣要 `ORCA_CLI_COMMAND`；本 repo 的留言、關單由它交給 `scripts/gh-tracker.mjs`），以及寫存檔的 `scripts/pilot-register.mjs`、`pilot-decision.mjs`、`pilot-request.mjs`、`pilot-hold.mjs`、`pilot-sources.mjs`、`pilot-gate.mjs`，Stage 搬移、暫緩成員的 `scripts/pilot-batch.mjs`，與 Push gate 產生 PR body 的 `scripts/pilot-pr-body.mjs`（都是 setup-workflow 正本的副本，指令與結果行見 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md#canonical-scripts)）；watch 由 coordinator 依下列指令手動做，`status.md` 由 Probe 的 `--status` 重產，沒列出的指令就是沒有。`.scratch/pilot/` 每個檔案（含 batch checkpoint）的路徑、格式與合法值都照 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md)，這裡只寫本 repo 的值。

- **Coordinator checkout.** 下文的 `<主 checkout>` 是 coordinator 所在 repo 的主 checkout，依機器不同（WSL、macOS 的路徑都不一樣），不寫死：coordinator 在主 checkout 時是 `git rev-parse --show-toplevel`；session 開在 linked worktree 時是 `git rev-parse --path-format=absolute --git-common-dir` 的上一層（兩種情況都可以用後者）。執行時代入實際的絕對路徑。`.scratch/pilot/` 放在主 checkout，不 commit。Orca 指令一律寫成 `"$ORCA_CLI_COMMAND"`（每台機器設成自己的 Orca CLI：WSL 是 PATH 上的指令名，macOS 是 Orca.app 內 `orca` 的絕對路徑）；沒有這個環境變數就回報人，不猜指令名。

- **Bare guard.** Orca 從 WSL 做 worktree 操作（create、rm 都會）時，可能把主 checkout `.git/config` 的 `core.bare` 改成 `true`，之後 `git status` 回 `must be run in a work tree`，stage、merge 全部失敗。在主 checkout 跑 `scripts/pilot-unbare.sh <主 checkout> <時機>`（時機如 `probe`、`dispatch #<n>`、`stage #<key>`、`close #<n>`）：是 bare 就執行 `git config core.bare false`、在 `.scratch/pilot/decisions.md` 的表格追加一列，並印出 `UNBARE <checkout>`；不是 bare 時不輸出。下列 Probe、Dispatch、Stage、Close 都只呼叫它。主 checkout 的工作樹還沒有這支腳本時（本機 `main` 落後 `origin/main`），改跑 `git -C <主 checkout> rev-parse --is-bare-repository`，印出 `true` 就執行 `git -C <主 checkout> config core.bare false`，再照 Decisions 記一列。

- **Permissions.** `.claude/settings.json` 的 `permissions.allow` 有三條，每條都是本 repo 的 wrapper（規則比對 `node scripts/<name>` 這個相對路徑）、只做 adapter 指定的步驟，auto mode 才不會擋成 External System Writes：`Bash(node scripts/gh-tracker.mjs:*)`，本 repo 的留言、label、關單、開單、sub-issue 與依賴都經這支（[issue-tracker.md](issue-tracker.md)，#96）；`Bash(node scripts/land.mjs:*)`，Push gate 與單獨跑的 `/issue-run` 落地時 push、開 PR、等 CI 通過後才合併（[Evidence and closing](issue-run.md#evidence-and-closing)）；`Bash(node scripts/pilot-close.mjs:*)`，Close 的證據留言、Counterpart 的跨 repo 對應單留言、關單，以及移除 worktree、刪本機與 `origin` 分支（`push origin --delete`）等收尾，這些都在 wrapper 底下跑、不再詢問（#131）。清單在 `scripts/check-coordinator-permissions.mjs`，`bin/check` 檢查每支都有放行規則，加新腳本時改那份清單、這一條與 allow。`gh pr merge` 會繞過 CI，不放行；wrapper 以外直接跑的跨 repo 寫入（`gh … --repo`）不放行；其他 git 寫入照 ADAPTER.md 的預設，每次都詢問。

- **Sessions.** Entry 成為 coordinator 時在主 checkout 跑 `node scripts/pilot-register.mjs <主 checkout> --name <ListAgents 印的 session 名稱> --loop yes|no <Sources 的每個檔案>`（pid、session 取 `$CLAUDE_PID`、`$CLAUDE_CODE_SESSION_ID`），之後每輪 Reconcile 一開始、跑 Probe 之前也跑同一條（只在 Entry 確認沒有別的 coordinator 活著之後跑，它會直接覆寫 `coordinator`）：它寫 `coordinator`（pid 不變時保留 `since`）、`sessions.md` 的 start 行只附加一次，最後記錄 Sources，印出的 `SOURCE_CHANGED`、`SOURCE_MISSING` 照 Sources 處理；`STOP retired` 表示這個 session 已交接出去，照 Entry 什麼都不做。不手寫 `coordinator` 與 start 行。

- **Sources.** 主 checkout 的 `AGENTS.md`（有的話）、`CLAUDE.md`、`docs/agents/issue-run.md`、`docs/agents/pilot.md`、`skills/engineering/issue-pilot/SKILL.md`、`skills/engineering/issue-pilot/PILOT-STORE.md`，以及 `~/.claude/skills/poteto-mode/SKILL.md` 的絕對路徑（執行時展開 `~`）。來源檢查就是每輪的 Sessions 指令：它最後以 `pilot-sources --record` 記錄這份清單，印出的每行 `SOURCE_CHANGED <path>`、`SOURCE_MISSING <path>` 就重讀那個檔案，沒有這兩種行就是都沒變；但第一輪與 compaction 之後仍照 SKILL 的 Sources 全部重讀，記錄可能是前任 session 留下的。同一輪不要再單獨跑 `node scripts/pilot-sources.mjs <主 checkout> --record …`：記錄已經被 Sessions 指令改寫，它什麼都印不出來，改過的檔案就漏讀了；只有那一輪沒跑 Sessions 指令時才單獨跑它。

- **Decisions.** `decisions.md` 只用 `node scripts/pilot-decision.mjs <主 checkout> --decision <決定> --reason <理由> --evidence <證據> --result <結果>` 附加，不手寫表格列；欄位不能有 `|`。Probe 或任何讀取發現表格散掉（`pilot-unbare.sh` 在檔案不存在時只附加列）時跑 `node scripts/pilot-decision.mjs <主 checkout> --repair`，`MALFORMED` 的行回報人。

- **Requests.** Probe 印出 `REQUEST` 時跑 `node scripts/pilot-request.mjs <主 checkout> list` 取得行號，處理完用 `node scripts/pilot-request.mjs <主 checkout> apply <行號> [--note <備註>]` 或 `decline <行號> --reason <原因>` 標記，不手寫 `applied`／`declined`。請求要合入沒有 Issue 的請求分支（`retro/<x>`）時，用請求的行號當 key，在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-land.mjs req-<行號> --branch retro/<x>`：它開出 `.scratch/pilot/batch-req-<行號>.md`（唯一的成員列 Issue 欄是 `-`，格式見 PILOT-STORE.md），之後 Stage、Regression、hold、Integrate 與結果行都照 Stage 到 Integrate 各條目，重跑同一行（帶不帶 `--branch` 都可以）從中斷處接著做；分支不存在印 `STOP branch …`，checkpoint 已有別的分支印 `STOP checkpoint …`。不要再手打 `switch -C pilot/stage-<x>`、`merge --no-ff`、`bin/check --upstream`、`merge --ff-only`、`branch -d`（請求 9、10 的做法沒留下 `regression:` 行，#143）。合入後照 Push gate 推上去（PR body 列這個 batch 的 staged SHA 與 Regression 結果，沒有 `Closes`），Close 對這個成員只清理 terminal、worktree、本機與 `origin` 的分支，再標記 `apply`；成員列沒有 handle，Close 會直接移除這個分支的 worktree，請求來源 session 還開著那個 worktree 時先請它結束。

- **Gates.** `gates.md` 不手改。開 gate 用 `node scripts/pilot-gate.mjs <主 checkout> open --title <標題> --issue <Issue 或 batch> --question <問題> --options <選項> --default <預設> --parked <擱置的項目>`（自動編號 `G<n>`、寫 `opened`，印 `GATE_OPENED G<n>`）；人回覆後用 `node scripts/pilot-gate.mjs <主 checkout> resolve G<n> --how <怎麼解、回覆在哪>` 解除（印 `GATE_RESOLVED G<n>`；`STOP G<n> resolved`、`STOP G<n> missing` 是已經解過或沒有這個 gate，檔案不動，先跑 `list` 對照）；`list` 列出開著的 gate，與 Probe 的 `GATE`、`GATE_MALFORMED` 行相同。依先例直接套用預設、不等人時，照樣先 `open` 留下紀錄，再用印出的 `G<n>` 立刻 `resolve`。欄位都是一行，`--how` 不能有 `|`。gate 要人改某個 worktree 裡的檔案（例如在成員的 `.claude/settings.json` 加 allow）時，`--question` 寫出檔案的絕對路徑，並附人可以直接用 `!` 執行的指令（編輯後 `git -C <worktree> commit`）；只寫相對路徑，人會改到主 checkout，Probe 印 `DIRTY` 擋住所有 merge（G10，#171）。

- **Defaults for `preferences.md`.** 不限同時跑的 worker 數；每批最多 2 個 Issue；worker 指令見 Dispatch；只有 coordinator 合進 batch 與整合分支；push、開 PR、合進 `main` 都由 coordinator 照 Push gate 做，不交給人（worker 不 push、不開 PR）；每個 session 合入 2 批或遇到 compaction 就 handoff。

- **Integration branch.** 本機 `pilot/integration`，第一次用時從 `main` 開（`git branch pilot/integration main`）。push、開 PR、合進 `main` 和之後跟上 `origin/main` 都見 Push gate。要手動讓它跟上 `origin/main` 時在 stage worktree 做：`git -C <stage worktree> switch pilot/integration && git -C <stage worktree> merge --ff-only origin/main`（stage worktree 還沒建時，主 checkout 不在 `pilot/integration` 上，用 `git -C <主 checkout> fetch . origin/main:pilot/integration`，非快轉時會拒絕）。

- **Stage worktree.** 下文的 `<stage worktree>` 是 `git -C <主 checkout> worktree list --porcelain` 裡分支（`branch refs/heads/…` 行）為 `pilot/integration` 或 `pilot/stage-*` 的那個 worktree，取它的 `worktree ` 行的路徑；找不到就是還沒建，照 Stage 用 Orca 建好後再找一次。Stage、Regression、Integrate 全在這裡做，`pilot/integration` 也只在這裡前進。主 checkout 一直停在 `main`，coordinator 在主 checkout 只做 fetch、讀狀態、快轉 `main`（`git -C <主 checkout> merge --ff-only origin/main`）：在主 checkout 切到還沒合入的分支，工作樹會帶出那個分支的 `.claude/settings.json`，在主 checkout 跑的 session 會即時載入它的 hook（#21）。

- **Scripts ahead.** Probe 印 `ADAPTER_AHEAD` 那一輪，整合分支 adapter 提到、主 checkout 還沒有的 `scripts/*.mjs`（`main` 上跑會 `MODULE_NOT_FOUND`），一律在主 checkout 以 `node <stage worktree>/scripts/<x>.mjs …` 執行，不必讀腳本確認：pilot 腳本以 cwd 的 `git worktree list` 第一行當主 checkout，從主 checkout 跑就對（#138）。

- **Pool.** `node scripts/issue-pool.mjs`（setup-workflow 正本的副本）把開著的 Issue 逐張分桶印成 `<桶> #<n> <標題>`，`ready` 桶已經排好序（`retro` label 的先、`priority` label 的先、直接或間接 block 最多開著的單的先、號碼小的先），照印出的順序挑，略過已經在某個開著的 batch checkpoint 裡的 Issue。分桶行之後的 `NO_CATEGORY <n>` 是開著、有 triage 狀態 label 卻沒有分類 label（[triage-labels.md](triage-labels.md#分類-label)）的單，母單與 `retro-candidates` 不算：照 `/triage` 補上一個分類 label（留言開頭放 AI 聲明、寫判斷理由），判斷不了就回報人；它不影響挑單，`ready` 桶照挑（#142：#130、#124、#123 只掛 `ready-for-agent` 與 `retro`，triage 的三個桶都沒列到）。帶 `retro` label 的 ready Issue 先挑：它是 `/retro-collect` 判定太大、交給 worker 的 retro 候選；候選清單本身掛 `retro-candidates`，留給 `/retro-collect`，不進池子。`ready` 桶就是[池子](../../GLOSSARY.md)：標 `ready-for-agent`，不是母單、沒有開著的 `blocked_by`、沒被[認領](../../GLOSSARY.md)，也沒有 `ready-for-human`、`needs-info`、`needs-triage`、`retro-candidates`（這些各有自己的桶，桶的優先序寫在腳本檔頭）；`stale`（認領超過 24 小時沒有新留言或新指派）不會自動釋放，回報人決定要不要取消指派。有 sub-issue 的是母單（`parent` 桶）：母單只分組、不派工也不驗收，pilot 一律挑它的子單（`/to-spec` 會給母單掛 `ready-for-agent`，不排除就會跟子單重複派工）。人手動跑 `/issue-run <母單>` 時仍照上游展開子單。`needs-triage` 的先照 [Readiness](issue-run.md#readiness) 補齊，變成 `ready-for-agent` 才挑。`/triage` 設了 `disable-model-invocation`，Skill tool 叫不動，coordinator 改讀 `~/.claude/skills/triage/SKILL.md` 自己照做：每則留言開頭放 AI 聲明，一個類別 label 加一個狀態 label；輸入都拿得到、範圍與驗收清楚才標 `ready-for-agent`，同時照同目錄的 `AGENT-BRIEF.md` 留一則 agent brief（#116 只留了 triage 理由，worker 拿到的只有 Issue 本文）；要拷問或要人決定的單標 `needs-info` 或 `ready-for-human`，交給人跑 `/triage`。

- **Batch.** 批次 checkpoint 是 `.scratch/pilot/batch-<key>.md`，由 Dispatch 建立；請求分支的 `batch-req-<行號>.md` 由 `pilot-land.mjs --branch` 建立（見 Requests）。各 Issue 自己的 checkpoint 仍在 `.scratch/issue-run-<n>/state.md`（在它的 worktree 裡）。

- **Brief check.** 沒有指令。worker 的 brief 就是 `/issue-run <n> --worker <checkpoint>` 加上 Issue 本文；tooling fix unit 的 brief 由 coordinator 寫在 `.scratch/pilot/briefs/`，派出去前自己核對契約列的每一節都在。

- **Dispatch.** 派工前先在主 checkout 對每個成員跑 `node scripts/issue-pool.mjs claim <n>`（session 取 `$CLAUDE_CODE_SESSION_ID`）：印 `CLAIMED <n>` 才派（同一個 session 重派會再認領一次，順便更新 `stale` 的時間）；認領者是這台機器上先前的 coordinator session（handoff 之前派的，`.scratch/pilot/sessions.md` 有它的 handoff 行），而 claim 的是現任 coordinator 時，腳本直接以那個 session 接手，印 `CLAIMED <n> takeover <session>`，照樣派；`STOP <n> claimed <機器>／<session>` 表示別的機器或 session 已經在做，這個成員不派、從這一批拿掉；`STOP <n> claimed <登入名>` 是有人手動指派（沒有認領留言，或指派換了人），回報人。認領之後 `pilot-dispatch.mjs` 對它印 `STOP`（`not-claimed` 除外）、這個成員不再重派時，用 `node scripts/gh-tracker.mjs edit <n> --remove-assignee @me` 放掉認領，免得其他機器要等它變成 `stale`。接著在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <key> <n>:<slug>...`（成員依號碼順序，如 `node scripts/pilot-dispatch.mjs 23-46 23:pilot-probe 46:pilot-dispatch`；腳本 540 秒內必定結束）。每個成員依序做：先讀 Issue 最近一則認領留言（格式與接手規則同 `issue-pool.mjs claim`），不是這個 session 的就印 `STOP <n> not-claimed`、成員行記 `stop`，不開 worktree、不開分頁（session 取 `$CLAUDE_CODE_SESSION_ID`，其次 `$ORCA_TERMINAL_HANDLE`，同 claim 的預設；claim 以 `--session` 帶前任 coordinator 認領的，靠 `sessions.md` 的接手規則算這個 session 的，帶其他 session 的不算；#165：claim 印了 `STOP` 卻在同一行用 `;` 接著跑 dispatch，照樣派出）；接著 `scripts/orca-worktree-create.mjs`（setup-workflow 正本的副本）建 worktree `issue-<n>`、分支 `issue/<n>-<slug>`、base `pilot/integration`，接著 Bare guard（時機 `dispatch #<n>`），以目錄存在、`git worktree list` 裡有這個分支判斷 worktree 建好（不信 create 回傳的 `ok`），再 `"$ORCA_CLI_COMMAND" terminal create --title '#<n>' --command claude`，最後用 orca-session-send 送出 `/issue-run <n> --worker <主 checkout>/.scratch/pilot/batch-<key>.md`。所有子行程的 stdin 都接 `/dev/null`。它會寫 batch checkpoint 的表頭（已存在就不動）和每個成員一行（重跑時同一個 Issue 的那行就地換掉），每個成員印一行 `DISPATCHED <n> <handle>`，或 `STOP <n> <原因>`（成員行的 state 記成 `stop`，原因只在這一行，要留就記進 `decisions.md`）；Bare guard 還原時另印 `UNBARE <主 checkout>`。exit 0 全部派出、4 有成員 STOP。`STOP <n> not-claimed` 照 claim 的 `STOP <n> claimed …` 處理：先跑 claim 看是誰，別的機器或 session 在做就從這一批拿掉、不放掉指派（同一個帳號，`--remove-assignee @me` 會拿掉對方的），`CLAIMED` 了才用同一個 key 只帶它重跑；`STOP <n> claim-check …` 是讀不到 Issue 留言，修好 gh 後重跑。認領之後、開 worktree 之前，成員本機已有分支（重跑）時，腳本照 Probe 的 `OVERLAP` 同一套比法（`pilot-probe.mjs` 共用）比對它和開著的 batch 裡其他 `running`、`done` 成員，改到同一個檔或同一個 `- **<名稱>.**` 條目就印 `STOP <n> overlap <m> <檔案>[:<條目>]…`（多個成員以 `, <m> …` 接著列），不關、不開分頁，分支不動，成員行記 `stop`（#174：重派 #94 時 #134 正在改同一個 **Probe.** 條目，之後 stage 衝突整個重做）：用 `node scripts/gh-tracker.mjs blocked-by add <n> <m>`（[issue-tracker.md](issue-tracker.md#wayfinding-operations)）讓後做的 #n 等 #m 合入，放掉 #n 的認領，從這一批拿掉；只有兩邊確定不會衝突（例如 #m 已確定不合入）時才加 `--allow-overlap` 重跑。還沒派過的成員沒有分支可比。STOP 的成員修好原因後用同一個 key 只帶它重跑（worktree 已在就不再 create，先關掉 worktree 裡每個舊分頁再開新的，不必再從 checkpoint 撈 handle 手動 `terminal close`）；`create` 開頭的 STOP 先到 Orca 查 worktree 是不是還在背景建立，不要直接重跑。不要自己手寫 `"$ORCA_CLI_COMMAND" worktree create`、`terminal create` 或裸 `terminal send` 的迴圈：Orca CLI 會吃掉 stdin，`while read` 只派到第一個成員；裸 `terminal send` 會回 accepted，文字卻停在輸入框沒提交。

- **Fresh redispatch.** Stage 判定同一條目衝突要重派成員時，先照 Dispatch 認領（認領者是前任 coordinator 時帶 `--session`），把給 fresh worker 的整併範圍寫進 `<主 checkout>/.scratch/pilot/fresh-<n>.md`（原 Issue、衝突檔、整合分支那一邊改了什麼、要怎麼整併），再在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <原 key> --fresh <n>:<slug> --note <主 checkout>/.scratch/pilot/fresh-<n>.md`。它不移除 worktree、不刪分支：關掉 worktree 裡每個 terminal，舊分支就地改名成 `issue/<n>-<slug>-prior`，從 `pilot/integration` 開同名新分支，worker 的 `.scratch/issue-run-<n>` 改名成 `issue-run-<n>-prior`，在 Issue 留言（note 加一行 `prior: <分支> @ <sha>`），把成員拆到 `batch-<n>.md`（表頭加一列，原 batch 那列記 `moved batch-<n>`），再照 Dispatch 開分頁、送出 worker 指令；印 `DISPATCHED <n> <handle>` 與 `PRIOR <n> <prior 分支> <sha>`。`STOP dirty <n>`（worktree 有未提交改動，什麼都沒動）回報人；`STOP <n> overlap <m> …`（要另存成 prior 的分支和開著的 `running`、`done` 成員改到同一處，什麼都沒動）照 Dispatch 的 overlap 處理，等 #m 合入後再重派；`STOP refresh-twice <n>` 照 Stage 開 gate，依先例（G2、G3、G5、G6、G14）直接套用預設「再重派一次」：照 Gates 先 `open` 再立刻 `resolve` 留紀錄，加 `--again` 重跑（另存成 `-prior2`，依序編號）；已經有 `-prior2`、這是第三次重派（SKILL 的 third forced re-stage）時才讓 gate 開著等人（#172）；其他 STOP 修好原因後重跑同一行，每一步都能從中斷處接著做。fresh worker 已經派出、還沒有 commit 時重跑會印 `STOP <n> running <handle>`，不關它的分頁；它有了 commit 之後重跑就是 `STOP refresh-twice`，`--again` 會關掉它的分頁，所以只在它做完（DONE 或 STOP）之後才加。G2–G7 手動重派留下 `-prior` 的 Issue，分支有了自己的 commit 時第一次跑就是 `STOP refresh-twice`。prior 分支不刪。不要再手做 `branch -m`、`switch -c`、搬 checkpoint 或改 `current:`、`integration:` 行。

- **Scope supplement.** Dispatch 之後要補範圍時，先在 Issue 留言（worker 以 Issue 為依據），再在主 checkout 跑 `node scripts/orca-session-send.mjs --terminal <handle> --prompt <提醒> --queue` 送提醒：它不等 worker 閒置，印 `QUEUED <handle>` 表示提醒已排進下一輪，`STOP <原因>` 時留言仍在，回報人（不加 `--queue` 會等 tui-idle，worker 一直在跑就逾時，#133）。Drain 到這個成員的 `DONE` 時，核對它的分支有沒有帶進補充的內容，沒有就回報人。

- **Watch.** `"$ORCA_CLI_COMMAND" terminal read --terminal <handle> --screen --json | jq -r '.result.terminal.tail[-40:][]'`（JSON 其餘大多是每行的 `trailingSpaces` 中繼資料，只取 `tail`；worker 的摘要和結果行都在這 40 行裡）：畫面最後一行是 `DONE <n> <sha>` 或 `STOP <n> <cause>` 就是做完了；`status: exited` 但沒有這行就是卡住。stuck-after 預設 90 分鐘，等累積了實際跑的時間再調。沒有背景 watcher 指令：worker 還在跑時，coordinator 每次被叫醒都 read 一次，以 1200 秒排下一次喚醒。

- **Agent rows.** 記在 batch checkpoint 的成員行（見 Batch）；worker 自己開的 subagent 不另外記。

- **Probe.** Reconcile 時在主 checkout 跑 `node scripts/pilot-probe.mjs <主 checkout> --apply --status`（讀 running 成員要 `ORCA_CLI_COMMAND`，沒有時其他檢查照跑），整份輸出照行處理，不再手動拼 Bare guard、`git status`、Watch 與 fetch，也不用 sed、`node -e` 或 heredoc 改 batch checkpoint 與 `status.md`：`--apply` 把 `WORKER` 的 DONE、STOP 寫回成員列、把已進 `origin/main` 的 `merged` 寫成 `pushed`，`--status` 最後重產 `.scratch/pilot/status.md`（格式見 PILOT-STORE.md），兩者都不改其他輸出行；Report 時要重產 `status.md` 就再跑同一條。它會先跑 Bare guard（時機 `probe`，還原時印 `UNBARE`），沒事的項目不印；各行與處理：`DIRTY <status>`（主 checkout 有改動）先回報人，不 merge；`NOT_MAIN <分支>` 回報人，不 stage、不 merge，也不替人切回；`HOLD` 不做 Integrate；`ADAPTER_AHEAD <檔案>` 是 `pilot/integration` 上的 adapter 比 `main` 新（整合分支有這個檔、內容不同，而且 `main` 最後一次改它的 commit 已在整合分支裡；兩邊都改過時不印；下一批在整合分支上 stage，#52），這一輪改讀 `git -C <主 checkout> show pilot/integration:<檔案>` 的版本；`REQUEST`、`GATE` 是 `requests.md`、`gates.md` 還開著的列，只打開對應那幾列處理；`GATE_MALFORMED <id> <行>` 是把 resolved 寫進別的欄位（如 `- status：resolved …`）的 gate，probe 仍當它開著，照 Gates 用 `resolve` 補上正確的 resolved 行；`DEPS_PROSE <n> #<m>` 是開著的 `ready-for-agent` Issue 內文寫了「依賴 #m」、#m 還開著，`blocked_by` 卻沒有它（Pool 只讀 `blocked_by`，會把 #n 跟 #m 同時派出，#94）：先讀那句確認說的是 #n 自己要等 #m（不是別張單或之後的子單），是才照 [issue-tracker.md](issue-tracker.md#wayfinding-operations) 的 Blocking 跑 `node scripts/gh-tracker.mjs blocked-by add <n> <m>`，再列 Pool 挑單（#n 這時進 `blocked` 桶，#m 關閉後才回到池子），不是就照常挑；`DEPS_PROSE_FAILED <錯誤>`（在主 checkout 跑 `gh` 失敗，這一輪的 PARENT_* 也沒檢查）回報人；`WORKER <n> DONE <sha>`、`WORKER <n> STOP <cause>` 已由 `--apply` 記進 batch checkpoint 的 state 與 candidate（STOP 的原因只在這一行，要留就記進 `decisions.md`），`APPLY_MISS <key> <n> rows <列數>`（對不到唯一一列 running 的成員列，沒寫檔）與 `APPLY_MISS <key> <n|current> verify`（寫回後再讀沒對上）會讓腳本 exit 1：照這一行回報人、不手改，這一輪不 stage、不 merge，不必照下面 exit 非 0 的做法跑 Bare guard（stderr 是空的），`WORKER <n> STUCK …`（terminal 已結束卻沒有結果行、超過 stuck-after、讀不到 terminal、沒有 `ORCA_CLI_COMMAND`、checkpoint 的 started 或 stuck-after 寫壞）回報人，`WORKER <n> RUNNING <分鐘>` 不動；`OVERLAP <n> <m 或 integration> <檔案>[:<條目>]` 是兩個開著的成員分支改到同一個檔案（`.md` 的改動都在 `- **<名稱>.**` 條目裡時細到條目），或成員改的地方 `pilot/integration` 自它的 base 以來也改過（#123），同一組只印一次，腳本只回報、不改派工或 stage 的順序：派下一批之前先排好順序，或用 `node scripts/gh-tracker.mjs blocked-by add <後做的> <先做的>`（[issue-tracker.md](issue-tracker.md#wayfinding-operations)）讓後一張等前一張合入；兩邊都已經 done 時先 stage 先進的那一個（`integration` 那一組就是這個成員），另一個等它合入後重派或在新的整合分支上重做衝突的條目；`STAGEABLE <key>`（每個沒移走的成員都 done）做 Stage；`MOVE <key> <n…>`（有 done 也有 stop、parked 的成員）照 Stage 先把列出的成員移走，下一輪就是 `STAGEABLE`；`PARKED <key> <n…>`（沒有 done 成員）不 stage，stop 的照 SKILL 處理 worker STOP 的方式、parked 的等 `UNPARK`；`UNPARK <n>`（暫緩到 #m 的成員，#m 已以 done 留在 closed 的 batch）跑 `node scripts/pilot-batch.mjs <主 checkout> unpark <n>` 改回 done，下一輪 `batch-<n>` 印 `STAGEABLE` 照常 stage（衝突照 Stage 的解法）；`current:` 是 `merged <sha>` 或 `pushed <sha>` 的 batch 印 `IN_MAIN <key>`、`RESUME_PUSH <key>` 或 `NOT_IN_MAIN <key>`（腳本已 `git fetch origin`）：`gates.md` 裡這個 batch 還有開著的列就跳過，等 gate 解除；`IN_MAIN` 做 Close（`merged` 已由 `--apply` 改成 `pushed`）；`RESUME_PUSH` 是 Integrate 之後、Push gate 做完之前中斷的 `merged` batch（`pilot/integration` 的 tip 等於最後一次 Regression SHA，#37），從 Push gate 第 1 步接著做，PR 已經開著時第 1 步會先更新 body、`land.mjs` 沿用它從等 CI、合併那步接著做；`NOT_IN_MAIN <key>` 是還沒進 `origin/main` 的 `pushed` batch（`--apply` 只在 merge 進了 `origin/main` 之後才寫 `pushed`，所以只有舊格式或之後被 revert 才會出現），重跑 Push gate（`land.mjs` 每一步都能從中斷處接著做）；`NOT_IN_MAIN <key> no-sha`、`NOT_IN_MAIN <key> no-regression`（`merged` 卻沒有 `regression:` 行，或它的 SHA 解析不到）、`NOT_IN_MAIN <key> tip <sha 或 none>`（`merged` 但 `pilot/integration` 的 tip 不是 Regression SHA，直接推會送出沒驗過的內容）與 `FETCH_FAILED` 回報人。母單（[issue-tracker.md](issue-tracker.md#母單)）由腳本整理，不再手動跑關係總覽（#164：寫在條目尾端的手動步驟好幾輪都被 stage 與 land 擠掉）：`PARENT_LABEL <n>`（開著、有 sub-issue，或已關閉卻有開著子單的母單，沒有 `parent` label 或還掛 triage label）與 `PARENT_REOPEN <n>`（開著的子單指向已關閉的母單 #n，新掛上或子單被重開）已由 `--apply` 經 `scripts/gh-tracker.mjs` 補上 `parent`、移除 triage label 或重開，不必再做；`PARENT_APPLY_FAILED <n> <錯誤>`（寫入失敗，腳本 exit 1，其他母單照修）回報人，不在 wrapper 外手動重跑。腳本 exit 非 0 時先照 Bare guard 單獨跑 `scripts/pilot-unbare.sh`（時機 `probe`），把 stderr 回報人，這一輪不 stage、不 merge（只有 `APPLY_MISS`、`PARENT_APPLY_FAILED` 而 stderr 是空的時照那兩行處理，不必跑 Bare guard）。

- **Hold flag.** Integrate 前一步檢查 `.scratch/pilot/hold`，存在就不 merge；Probe 這時印 `HOLD`。設、清、看 hold 都用 `node scripts/pilot-hold.mjs <主 checkout> set <原因>`、`clear`、`show`，不手寫檔案。

- **Stage.** Stage、Regression、Integrate 由一個指令做完：在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-land.mjs <key>`（`bin/check --upstream` 約一分多鐘），不要再手打 git 指令或用 sed 改 checkpoint。跑之前，Probe 印 `MOVE <key> <n…>` 時先把列出的成員移到自己的 batch：stop 的跑 `node scripts/pilot-batch.mjs <主 checkout> move <key> <n> --state stop`（新 batch 的成員行記 stop、清掉 candidate，舊行記 `moved batch-<n>`；全員移走時 `current:` 自動寫成 `closed moved`），不手抄表頭與成員行；不移的話，Close 會對這張還沒合入的 Issue 留證據、關單、移除 worktree（retro a6）。done 成員要等別的 Issue 先合入（例如兩張改同一列）時，跑 `node scripts/pilot-batch.mjs <主 checkout> park <key> <n> --after <m> --reason <原因>`：state 記 `parked after #<m>`、candidate 保留，不要寫成 stop。結果行與 STOP 見 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md#canonical-scripts)。腳本看到還有 `running` 或 `stop` 成員就印 `STOP member <n> <state>`，不 stage。它全在 `<stage worktree>` 做：stage worktree 還不存在時經 `scripts/orca-worktree-create.mjs` 跑 `"$ORCA_CLI_COMMAND" worktree create --name pilot-stage --base-branch pilot/integration --branch pilot/stage-<key>`（不帶 `--repo`、`--agent`），之後跑 Bare guard（時機 `stage #<key>`），沒有 `ORCA_CLI_COMMAND` 時印 `STOP no-stage-worktree`；已存在時工作樹要乾淨，不是就印 `STOP dirty <worktree>`，回報人。接著把 `pilot/stage-<key>` 重設到 `pilot/integration` 的 tip（同 key 的舊分支也從頭來），依號碼 `merge --no-ff` 每個 `done` 成員，把 staged SHA 和那個 tip 寫成 `current: staged <sha> onto <tip>`，印 `STAGED <key> <sha> onto <tip>`。衝突只照下列解法自己解，每解一次印 `RESOLVED <n> <解法> <檔案…>`，解完的 staged SHA 一樣要跑 Regression：衝突檔有戳記檔（`scripts/restamp.mjs` 的 `STAMP_FILES`：`scripts/workflow-doc-sync.json`、`docs/agents/workflow-templates.json`）時（兩邊合併前都已各自對照 `docs/workflow/` 並 restamp），其他衝突檔先用下列解法解完，再交給和 `land.mjs` 共用的 `restamp()` 依合併結果重算：`workflow-doc-sync.json` 重產站台後跑 `scripts/check-workflow-sync.mjs --restamp`，`workflow-templates.json` 取兩邊條目的聯集、依合併後的副本重算 sha256（`restamp`，#72、#173；和別的解法一起時 restamp 排最後，印成 `entries+restamp`、`rows+restamp` 這類組合）；每個衝突 hunk 的 base 都是空的、兩邊只是在同一處新增不重疊的段落時，依號碼兩段都留下（`additions`；兩邊各自新增同一個檔、新增的段落有相同的行或同名的條目都不算）；每個衝突 hunk 裡兩邊改的是不同的 `- **<名稱>.**` 條目時各取各的版本，兩邊改過的條目都留下（`entries`，#45）；衝突 hunk 的 base、ours、theirs 三份的行都是 Markdown 表格列（`|` 開頭）時，以第一格為鍵，兩邊改的是不同列就各取各的版本、依原順序排好，新增的列都留下（`rows`，#162；同一列兩邊都改、一邊刪一邊改、兩邊新增同一個鍵、某一份有重複的鍵、留下的列順序變了、各列欄數不同都仍是衝突）。`additions`、`entries` 與 `rows` 只解三個版本都是 UTF-8 文字的檔案。其他衝突（包括戳記檔和解不了的檔一起衝突）它先 `merge --abort`，印 `STOP conflict <n> <檔案…>`，stage worktree 是乾淨的。這時先判斷是不是同一條目衝突：比對兩邊對每個衝突檔的改動（`git -C <主 checkout> diff pilot/integration...issue/<n>-<slug> -- <檔>` 是成員改的，`git -C <主 checkout> diff issue/<n>-<slug>...pilot/integration -- <檔>` 是整合分支改的），至少一個檔是兩邊都改了同一個 `- **<名稱>.**` 條目（或 skill 的同一條規則），其餘衝突檔只是同一處改動在 `docs/workflow/` 的轉述、產生的 html 與戳記檔。是的話不開 gate，照 Fresh redispatch 重派這個成員，帶上整併後的範圍，並照 Decisions 記一筆（衝突檔、prior 分支與 SHA）；重派後原 batch 只剩其他成員，重跑 `pilot-land.mjs <key>` 合入它們。同一個 Issue 重派後又衝突時 `--fresh` 印 `STOP refresh-twice <n>`，這時才開 gate，預設選項是「再重派一次」（帶 `--again`）。其他衝突照舊變成 gate。

- **Regression.** `pilot-land.mjs` 在 `<stage worktree>` 的 staged SHA、工作樹乾淨時跑 `<stage worktree>/bin/check --upstream`，exit 0 才算過；只對那個 SHA 有效。完整輸出在 `<主 checkout>/.scratch/pilot/reg-<key>.log`，結果追加成 `regression: <sha> exit <code>`，通過時後面附 `bin/check` 最後一行 `CHECK_PASS tests <a>+<b>+<c>`（各組測試的數目：tests、setup-workflow 正本、以 macOS 樣本重跑用到假 Orca 的測試；只看尾段的 `ℹ tests` 會只拿到最後一組）。沒過印 `STOP regression <exit>`，`pilot/integration` 不動：讀 log 找原因，修好後重跑同一行指令，它會重新 stage、重跑。

- **Integrate.** `pilot-land.mjs` 在 Regression 通過後先看 hold flag，存在就印 `STOP hold`；再比對 `pilot/integration` 現在的 tip 和 `current:` 記下的 `onto <tip>`，不同就印 `STOP drift`：stage 之後整合分支前進了，這個組合沒驗過。比的是 stage 當下記的 tip，不數 parent（batch-40-51 用 `$SHA^1` 誤判兩個成員的 batch），也不是 dispatch 時 `integration:` 行的 SHA（Push gate 的 `land.mjs` 會把 `pilot/integration` 推進到 PR 的 merge commit）。兩種 STOP 都不動 `pilot/integration`，下一輪重跑同一行指令：tip、成員組合與各成員分支都沒變、staged SHA 的 Regression 已經通過時直接從這一步繼續（印 `RESUME <key> <sha>`，不重跑 Regression），tip 變了就從新的 tip 重新 stage。都沒有才在 `<stage worktree>` 切回 `pilot/integration`、`merge --ff-only pilot/stage-<key>`、`branch -d pilot/stage-<key>`，把 `current:` 寫成 `merged <sha>`，最後一行印 `MERGED <key> <sha>`（已經 `merged` 時重跑只再印一次）。checkpoint 寫回後腳本會再讀一次，沒寫進去就印 `STOP checkpoint …`。stage worktree 停在 `pilot/integration` 等下一批，不移除。exit 0 是 `MERGED`、4 是 STOP、2 是用法錯誤。

- **Push gate.** `pilot/integration` 的 tip 等於最後一次 Regression 通過的 SHA。通過後 coordinator 在主 checkout 依序執行：
  1. 跑 `node scripts/pilot-pr-body.mjs <主 checkout> --out .scratch/pilot/pr-body.md`（與 `gh pr edit`、第 2 步的 `land.mjs` 是同一個檔）（setup-workflow 正本的副本），印 `PR_BODY …` 才往下：它從 `current: merged` 的 batch checkpoint 列出這個 PR 裡的全部 batch、各自的 staged SHA、最後的 `regression:` 行和每個 Issue 成員的 `Closes #<n>`（請求分支成員沒有 Issue，列分支名稱），結尾帶署名；不要再跑迴圈抽 checkpoint、heredoc 手寫或用 sed 插列（#145）。`STOP no-merged-batch` 表示沒有待推的 batch，`STOP regression <key>` 表示那個 batch 最後的 Regression 不是它的 staged SHA 通過，都不往下推，變成 gate。`gh pr list --head pilot/integration --state open --json url --jq '.[].url'` 輸出非空時，PR 已經開著，`land.mjs` 會沿用它但不改 body，先跑 `gh pr edit pilot/integration --body-file .scratch/pilot/pr-body.md`。
  2. 用 Bash `timeout: 600000` 跑 `node scripts/land.mjs pilot/integration --keep-branch --title '<batch key 與標題>' --body-file .scratch/pilot/pr-body.md`。它依序 push、找或開 PR、等 CI、`gh pr merge --merge`（不刪分支），再在 stage worktree 把 `pilot/integration` 以 `--ff-only` 跟上 `origin/main` 後 push，並讓主 checkout 的 `main` 跟上；不用 `git branch -f`，它會把 upstream 改成 `origin/main`。
  3. 最後一行是 `LANDED <pr> <merge sha>` 就接著做 Close，不手改 `current:`：Close 做完會寫成 `closed`；Close 之前中斷時，下一輪 Probe 印 `IN_MAIN` 並由 `--apply` 把 `merged` 寫成 `pushed`；`STOP checks-timeout` 下一輪重跑；`STOP behind-main`（`pilot/integration` 沒包含 origin/main，push 事件的 CI 會跑舊 workflow）在 `<stage worktree>` 手動做（`pilot-land.mjs` 只合 batch 成員）：`git -C <stage worktree> switch -C pilot/stage-sync-main pilot/integration`、`git -C <stage worktree> merge --no-ff --no-edit origin/main`，在新的 SHA 跑 `<stage worktree>/bin/check --upstream`，exit 0 才 `git -C <stage worktree> switch pilot/integration && git -C <stage worktree> merge --ff-only pilot/stage-sync-main && git -C <stage worktree> branch -d pilot/stage-sync-main`，再重跑本步；其他 `STOP <原因>` 變成 gate。`WARN main-not-synced` 不擋，Close 開頭會再檢查。
  4. `STOP ci-not-started <pr> <原因> repo <可見性>[（額度提示）] <run 網址>`：失敗的 job 全都 0 個 step，GitHub Actions 沒有啟動它們（#132）。`<原因>` 是 check-run annotation 的第一句（讀不到時是 `unknown`，含空白，網址取行尾）；repo 是 private 時 `<可見性>` 後面緊接全形括號的提示：帳號下所有 private repo 共用 Actions 額度，到 Billing & plans → Usage 查看。不要原樣重跑（job 一樣不會啟動）。`<原因>` 寫著 recent account payments have failed 或 spending limit（帳務擋下）時，在第 2 步的指令加 `--local-checks <Regression SHA> --check-command 'bin/check --upstream'` 重跑（不帶 `--check-command` 時正本跑的是 `bin/check`）；`unknown` 或其他原因（runner 沒接單、policy 擋下）不改用本機結果，開 gate 交給人；兩種情況的付款與額度設定都由人處理。`land.mjs` 不等 GitHub checks，改確認 `pilot/integration` 的 tip 等於這個 SHA，在它的暫時 worktree（工作樹乾淨）重跑 `bin/check --upstream`，exit 0 而且有 `CHECK_PASS` 行才合併，並在 PR 留言附 SHA 與 `CHECK_PASS` 行（`LOCAL_CHECKS <pr> <sha> <CHECK_PASS 行>`）；tip 不符印 `STOP local-checks-sha`、檢查沒過印 `STOP local-checks-failed`（完整輸出在主 checkout 的 `.scratch/land-local-checks-<sha>.log`），都還沒 push，照其他 STOP 變成 gate；只有 `STOP local-checks-failed … exit ETIMEDOUT`（`bin/check` 超過 420 秒，實測約 170 秒，多半是 clone 上游卡住）先重跑同一條指令一次。這是放寬關卡，只在 CI 沒啟動時用：CI 有跑起來而失敗（job 有 step，例如測試紅燈）不能改用本機結果，照 `ci-failed` 處理；也不能為了省等待時間跳過 CI。把用 `--local-checks` 的原因與 run 網址記進 `decisions.md`。

- **Counterpart.** 跨 repo 的[對應單](../../GLOSSARY.md)交接由 Close 的 `scripts/pilot-close.mjs` 在證據留言之後做：它把成員本文交給 `scripts/pilot-counterpart.mjs`，每張印出的 `COUNTERPART` 都用 `<主 checkout>/.scratch/pilot/counterpart-<n>.md` 的內容到那張對應單留言。指令依對應單的 host 選：裸的 `<owner>/<repo>#<m>` 是 github.com，印 `COUNTERPART <owner>/<repo>#<m>`；GitLab（含自架的 http、IP，例如 spay2 在 `http://192.168.200.202`）與 GitHub Enterprise 的對應單在本文寫成 issue 網址（`http://192.168.200.202/spay/spay2/-/issues/692`），印 `COUNTERPART <path>#<m> <github|gitlab> <repo>`；GitLab 對應單寫成裸 ref 時 `gh` 讀不到，Close 印 `STOP <n> counterpart <ref> …`，提示改寫成 issue 網址（改成員本文後重跑）。腳本帶 `--file <交接檔>` 時每張後面多一行 `COMMAND <指令>`，取自 setup-workflow 的 gh／glab 對照表（`scripts/lib/hosts.mjs`，人看的是 [HOSTS.md](../../skills/engineering/setup-workflow/HOSTS.md)，旗標的 `--help` 核對紀錄也在那裡）：GitHub 是 `gh issue comment <m> --repo <repo> --body-file <檔>`，GitLab 是 `glab issue note <m> -R <專案網址> -m "$(cat <檔>)"`（`glab issue note` 沒有 `-F`／`--body-file`）；Close 執行的與交給人的是同一行。寫入被擋下時（auto mode 分類器以 External System Writes 擋、沒有權限、沒裝或沒登入 `glab`，或讀不到 GitLab 對應單的留言）Close 不停：每張印 `HANDOFF <n> <ref> ! <指令>`、這一步印 `MANUAL <n> counterpart`，照常往下關單、收尾；coordinator 把交接檔路徑和那行指令（前面加 `!` 就能在人的 prompt 直接跑）列給人，不自己在 wrapper 外重跑（直接跑的跨 repo 寫入不放行，見 Permissions）。整個 `pilot-close.mjs` 被擋下時也一樣：先用 `gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs --file <交接檔>` 取得 `COMMAND` 行交給人，Close 照常往下做。交接內容要 coordinator 自己寫：跑 Close 前先看成員本文（`gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs`，沒有輸出就不用寫），有對應單就寫好這個檔：成員 `ron03wlb/ron-skills#<n>`、ron-skills 的 merge SHA 與 PR 網址、這個成員改了什麼、對方要做的下一步。檔案不在，或沒寫出 merge SHA 與 `ron03wlb/ron-skills#<n>`，腳本會印 `STOP <n> counterpart …`，寫好後重跑。同一張對應單可能有好幾個成員（例如 #28、#29、#30 都指向同一張），所以略過條件兩個都比：對應單已經有同時含 merge SHA 與 `ron03wlb/ron-skills#<n>` 的留言就略過。給人的回報列出每張對應單和留言網址（#53）。

- **Close.** Push gate 印出 `LANDED`、batch 的 merge 進到 `origin/main` 之後馬上做，不等人：在主 checkout 跑 `node scripts/pilot-close.mjs <key> <pr> <merge sha>`，不要再手寫 shell function（batch-40-51 手寫的版本用了 `branch -D`，orca 的錯誤也被 `2>/dev/null` 吞掉）。它先照 Bare guard 跑一次 `scripts/pilot-unbare.sh`（時機 `close #<key>`，上一輪可能中斷在 Orca 設成 bare 之後），再確認 merge SHA 已在 `origin/main`、主 checkout 在 `main` 上，`git -C <主 checkout> merge-base --is-ancestor origin/main main` 不是 0 就 `merge --ff-only origin/main`；再對 batch checkpoint 每個 `done` 成員照 [Evidence and closing](issue-run.md#evidence-and-closing) 依序做，每一步先看做過沒有，做過就略過，所以中斷後用同一行指令重跑：`evidence` 證據留言（附 PR 網址、merge SHA 與 `regression:` 行；留言已含 merge SHA 時略過）；`counterpart` 照 Counterpart 到對應單交接（交接檔要 coordinator 先寫好，沒有時 STOP；留言被擋下時印 `HANDOFF` 行與 `MANUAL <n> counterpart`，不停）；`close` 關 Issue（PR 的 `Closes #<n>` 已經關掉時略過）；`terminal` 用 `"$ORCA_CLI_COMMAND" terminal close --terminal <handle>` 關成員的 terminal（worktree 已移除或 `"$ORCA_CLI_COMMAND" terminal list --worktree path:<worktree>` 裡沒有它時略過）；`worktree` 用 `"$ORCA_CLI_COMMAND" worktree rm --worktree path:<worktree>` 移除 worktree（`<worktree>` 取自 `git worktree list`；Orca 開的 worktree 用 `branch:` 選擇器找不到，#49），rm 之後跑 Bare guard（時機 `close #<n>`），再以 `git worktree list` 確認真的不在；`branch` 用 `git -C <主 checkout> branch -d issue/<n>-<slug>` 刪本機分支（一律 `-d`：沒合進 `main` 就讓 git 拒絕；分支設了 upstream 時 `-d` 只比 upstream，所以先以 `merge-base --is-ancestor <分支> main` 檢查，沒合入就 STOP；Orca rm 已經一起刪掉時略過）；`remote` 在 `ls-remote --exit-code --heads origin issue/<n>-<slug>` exit 0 時 `push origin --delete`，exit 2（遠端沒有，worker 不 push）略過，其他 exit code STOP；`parent` 在成員有母單、母單還開著而且 `sub_issues_summary.completed == total` 時，留言列出每張子單和它的 `state_reason`（`completed` 與 `not_planned` 都算結束）再關閉母單。子行程的 stdin 都接 `/dev/null`；stderr 照常顯示，只濾掉 WSL 上 Orca 每次都印的 crashpad 錯誤行（`registration_protocol_win.cc`）。每一步印一行 `DONE <n> <step>` 或 `SKIP <n> <step>`（開頭 `main` 那步的 `<n>` 是 batch key；checkpoint 不在、沒有 `current:` 行或沒有 `done` 成員時只印 `STOP <key> checkpoint …`；有 `done` 成員的 branch 欄是空的或不是 `issue/<這一列的 n>-<slug>` 時，在 Bare guard 與任何寫入之前只印 `STOP branch-malformed <n> <JSON 字串的值>`（#120），把 checkpoint 那一列改對再重跑；這些都沒有 DONE／SKIP 行），請求分支成員（Issue 欄 `-`，見 Requests）沒有 Issue：只做 `terminal`、`worktree`、`branch`、`remote`，不留言、不關單、不呼叫 `gh` 與 `gh-tracker.mjs`，結果行的 `<n>` 與 Bare guard 的時機（`close <分支>`）用分支名稱，branch 欄要是 `retro/<x>`，否則同樣 `STOP branch-malformed - <值>`。全部成員做完它把 `current:` 設成 `closed`，最後一行印 `CLOSED <key>`（exit 0）。任何一步失敗都印 `STOP <n> <step> <原因>`（exit 4）並停在那一步：`counterpart` 缺交接檔時照 Counterpart 寫好再重跑；`branch` 的 STOP 表示這個分支有沒合進 `main` 的 commit，分支留著，回報人；其他 STOP 變成 gate。exit 2 是用法錯誤或沒有 `ORCA_CLI_COMMAND`。

- **Handoff.** 條件達到時（見 Defaults），coordinator 先照 Decisions 記一筆原因、停掉自己的背景工作，再在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-handoff.mjs --session "$CLAUDE_CODE_SESSION_ID" --pid "$CLAUDE_PID" --reason <原因>`（setup-workflow 正本的副本；本 repo 沒有「整合分支合併進行中」的檢查，所以不帶 `--held-check`；要交給已經開著的 session 時加 `--to <分頁標題或 handle>`。腳本 540 秒內必定結束：逾時印 `STOP timeout`，收到 SIGTERM、SIGINT 印 `STOP signal <名稱>`，都會先還原）。它確認 `coordinator` 的 pid 是自己後改寫成 handoff 行，新開分頁 `issue-pilot coordinator` 送出 `/loop /issue-pilot`（或送給 `--to` 的 session），等新 session 寫入 `pid ` 行。最後一行 `HANDED_OFF <handle>` 才算交接完成，腳本這時已在 `sessions.md` 附加 handoff 行，coordinator 不再手動附加；`STOP <原因>` 時 `coordinator` 已還原、這次新開的分頁已關掉、`sessions.md` 沒動，照常繼續當 coordinator（`STOP not-coordinator` 表示已經有別的 coordinator，不要再交接；`STOP to-not-found`、`to-ambiguous`、`to-self` 是 `--to` 沒對到唯一一個別的 session，改用 handle 或不帶 `--to` 重跑）。

- **Retro collect.** `/retro-collect` 在主 checkout 跑，把開著的 `retro-candidates` Issue 做成一個 retro 單位；`<key>` 是 `<MMDD><字母>`，和計畫檔 `.scratch/retro/plan-<key>.md` 同名。認領：在主 checkout 對每張跑 `node scripts/issue-pool.mjs claim <n>`，印 `CLAIMED <n>` 才收，`STOP <n> claimed …` 表示別的 session 在收、這次略過。目標分支是 `main`。worktree：設了 `ORCA_CLI_COMMAND` 時 `node scripts/orca-worktree-create.mjs --name retro-<key> --base-branch main --branch retro/<key>`（看最後一行 JSON 的 `path`），沒有 Orca 時 `git worktree add -b retro/<key> <路徑> main`。計畫檔寫在主 checkout，不寫在 retro worktree：`land.mjs` 移除 worktree 時會一起刪掉（#170）。檢查：開發中 `bin/check`，合入前在 tip、工作樹乾淨時跑 `bin/check --upstream`。commit 用 `git add -A`：`.scratch` 已在 `.gitignore`，再加 `':!.scratch'` 排除會讓 git 印 ignored 提示並 exit 1，`&&` 後面的 commit 不會跑（#170）。合入與 push 照 [Evidence and closing](issue-run.md#evidence-and-closing) 單獨跑的方式：PR body 每張收集的 Issue 一行 `Closes #<n>`，用 Bash `timeout: 600000` 跑 `node scripts/land.mjs retro/<key> --title 'chore: retro <key>' --body-file <檔>`，結果行的處理也照那一段。
