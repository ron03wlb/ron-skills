# Pilot：ron-skills

給使用者層級的 `/issue-pilot` coordinator 用的專案設定（`/loop /issue-pilot`）。[issue-run.md](issue-run.md) 各段在 pilot 底下照樣適用，這裡只寫 pilot 不同的地方。本 repo 的 pilot 腳本有 Pool 與 Dispatch 認領的 `scripts/issue-pool.mjs`、Bare guard 的 `scripts/pilot-unbare.sh`、Probe 的 `scripts/pilot-probe.mjs`、Dispatch 的 `scripts/pilot-dispatch.mjs`（兩支都是 setup-workflow 正本的副本，Bare guard 用同目錄的 `pilot-unbare.sh`）和 Handoff 的 `scripts/pilot-handoff.mjs`（後兩者要 `ORCA_CLI_COMMAND`，Probe 讀 worker 時也要），Stage、Regression、Integrate 的 `scripts/pilot-land.mjs`，Close 的 `scripts/pilot-close.mjs`（它再呼叫 `scripts/pilot-counterpart.mjs`，Orca 指令同樣要 `ORCA_CLI_COMMAND`；本 repo 的留言、關單由它交給 `scripts/gh-tracker.mjs`），以及寫存檔的 `scripts/pilot-register.mjs`、`pilot-decision.mjs`、`pilot-request.mjs`、`pilot-hold.mjs`、`pilot-sources.mjs`（setup-workflow 正本的副本，指令與結果行見 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md#canonical-scripts)）；watch、status 都由 coordinator 依下列指令手動做，沒列出的指令就是沒有。`.scratch/pilot/` 每個檔案（含 batch checkpoint）的路徑、格式與合法值都照 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md)，這裡只寫本 repo 的值。

- **Coordinator checkout.** 下文的 `<主 checkout>` 是 coordinator 所在 repo 的主 checkout，依機器不同（WSL、macOS 的路徑都不一樣），不寫死：coordinator 在主 checkout 時是 `git rev-parse --show-toplevel`；session 開在 linked worktree 時是 `git rev-parse --path-format=absolute --git-common-dir` 的上一層（兩種情況都可以用後者）。執行時代入實際的絕對路徑。`.scratch/pilot/` 放在主 checkout，不 commit。Orca 指令一律寫成 `"$ORCA_CLI_COMMAND"`（每台機器設成自己的 Orca CLI：WSL 是 PATH 上的指令名，macOS 是 Orca.app 內 `orca` 的絕對路徑）；沒有這個環境變數就回報人，不猜指令名。

- **Bare guard.** Orca 從 WSL 做 worktree 操作（create、rm 都會）時，可能把主 checkout `.git/config` 的 `core.bare` 改成 `true`，之後 `git status` 回 `must be run in a work tree`，stage、merge 全部失敗。在主 checkout 跑 `scripts/pilot-unbare.sh <主 checkout> <時機>`（時機如 `probe`、`dispatch #<n>`、`stage #<key>`、`close #<n>`）：是 bare 就執行 `git config core.bare false`、在 `.scratch/pilot/decisions.md` 的表格追加一列，並印出 `UNBARE <checkout>`；不是 bare 時不輸出。下列 Probe、Dispatch、Stage、Close 都只呼叫它。主 checkout 的工作樹還沒有這支腳本時（本機 `main` 落後 `origin/main`），改跑 `git -C <主 checkout> rev-parse --is-bare-repository`，印出 `true` 就執行 `git -C <主 checkout> config core.bare false`，再照 Decisions 記一列。

- **Permissions.** `.claude/settings.json` 的 `permissions.allow` 只有 `Bash(node scripts/gh-tracker.mjs:*)`：本 repo 的留言、label、關單、開單、sub-issue 與依賴都經這支 wrapper（[issue-tracker.md](issue-tracker.md)），auto mode 才不會擋成 External System Writes（#96）。跨 repo 的寫入（Counterpart）不放行；git 寫入照 ADAPTER.md 的預設，每次都詢問。

- **Sessions.** Entry 成為 coordinator 時在主 checkout 跑 `node scripts/pilot-register.mjs <主 checkout> --name <ListAgents 印的 session 名稱> --loop yes|no <Sources 的每個檔案>`（pid、session 取 `$CLAUDE_PID`、`$CLAUDE_CODE_SESSION_ID`），之後每輪 Reconcile 一開始、跑 Probe 之前也跑同一條（只在 Entry 確認沒有別的 coordinator 活著之後跑，它會直接覆寫 `coordinator`）：它寫 `coordinator`（pid 不變時保留 `since`）、`sessions.md` 的 start 行只附加一次，最後記錄 Sources，印出的 `SOURCE_CHANGED`、`SOURCE_MISSING` 照 Sources 處理；`STOP retired` 表示這個 session 已交接出去，照 Entry 什麼都不做。不手寫 `coordinator` 與 start 行。

- **Sources.** 主 checkout 的 `AGENTS.md`（有的話）、`CLAUDE.md`、`docs/agents/issue-run.md`、`docs/agents/pilot.md`、`skills/engineering/issue-pilot/SKILL.md`、`skills/engineering/issue-pilot/PILOT-STORE.md`，以及 `~/.claude/skills/poteto-mode/SKILL.md` 的絕對路徑（執行時展開 `~`）。來源檢查就是每輪的 Sessions 指令：它最後以 `pilot-sources --record` 記錄這份清單，印出的每行 `SOURCE_CHANGED <path>`、`SOURCE_MISSING <path>` 就重讀那個檔案，沒有這兩種行就是都沒變；但第一輪與 compaction 之後仍照 SKILL 的 Sources 全部重讀，記錄可能是前任 session 留下的。同一輪不要再單獨跑 `node scripts/pilot-sources.mjs <主 checkout> --record …`：記錄已經被 Sessions 指令改寫，它什麼都印不出來，改過的檔案就漏讀了；只有那一輪沒跑 Sessions 指令時才單獨跑它。

- **Decisions.** `decisions.md` 只用 `node scripts/pilot-decision.mjs <主 checkout> --decision <決定> --reason <理由> --evidence <證據> --result <結果>` 附加，不手寫表格列；欄位不能有 `|`。Probe 或任何讀取發現表格散掉（`pilot-unbare.sh` 在檔案不存在時只附加列）時跑 `node scripts/pilot-decision.mjs <主 checkout> --repair`，`MALFORMED` 的行回報人。

- **Requests.** Probe 印出 `REQUEST` 時跑 `node scripts/pilot-request.mjs <主 checkout> list` 取得行號，處理完用 `node scripts/pilot-request.mjs <主 checkout> apply <行號> [--note <備註>]` 或 `decline <行號> --reason <原因>` 標記，不手寫 `applied`／`declined`。

- **Defaults for `preferences.md`.** 不限同時跑的 worker 數；每批最多 2 個 Issue；worker 指令見 Dispatch；只有 coordinator 合進 batch 與整合分支；push、開 PR、合進 `main` 都由 coordinator 照 Push gate 做，不交給人（worker 不 push、不開 PR）；每個 session 合入 2 批或遇到 compaction 就 handoff。

- **Integration branch.** 本機 `pilot/integration`，第一次用時從 `main` 開（`git branch pilot/integration main`）。push、開 PR、合進 `main` 和之後跟上 `origin/main` 都見 Push gate。要手動讓它跟上 `origin/main` 時在 stage worktree 做：`git -C <stage worktree> switch pilot/integration && git -C <stage worktree> merge --ff-only origin/main`（stage worktree 還沒建時，主 checkout 不在 `pilot/integration` 上，用 `git -C <主 checkout> fetch . origin/main:pilot/integration`，非快轉時會拒絕）。

- **Stage worktree.** 下文的 `<stage worktree>` 是 `git -C <主 checkout> worktree list --porcelain` 裡分支（`branch refs/heads/…` 行）為 `pilot/integration` 或 `pilot/stage-*` 的那個 worktree，取它的 `worktree ` 行的路徑；找不到就是還沒建，照 Stage 用 Orca 建好後再找一次。Stage、Regression、Integrate 全在這裡做，`pilot/integration` 也只在這裡前進。主 checkout 一直停在 `main`，coordinator 在主 checkout 只做 fetch、讀狀態、快轉 `main`（`git -C <主 checkout> merge --ff-only origin/main`）：在主 checkout 切到還沒合入的分支，工作樹會帶出那個分支的 `.claude/settings.json`，在主 checkout 跑的 session 會即時載入它的 hook（#21）。

- **Pool.** `node scripts/issue-pool.mjs`（setup-workflow 正本的副本）把開著的 Issue 逐張分桶印成 `<桶> #<n> <標題>`，`ready` 桶已經排好序（`retro` label 的先、`priority` label 的先、直接或間接 block 最多開著的單的先、號碼小的先），照印出的順序挑，略過已經在某個開著的 batch checkpoint 裡的 Issue。帶 `retro` label 的 ready Issue 先挑：它是 `/retro-collect` 判定太大、交給 worker 的 retro 候選；候選清單本身掛 `retro-candidates`，留給 `/retro-collect`，不進池子。`ready` 桶就是[池子](../../GLOSSARY.md)：標 `ready-for-agent`，不是母單、沒有開著的 `blocked_by`、沒被[認領](../../GLOSSARY.md)，也沒有 `ready-for-human`、`needs-info`、`needs-triage`、`retro-candidates`（這些各有自己的桶，桶的優先序寫在腳本檔頭）；`stale`（認領超過 24 小時沒有新留言或新指派）不會自動釋放，回報人決定要不要取消指派。有 sub-issue 的是母單（`parent` 桶）：母單只分組、不派工也不驗收，pilot 一律挑它的子單（`/to-spec` 會給母單掛 `ready-for-agent`，不排除就會跟子單重複派工）。人手動跑 `/issue-run <母單>` 時仍照上游展開子單。`needs-triage` 的先照 [Readiness](issue-run.md#readiness) 補齊，變成 `ready-for-agent` 才挑。`/triage` 設了 `disable-model-invocation`，Skill tool 叫不動，coordinator 改讀 `~/.claude/skills/triage/SKILL.md` 自己照做：每則留言開頭放 AI 聲明，一個類別 label 加一個狀態 label；輸入都拿得到、範圍與驗收清楚才標 `ready-for-agent`，同時照同目錄的 `AGENT-BRIEF.md` 留一則 agent brief（#116 只留了 triage 理由，worker 拿到的只有 Issue 本文）；要拷問或要人決定的單標 `needs-info` 或 `ready-for-human`，交給人跑 `/triage`。

- **Batch.** 批次 checkpoint 是 `.scratch/pilot/batch-<key>.md`，由 Dispatch 建立。各 Issue 自己的 checkpoint 仍在 `.scratch/issue-run-<n>/state.md`（在它的 worktree 裡）。

- **Brief check.** 沒有指令。worker 的 brief 就是 `/issue-run <n> --worker <checkpoint>` 加上 Issue 本文；tooling fix unit 的 brief 由 coordinator 寫在 `.scratch/pilot/briefs/`，派出去前自己核對契約列的每一節都在。

- **Dispatch.** 派工前先在主 checkout 對每個成員跑 `node scripts/issue-pool.mjs claim <n>`（session 取 `$CLAUDE_CODE_SESSION_ID`）：印 `CLAIMED <n>` 才派（同一個 session 重派會再認領一次，順便更新 `stale` 的時間）；`STOP <n> claimed <機器>／<session>` 表示別的機器或 session 已經在做，這個成員不派、從這一批拿掉。認領者是這台機器上先前的 coordinator session（handoff 之前派的，`.scratch/pilot/sessions.md` 查得到）時，改用 `--session <那個 session>` 重跑接手；`STOP <n> claimed <登入名>` 是有人手動指派（沒有認領留言，或指派換了人），回報人。認領之後 `pilot-dispatch.mjs` 對它印 `STOP`、這個成員不再重派時，用 `node scripts/gh-tracker.mjs edit <n> --remove-assignee @me` 放掉認領，免得其他機器要等它變成 `stale`。接著在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <key> <n>:<slug>...`（成員依號碼順序，如 `node scripts/pilot-dispatch.mjs 23-46 23:pilot-probe 46:pilot-dispatch`；腳本 540 秒內必定結束）。每個成員依序做：`scripts/orca-worktree-create.mjs`（setup-workflow 正本的副本）建 worktree `issue-<n>`、分支 `issue/<n>-<slug>`、base `pilot/integration`，接著 Bare guard（時機 `dispatch #<n>`），以目錄存在、`git worktree list` 裡有這個分支判斷 worktree 建好（不信 create 回傳的 `ok`），再 `"$ORCA_CLI_COMMAND" terminal create --title '#<n>' --command claude`，最後用 orca-session-send 送出 `/issue-run <n> --worker <主 checkout>/.scratch/pilot/batch-<key>.md`。所有子行程的 stdin 都接 `/dev/null`。它會寫 batch checkpoint 的表頭（已存在就不動）和每個成員一行（重跑時同一個 Issue 的那行就地換掉），每個成員印一行 `DISPATCHED <n> <handle>`，或 `STOP <n> <原因>`（成員行的 state 記成 `stop`，原因只在這一行，要留就記進 `decisions.md`）；Bare guard 還原時另印 `UNBARE <主 checkout>`。exit 0 全部派出、4 有成員 STOP。STOP 的成員修好原因後用同一個 key 只帶它重跑（worktree 已在就不再 create）；`create` 開頭的 STOP 先到 Orca 查 worktree 是不是還在背景建立，不要直接重跑。不要自己手寫 `"$ORCA_CLI_COMMAND" worktree create`、`terminal create` 或裸 `terminal send` 的迴圈：Orca CLI 會吃掉 stdin，`while read` 只派到第一個成員；裸 `terminal send` 會回 accepted，文字卻停在輸入框沒提交。

- **Scope supplement.** Dispatch 之後要補範圍時，先在 Issue 留言（worker 以 Issue 為依據），再在主 checkout 跑 `node scripts/orca-session-send.mjs --terminal <handle> --prompt <提醒> --queue` 送提醒：它不等 worker 閒置，印 `QUEUED <handle>` 表示提醒已排進下一輪，`STOP <原因>` 時留言仍在，回報人（不加 `--queue` 會等 tui-idle，worker 一直在跑就逾時，#133）。Drain 到這個成員的 `DONE` 時，核對它的分支有沒有帶進補充的內容，沒有就當 STOP 處理。

- **Watch.** `"$ORCA_CLI_COMMAND" terminal read --terminal <handle> --screen --json | jq -r '.result.terminal.tail[-40:][]'`（JSON 其餘大多是每行的 `trailingSpaces` 中繼資料，只取 `tail`；worker 的摘要和結果行都在這 40 行裡）：畫面最後一行是 `DONE <n> <sha>` 或 `STOP <n> <cause>` 就是做完了；`status: exited` 但沒有這行就是卡住。stuck-after 預設 90 分鐘，等累積了實際跑的時間再調。沒有背景 watcher 指令：worker 還在跑時，coordinator 每次被叫醒都 read 一次，以 1200 秒排下一次喚醒。

- **Agent rows.** 記在 batch checkpoint 的成員行（見 Batch）；worker 自己開的 subagent 不另外記。

- **Probe.** Reconcile 時在主 checkout 跑 `node scripts/pilot-probe.mjs <主 checkout>`（讀 running 成員要 `ORCA_CLI_COMMAND`，沒有時其他檢查照跑），整份輸出照行處理，不再手動拼 Bare guard、`git status`、Watch 與 fetch。它會先跑 Bare guard（時機 `probe`，還原時印 `UNBARE`），沒事的項目不印；各行與處理：`DIRTY <status>`（主 checkout 有改動）先回報人，不 merge；`NOT_MAIN <分支>` 回報人，不 stage、不 merge，也不替人切回；`HOLD` 不做 Integrate；`ADAPTER_AHEAD <檔案>` 是 `pilot/integration` 上的 adapter 比 `main` 新（整合分支有這個檔、內容不同，而且 `main` 最後一次改它的 commit 已在整合分支裡；兩邊都改過時不印；下一批在整合分支上 stage，#52），這一輪改讀 `git -C <主 checkout> show pilot/integration:<檔案>` 的版本；`REQUEST`、`GATE` 是 `requests.md`、`gates.md` 還開著的列，只打開對應那幾列處理；`GATE_MALFORMED <id> <行>` 是把 resolved 寫進別的欄位（如 `- status：resolved …`）的 gate，probe 仍當它開著，把那一行改成 `- resolved <time> <how>`；`WORKER <n> DONE <sha>`、`WORKER <n> STOP <cause>` 記進 batch checkpoint 的 state 與 candidate，`WORKER <n> STUCK …`（terminal 已結束卻沒有結果行、超過 stuck-after、讀不到 terminal、沒有 `ORCA_CLI_COMMAND`、checkpoint 的 started 或 stuck-after 寫壞）回報人，`WORKER <n> RUNNING <分鐘>` 不動；`STAGEABLE <key>` 做 Stage；`current:` 是 `merged <sha>` 或 `pushed <sha>` 的 batch 印 `IN_MAIN <key>`、`RESUME_PUSH <key>` 或 `NOT_IN_MAIN <key>`（腳本已 `git fetch origin`）：`gates.md` 裡這個 batch 還有開著的列就跳過，等 gate 解除；`IN_MAIN` 做 Close；`RESUME_PUSH` 是 Integrate 之後、Push gate 做完之前中斷的 `merged` batch（`pilot/integration` 的 tip 等於最後一次 Regression SHA，#37），從 Push gate 第 1 步接著做，PR 已經開著時第 1 步會先更新 body、`land.mjs` 沿用它從等 CI、合併那步接著做；`NOT_IN_MAIN <key>` 是還沒進 `origin/main` 的 `pushed` batch（照 Push gate 第 3 步，`LANDED` 之後才設 `pushed <sha>`，所以只有舊格式或 `LANDED` 之後被 revert 才會出現），重跑 Push gate（`land.mjs` 每一步都能從中斷處接著做）；`NOT_IN_MAIN <key> no-sha`、`NOT_IN_MAIN <key> no-regression`（`merged` 卻沒有 `regression:` 行，或它的 SHA 解析不到）、`NOT_IN_MAIN <key> tip <sha 或 none>`（`merged` 但 `pilot/integration` 的 tip 不是 Regression SHA，直接推會送出沒驗過的內容）與 `FETCH_FAILED` 回報人。腳本 exit 非 0 時先照 Bare guard 單獨跑 `scripts/pilot-unbare.sh`（時機 `probe`），把 stderr 回報人，這一輪不 stage、不 merge。最後整理母單：用 [issue-tracker.md](issue-tracker.md#母單) 的關係總覽（只列開著的 issue），`subIssuesSummary.total > 0` 的是開著的母單，補上 `parent` label、移除所有 triage label（`node scripts/gh-tracker.mjs edit <n> --add-label parent --remove-label <label>`）；開著的 issue 的 `parent.number` 不在總覽裡，就是有開著子單（新掛上或子單被重開）卻已關閉的母單，用 `gh issue reopen <n>` 重開。

- **Hold flag.** Integrate 前一步檢查 `.scratch/pilot/hold`，存在就不 merge；Probe 這時印 `HOLD`。設、清、看 hold 都用 `node scripts/pilot-hold.mjs <主 checkout> set <原因>`、`clear`、`show`，不手寫檔案。

- **Stage.** Stage、Regression、Integrate 由一個指令做完：在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-land.mjs <key>`（`bin/check --upstream` 約一分多鐘），不要再手打 git 指令或用 sed 改 checkpoint。跑之前，成員有 `stop` 時先把它移到自己的 batch：開 `.scratch/pilot/batch-<n>.md`（表頭照抄、成員行照抄），舊 checkpoint 那一行的 state 改成 `moved batch-<n>`；不移的話，Close 會對這張還沒合入的 Issue 留證據、關單、移除 worktree（retro a6）。腳本看到還有 `running` 或 `stop` 成員就印 `STOP member <n> <state>`，不 stage。它全在 `<stage worktree>` 做：stage worktree 還不存在時經 `scripts/orca-worktree-create.mjs` 跑 `"$ORCA_CLI_COMMAND" worktree create --name pilot-stage --base-branch pilot/integration --branch pilot/stage-<key>`（不帶 `--repo`、`--agent`），之後跑 Bare guard（時機 `stage #<key>`），沒有 `ORCA_CLI_COMMAND` 時印 `STOP no-stage-worktree`；已存在時工作樹要乾淨，不是就印 `STOP dirty <worktree>`，回報人。接著把 `pilot/stage-<key>` 重設到 `pilot/integration` 的 tip（同 key 的舊分支也從頭來），依號碼 `merge --no-ff` 每個 `done` 成員，把 staged SHA 和那個 tip 寫成 `current: staged <sha> onto <tip>`，印 `STAGED <key> <sha> onto <tip>`。衝突只照下列解法自己解，每解一次印 `RESOLVED <n> <解法> <檔案…>`，解完的 staged SHA 一樣要跑 Regression：衝突檔有 `scripts/workflow-doc-sync.json` 時（兩邊合併前都已各自對照 `docs/workflow/` 並 restamp），其他衝突檔先用下兩種解法解完，再依合併結果跑 `scripts/check-workflow-sync.mjs --restamp` 重算（`restamp`，#72；和別的解法一起時印成 `entries+restamp` 這類組合）；每個衝突 hunk 的 base 都是空的、兩邊只是在同一處新增不重疊的段落時，依號碼兩段都留下（`additions`；兩邊各自新增同一個檔、新增的段落有相同的行或同名的條目都不算）；每個衝突 hunk 裡兩邊改的是不同的 `- **<名稱>.**` 條目時各取各的版本，兩邊改過的條目都留下（`entries`，#45）。`additions` 與 `entries` 只解三個版本都是 UTF-8 文字的檔案。其他衝突（包括戳記檔和解不了的檔一起衝突）它先 `merge --abort`，印 `STOP conflict <n> <檔案…>`，stage worktree 是乾淨的，這時變成 gate。

- **Regression.** `pilot-land.mjs` 在 `<stage worktree>` 的 staged SHA、工作樹乾淨時跑 `<stage worktree>/bin/check --upstream`，exit 0 才算過；只對那個 SHA 有效。完整輸出在 `<主 checkout>/.scratch/pilot/reg-<key>.log`，結果追加成 `regression: <sha> exit <code>`，通過時後面附 `bin/check` 最後一行 `CHECK_PASS tests <a>+<b>+<c>`（各組測試的數目：tests、setup-workflow 正本、以 macOS 樣本重跑用到假 Orca 的測試；只看尾段的 `ℹ tests` 會只拿到最後一組）。沒過印 `STOP regression <exit>`，`pilot/integration` 不動：讀 log 找原因，修好後重跑同一行指令，它會重新 stage、重跑。

- **Integrate.** `pilot-land.mjs` 在 Regression 通過後先看 hold flag，存在就印 `STOP hold`；再比對 `pilot/integration` 現在的 tip 和 `current:` 記下的 `onto <tip>`，不同就印 `STOP drift`：stage 之後整合分支前進了，這個組合沒驗過。比的是 stage 當下記的 tip，不數 parent（batch-40-51 用 `$SHA^1` 誤判兩個成員的 batch），也不是 dispatch 時 `integration:` 行的 SHA（Push gate 的 `land.mjs` 會把 `pilot/integration` 推進到 PR 的 merge commit）。兩種 STOP 都不動 `pilot/integration`，下一輪重跑同一行指令：tip、成員組合與各成員分支都沒變、staged SHA 的 Regression 已經通過時直接從這一步繼續（印 `RESUME <key> <sha>`，不重跑 Regression），tip 變了就從新的 tip 重新 stage。都沒有才在 `<stage worktree>` 切回 `pilot/integration`、`merge --ff-only pilot/stage-<key>`、`branch -d pilot/stage-<key>`，把 `current:` 寫成 `merged <sha>`，最後一行印 `MERGED <key> <sha>`（已經 `merged` 時重跑只再印一次）。checkpoint 寫回後腳本會再讀一次，沒寫進去就印 `STOP checkpoint …`。stage worktree 停在 `pilot/integration` 等下一批，不移除。exit 0 是 `MERGED`、4 是 STOP、2 是用法錯誤。

- **Push gate.** `pilot/integration` 的 tip 等於最後一次 Regression 通過的 SHA。通過後 coordinator 在主 checkout 依序執行：
  1. 把 PR body 寫進 `.scratch/pilot/pr-body.md`：列出這個 PR 裡的全部 batch、各自的 staged SHA、Regression 結果（exit code）和每個成員的 `Closes #<n>`。`gh pr list --head pilot/integration --state open --json url --jq '.[].url'` 輸出非空時，PR 已經開著，`land.mjs` 會沿用它但不改 body，先跑 `gh pr edit pilot/integration --body-file .scratch/pilot/pr-body.md`。
  2. 用 Bash `timeout: 600000` 跑 `node scripts/land.mjs pilot/integration --keep-branch --title '<batch key 與標題>' --body-file .scratch/pilot/pr-body.md`。它依序 push、找或開 PR、等 CI、`gh pr merge --merge`（不刪分支），再在 stage worktree 把 `pilot/integration` 以 `--ff-only` 跟上 `origin/main` 後 push，並讓主 checkout 的 `main` 跟上；不用 `git branch -f`，它會把 upstream 改成 `origin/main`。
  3. 最後一行是 `LANDED <pr> <merge sha>` 就把 `current:` 設成 `pushed <sha>`，接著做 Close；`STOP checks-timeout` 下一輪重跑；`STOP behind-main`（`pilot/integration` 沒包含 origin/main，push 事件的 CI 會跑舊 workflow）在 `<stage worktree>` 手動做（`pilot-land.mjs` 只合 batch 成員）：`git -C <stage worktree> switch -C pilot/stage-sync-main pilot/integration`、`git -C <stage worktree> merge --no-ff --no-edit origin/main`，在新的 SHA 跑 `<stage worktree>/bin/check --upstream`，exit 0 才 `git -C <stage worktree> switch pilot/integration && git -C <stage worktree> merge --ff-only pilot/stage-sync-main && git -C <stage worktree> branch -d pilot/stage-sync-main`，再重跑本步；其他 `STOP <原因>` 變成 gate。`WARN main-not-synced` 不擋，Close 開頭會再檢查。

- **Counterpart.** 跨 repo 的[對應單](../../GLOSSARY.md)交接由 Close 的 `scripts/pilot-close.mjs` 在證據留言之後做：它把成員本文交給 `scripts/pilot-counterpart.mjs`，每張印出的 `COUNTERPART <owner>/<repo>#<m>` 都用 `<主 checkout>/.scratch/pilot/counterpart-<n>.md` 的內容到那張對應單留言。交接內容要 coordinator 自己寫：跑 Close 前先看成員本文（`gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs`，沒有輸出就不用寫），有對應單就寫好這個檔：成員 `ron03wlb/ron-skills#<n>`、ron-skills 的 merge SHA 與 PR 網址、這個成員改了什麼、對方要做的下一步。檔案不在，或沒寫出 merge SHA 與 `ron03wlb/ron-skills#<n>`，腳本會印 `STOP <n> counterpart …`，寫好後重跑。同一張對應單可能有好幾個成員（例如 #28、#29、#30 都指向同一張），所以略過條件兩個都比：對應單已經有同時含 merge SHA 與 `ron03wlb/ron-skills#<n>` 的留言就略過。給人的回報列出每張對應單和留言網址（#53）。

- **Close.** Push gate 印出 `LANDED`、batch 的 merge 進到 `origin/main` 之後馬上做，不等人：在主 checkout 跑 `node scripts/pilot-close.mjs <key> <pr> <merge sha>`，不要再手寫 shell function（batch-40-51 手寫的版本用了 `branch -D`，orca 的錯誤也被 `2>/dev/null` 吞掉）。它先照 Bare guard 跑一次 `scripts/pilot-unbare.sh`（時機 `close #<key>`，上一輪可能中斷在 Orca 設成 bare 之後），再確認 merge SHA 已在 `origin/main`、主 checkout 在 `main` 上，`git -C <主 checkout> merge-base --is-ancestor origin/main main` 不是 0 就 `merge --ff-only origin/main`；再對 batch checkpoint 每個 `done` 成員照 [Evidence and closing](issue-run.md#evidence-and-closing) 依序做，每一步先看做過沒有，做過就略過，所以中斷後用同一行指令重跑：`evidence` 證據留言（附 PR 網址、merge SHA 與 `regression:` 行；留言已含 merge SHA 時略過）；`counterpart` 照 Counterpart 到對應單交接（交接檔要 coordinator 先寫好，沒有時 STOP）；`close` 關 Issue（PR 的 `Closes #<n>` 已經關掉時略過）；`terminal` 用 `"$ORCA_CLI_COMMAND" terminal close --terminal <handle>` 關成員的 terminal（worktree 已移除或 `"$ORCA_CLI_COMMAND" terminal list --worktree path:<worktree>` 裡沒有它時略過）；`worktree` 用 `"$ORCA_CLI_COMMAND" worktree rm --worktree path:<worktree>` 移除 worktree（`<worktree>` 取自 `git worktree list`；Orca 開的 worktree 用 `branch:` 選擇器找不到，#49），rm 之後跑 Bare guard（時機 `close #<n>`），再以 `git worktree list` 確認真的不在；`branch` 用 `git -C <主 checkout> branch -d issue/<n>-<slug>` 刪本機分支（一律 `-d`：沒合進 `main` 就讓 git 拒絕；分支設了 upstream 時 `-d` 只比 upstream，所以先以 `merge-base --is-ancestor <分支> main` 檢查，沒合入就 STOP；Orca rm 已經一起刪掉時略過）；`remote` 在 `ls-remote --exit-code --heads origin issue/<n>-<slug>` exit 0 時 `push origin --delete`，exit 2（遠端沒有，worker 不 push）略過，其他 exit code STOP；`parent` 在成員有母單、母單還開著而且 `sub_issues_summary.completed == total` 時，留言列出每張子單和它的 `state_reason`（`completed` 與 `not_planned` 都算結束）再關閉母單。子行程的 stdin 都接 `/dev/null`；stderr 照常顯示，只濾掉 WSL 上 Orca 每次都印的 crashpad 錯誤行（`registration_protocol_win.cc`）。每一步印一行 `DONE <n> <step>` 或 `SKIP <n> <step>`（開頭 `main` 那步的 `<n>` 是 batch key；checkpoint 不在、沒有 `current:` 行或沒有 `done` 成員時只印 `STOP <key> checkpoint …`；有 `done` 成員的 branch 欄是空的或不是 `issue/<這一列的 n>-<slug>` 時，在 Bare guard 與任何寫入之前只印 `STOP branch-malformed <n> <JSON 字串的值>`（#120），把 checkpoint 那一列改對再重跑；這些都沒有 DONE／SKIP 行），全部成員做完它把 `current:` 設成 `closed`，最後一行印 `CLOSED <key>`（exit 0）。任何一步失敗都印 `STOP <n> <step> <原因>`（exit 4）並停在那一步：`counterpart` 缺交接檔時照 Counterpart 寫好再重跑；`branch` 的 STOP 表示這個分支有沒合進 `main` 的 commit，分支留著，回報人；其他 STOP 變成 gate。exit 2 是用法錯誤或沒有 `ORCA_CLI_COMMAND`。

- **Handoff.** 條件達到時（見 Defaults），coordinator 先照 Decisions 記一筆原因、停掉自己的背景工作，再在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-handoff.mjs --session "$CLAUDE_CODE_SESSION_ID" --pid "$CLAUDE_PID" --reason <原因>`（setup-workflow 正本的副本；本 repo 沒有「整合分支合併進行中」的檢查，所以不帶 `--held-check`；要交給已經開著的 session 時加 `--to <分頁標題或 handle>`。腳本 540 秒內必定結束：逾時印 `STOP timeout`，收到 SIGTERM、SIGINT 印 `STOP signal <名稱>`，都會先還原）。它確認 `coordinator` 的 pid 是自己後改寫成 handoff 行，新開分頁 `issue-pilot coordinator` 送出 `/loop /issue-pilot`（或送給 `--to` 的 session），等新 session 寫入 `pid ` 行。最後一行 `HANDED_OFF <handle>` 才算交接完成，腳本這時已在 `sessions.md` 附加 handoff 行，coordinator 不再手動附加；`STOP <原因>` 時 `coordinator` 已還原、這次新開的分頁已關掉、`sessions.md` 沒動，照常繼續當 coordinator（`STOP not-coordinator` 表示已經有別的 coordinator，不要再交接；`STOP to-not-found`、`to-ambiguous`、`to-self` 是 `--to` 沒對到唯一一個別的 session，改用 handle 或不帶 `--to` 重跑）。

- **Project tick hooks.** 預設：沒有。

- **Retro collect.** `/retro-collect` 在主 checkout 跑，把開著的 `retro-candidates` Issue 做成一個 retro 單位；`<key>` 是 `<MMDD><字母>`，和計畫檔 `.scratch/retro/plan-<key>.md` 同名。認領：在主 checkout 對每張跑 `node scripts/issue-pool.mjs claim <n>`，印 `CLAIMED <n>` 才收，`STOP <n> claimed …` 表示別的 session 在收、這次略過。目標分支是 `main`。worktree：設了 `ORCA_CLI_COMMAND` 時 `node scripts/orca-worktree-create.mjs --name retro-<key> --base-branch main --branch retro/<key>`（看最後一行 JSON 的 `path`），沒有 Orca 時 `git worktree add -b retro/<key> <路徑> main`。檢查：開發中 `bin/check`，合入前在 tip、工作樹乾淨時跑 `bin/check --upstream`。合入與 push 照 [Evidence and closing](issue-run.md#evidence-and-closing) 單獨跑的方式：PR body 每張收集的 Issue 一行 `Closes #<n>`，用 Bash `timeout: 600000` 跑 `node scripts/land.mjs retro/<key> --title 'chore: retro <key>' --body-file <檔>`，結果行的處理也照那一段。
