# Pilot：ron-skills

給使用者層級的 `/issue-pilot` coordinator 用的專案設定（`/loop /issue-pilot`）。[issue-run.md](issue-run.md) 各段在 pilot 底下照樣適用，這裡只寫 pilot 不同的地方。本 repo 的 pilot 腳本有 Bare guard 的 `scripts/pilot-unbare.sh`、Probe 的 `scripts/pilot-probe.mjs`、Dispatch 的 `scripts/pilot-dispatch.mjs` 和 Handoff 的 `scripts/pilot-handoff.mjs`（後兩者要 `ORCA_CLI_COMMAND`，Probe 讀 worker 時也要），以及 Close 的 `scripts/pilot-counterpart.mjs`；watch、status 都由 coordinator 依下列指令手動做，沒列出的指令就是沒有。`.scratch/pilot/` 每個檔案（含 batch checkpoint）的路徑、格式與合法值都照 [PILOT-STORE.md](../../skills/engineering/issue-pilot/PILOT-STORE.md)，這裡只寫本 repo 的值。

- **Coordinator checkout.** 主 checkout `/home/ron/code/ron-skills`，`.scratch/pilot/` 放在這裡，不 commit。

- **Bare guard.** Orca 從 WSL 做 worktree 操作（create、rm 都會）時，可能把主 checkout `.git/config` 的 `core.bare` 改成 `true`，之後 `git status` 回 `must be run in a work tree`，stage、merge 全部失敗。在主 checkout 跑 `scripts/pilot-unbare.sh /home/ron/code/ron-skills <時機>`（時機如 `probe`、`dispatch #<n>`、`stage #<key>`、`close #<n>`）：是 bare 就執行 `git config core.bare false`、在 `.scratch/pilot/decisions.md` 的表格追加一列，並印出 `UNBARE <checkout>`；不是 bare 時不輸出。下列 Probe、Dispatch、Stage、Close 都只呼叫它。主 checkout 的工作樹還沒有這支腳本時（本機 `main` 落後 `origin/main`），改跑 `git -C /home/ron/code/ron-skills rev-parse --is-bare-repository`，印出 `true` 就執行 `git -C /home/ron/code/ron-skills config core.bare false` 並手動記一列。

- **Sessions.** 預設：coordinator 自己在 `.scratch/pilot/sessions.md` 追加 start 行。

- **Defaults for `preferences.md`.** 不限同時跑的 worker 數；每批最多 2 個 Issue；worker 指令見 Dispatch；只有 coordinator 合進 batch 與整合分支；push、開 PR、合進 `main` 都由 coordinator 照 Push gate 做，不交給人（worker 不 push、不開 PR）；每個 session 合入 2 批或遇到 compaction 就 handoff。

- **Integration branch.** 本機 `pilot/integration`，第一次用時從 `main` 開（`git branch pilot/integration main`）。push、開 PR、合進 `main` 和之後跟上 `origin/main` 都見 Push gate。要手動讓它跟上 `origin/main` 時在 stage worktree 做：`git -C /home/ron/orca/workspaces/ron-skills/pilot-stage switch pilot/integration && git -C /home/ron/orca/workspaces/ron-skills/pilot-stage merge --ff-only origin/main`（stage worktree 還沒建時，主 checkout 不在 `pilot/integration` 上，用 `git -C /home/ron/code/ron-skills fetch . origin/main:pilot/integration`，非快轉時會拒絕）。

- **Stage worktree.** `/home/ron/orca/workspaces/ron-skills/pilot-stage`，Stage、Regression、Integrate 全在這裡做，`pilot/integration` 也只在這裡前進。主 checkout 一直停在 `main`，coordinator 在主 checkout 只做 fetch、讀狀態、快轉 `main`（`git -C /home/ron/code/ron-skills merge --ff-only origin/main`）：在主 checkout 切到還沒合入的分支，工作樹會帶出那個分支的 `.claude/settings.json`，在主 checkout 跑的 session 會即時載入它的 hook（#21）。

- **Pool.** `gh issue list --state open --label ready-for-agent --json number,title,labels`，再用 `gh api repos/ron03wlb/ron-skills/issues/<n> --jq '[.issue_dependencies_summary.blocked_by, .sub_issues_summary.total]'` 濾掉 `blocked_by > 0` 或 `sub_issues_summary.total > 0` 的 Issue，以及已經在某個開著的 batch checkpoint 裡的 Issue；號碼小的先挑。有 sub-issue 的是母單：母單只分組、不派工也不驗收，pilot 一律挑它的子單（`/to-spec` 會給母單掛 `ready-for-agent`，不排除就會跟子單重複派工）。人手動跑 `/issue-run <母單>` 時仍照上游展開子單。`needs-triage` 的先照 [Readiness](issue-run.md#readiness) 用 `/triage <n>` 補齊，補完變成 `ready-for-agent` 才挑。

- **Batch.** 批次 checkpoint 是 `.scratch/pilot/batch-<key>.md`，由 Dispatch 建立。各 Issue 自己的 checkpoint 仍在 `.scratch/issue-run-<n>/state.md`（在它的 worktree 裡）。

- **Brief check.** 沒有指令。worker 的 brief 就是 `/issue-run <n> --worker <checkpoint>` 加上 Issue 本文；tooling fix unit 的 brief 由 coordinator 寫在 `.scratch/pilot/briefs/`，派出去前自己核對契約列的每一節都在。

- **Dispatch.** 在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <key> <n>:<slug>...`（成員依號碼順序，如 `node scripts/pilot-dispatch.mjs 23-46 23:pilot-probe 46:pilot-dispatch`；腳本 540 秒內必定結束）。每個成員依序做：`scripts/orca-worktree-create.mjs`（setup-workflow 正本的副本）建 worktree `issue-<n>`、分支 `issue/<n>-<slug>`、base `pilot/integration`，接著 Bare guard（時機 `dispatch #<n>`），以目錄存在、`git worktree list` 裡有這個分支判斷 worktree 建好（不信 create 回傳的 `ok`），再 `orca-ide terminal create --title '#<n>' --command claude`，最後用 orca-session-send 送出 `/issue-run <n> --worker /home/ron/code/ron-skills/.scratch/pilot/batch-<key>.md`。所有子行程的 stdin 都接 `/dev/null`。它會寫 batch checkpoint 的表頭（已存在就不動）和每個成員一行（重跑時同一個 Issue 的那行就地換掉），每個成員印一行 `DISPATCHED <n> <handle>`，或 `STOP <n> <原因>`（成員行的 state 記成 `stop`，原因只在這一行，要留就記進 `decisions.md`）；Bare guard 還原時另印 `UNBARE <主 checkout>`。exit 0 全部派出、4 有成員 STOP。STOP 的成員修好原因後用同一個 key 只帶它重跑（worktree 已在就不再 create）；`create` 開頭的 STOP 先到 Orca 查 worktree 是不是還在背景建立，不要直接重跑。不要自己手寫 `orca-ide worktree create`、`terminal create` 或裸 `terminal send` 的迴圈：Orca CLI 會吃掉 stdin，`while read` 只派到第一個成員；裸 `terminal send` 會回 accepted，文字卻停在輸入框沒提交。

- **Watch.** `orca-ide terminal read --terminal <handle> --screen --json`：畫面最後一行是 `DONE <n> <sha>` 或 `STOP <n> <cause>` 就是做完了；`status: exited` 但沒有這行就是卡住。stuck-after 預設 90 分鐘，等累積了實際跑的時間再調。沒有背景 watcher 指令：worker 還在跑時，coordinator 每次被叫醒都 read 一次，以 1200 秒排下一次喚醒。

- **Agent rows.** 記在 batch checkpoint 的成員行（見 Batch）；worker 自己開的 subagent 不另外記。

- **Probe.** Reconcile 時在主 checkout 跑 `node scripts/pilot-probe.mjs /home/ron/code/ron-skills`（讀 running 成員要 `ORCA_CLI_COMMAND`，沒有時其他檢查照跑），整份輸出照行處理，不再手動拼 Bare guard、`git status`、Watch 與 fetch。它會先跑 Bare guard（時機 `probe`，還原時印 `UNBARE`），沒事的項目不印；各行與處理：`DIRTY <status>`（主 checkout 有改動）先回報人，不 merge；`NOT_MAIN <分支>` 回報人，不 stage、不 merge，也不替人切回；`HOLD` 不做 Integrate；`ADAPTER_AHEAD <檔案>` 是 `pilot/integration` 上的 adapter 比 `main` 新（整合分支有這個檔、內容不同，而且 `main` 最後一次改它的 commit 已在整合分支裡；兩邊都改過時不印；下一批在整合分支上 stage，#52），這一輪改讀 `git -C /home/ron/code/ron-skills show pilot/integration:<檔案>` 的版本；`REQUEST`、`GATE` 是 `requests.md`、`gates.md` 還開著的列，只打開對應那幾列處理；`GATE_MALFORMED <id> <行>` 是把 resolved 寫進別的欄位（如 `- status：resolved …`）的 gate，probe 仍當它開著，把那一行改成 `- resolved <time> <how>`；`WORKER <n> DONE <sha>`、`WORKER <n> STOP <cause>` 記進 batch checkpoint 的 state 與 candidate，`WORKER <n> STUCK …`（terminal 已結束卻沒有結果行、超過 stuck-after、讀不到 terminal、沒有 `ORCA_CLI_COMMAND`、checkpoint 的 started 或 stuck-after 寫壞）回報人，`WORKER <n> RUNNING <分鐘>` 不動；`STAGEABLE <key>` 做 Stage；`current:` 是 `merged <sha>` 或 `pushed <sha>` 的 batch 印 `IN_MAIN <key>`、`RESUME_PUSH <key>` 或 `NOT_IN_MAIN <key>`（腳本已 `git fetch origin`）：`gates.md` 裡這個 batch 還有開著的列就跳過，等 gate 解除；`IN_MAIN` 做 Close；`RESUME_PUSH` 是 Integrate 之後、Push gate 做完之前中斷的 `merged` batch（`pilot/integration` 的 tip 等於最後一次 Regression SHA，#37），從 Push gate 第 1 步接著做，PR 已經開著時第 1 步會先更新 body、`land.mjs` 沿用它從等 CI、合併那步接著做；`NOT_IN_MAIN <key>` 是還沒進 `origin/main` 的 `pushed` batch（照 Push gate 第 3 步，`LANDED` 之後才設 `pushed <sha>`，所以只有舊格式或 `LANDED` 之後被 revert 才會出現），重跑 Push gate（`land.mjs` 每一步都能從中斷處接著做）；`NOT_IN_MAIN <key> no-sha`、`NOT_IN_MAIN <key> no-regression`（`merged` 卻沒有 `regression:` 行，或它的 SHA 解析不到）、`NOT_IN_MAIN <key> tip <sha 或 none>`（`merged` 但 `pilot/integration` 的 tip 不是 Regression SHA，直接推會送出沒驗過的內容）與 `FETCH_FAILED` 回報人。腳本 exit 非 0 時先照 Bare guard 單獨跑 `scripts/pilot-unbare.sh`（時機 `probe`），把 stderr 回報人，這一輪不 stage、不 merge。最後整理母單：用 [issue-tracker.md](issue-tracker.md#母單) 的關係總覽（只列開著的 issue），`subIssuesSummary.total > 0` 的是開著的母單，補上 `parent` label、移除所有 triage label（`gh issue edit <n> --add-label parent --remove-label <label>`）；開著的 issue 的 `parent.number` 不在總覽裡，就是有開著子單（新掛上或子單被重開）卻已關閉的母單，用 `gh issue reopen <n>` 重開。

- **Hold flag.** Integrate 前一步檢查 `.scratch/pilot/hold`，存在就不 merge；Probe 這時印 `HOLD`。

- **Stage.** 在 stage worktree `/home/ron/orca/workspaces/ron-skills/pilot-stage` 從 `pilot/integration` 開 `pilot/stage-<key>`。它還不存在時在主 checkout 建：`orca-ide worktree create --name pilot-stage --base-branch pilot/integration --branch pilot/stage-<key> --json`（不要帶 `--repo`：Orca 會從 cwd 推斷 repo，帶 `--repo path:<WSL 路徑>` 會回 `repo_not_found`；也不要帶 `--agent`：一起帶時錯誤會被包成 `agent_session_operation_unknown`），之後跑 Bare guard（時機 `stage #<key>`）；已存在時先確認 `git -C /home/ron/orca/workspaces/ron-skills/pilot-stage status --short` 是空的（不是就回報人），再 `git -C /home/ron/orca/workspaces/ron-skills/pilot-stage switch -C pilot/stage-<key> pilot/integration`（`-C` 會把同 key 的舊分支重設到 `pilot/integration`，重新 stage 或上一次 Regression 沒過時都從頭來）。然後依號碼順序 `git -C /home/ron/orca/workspaces/ron-skills/pilot-stage merge --no-ff issue/<n>-<slug>` 合進每個 `done` 成員。成員有 `stop` 時，先把它移到自己的 batch：開 `.scratch/pilot/batch-<n>.md`（表頭照抄、成員行照抄），舊 checkpoint 那一行的 state 改成 `moved batch-<n>`，再 stage 剩下的 `done` 成員；不移的話，Close 會對這張還沒合入的 Issue 留證據、關單、移除 worktree（retro a6）。只有兩邊都只是新增、不重疊的段落時，coordinator 才可以自己解衝突；每個衝突 hunk 裡兩邊改的是不同的 `- **<名稱>.**` 條目時，也可以各取各的版本（兩邊改過的條目都留下），解完一定要在新的 staged SHA 重跑 Regression（#45）。其他衝突先 `git -C /home/ron/orca/workspaces/ron-skills/pilot-stage merge --abort`，再變成 gate。

- **Regression.** 在 stage worktree 的 staged SHA、工作樹乾淨時跑 `/home/ron/orca/workspaces/ron-skills/pilot-stage/bin/check --upstream`，exit 0 才算過；只對那個 SHA 有效。結果記成 `regression: <sha> exit <code>`，後面附 `bin/check` 最後一行 `CHECK_PASS tests <a>+<b>`（兩組測試的數目；只看尾段的 `ℹ tests` 會只拿到第二組）。

- **Integrate.** 沒有 hold flag、而且 `pilot/integration` 從 stage 之後沒有新 commit（`git -C /home/ron/orca/workspaces/ron-skills/pilot-stage merge-base --is-ancestor pilot/integration pilot/stage-<key>` exit 0；用這個判斷，不要拿事先記下的 SHA 比：Push gate 的 `land.mjs` 會把 `pilot/integration` 推進到 PR 的 merge commit），才在 stage worktree 做 `git -C /home/ron/orca/workspaces/ron-skills/pilot-stage switch pilot/integration && git -C /home/ron/orca/workspaces/ron-skills/pilot-stage merge --ff-only pilot/stage-<key>`；有新 commit 就重新 stage、重跑 Regression。合完 `git -C /home/ron/orca/workspaces/ron-skills/pilot-stage branch -d pilot/stage-<key>`，`current:` 設成 `merged <sha>`。stage worktree 停在 `pilot/integration` 等下一批，不移除。

- **Push gate.** `pilot/integration` 的 tip 等於最後一次 Regression 通過的 SHA。通過後 coordinator 在主 checkout 依序執行：
  1. 把 PR body 寫進 `.scratch/pilot/pr-body.md`：列出這個 PR 裡的全部 batch、各自的 staged SHA、Regression 結果（exit code）和每個成員的 `Closes #<n>`。`gh pr list --head pilot/integration --state open --json url --jq '.[].url'` 輸出非空時，PR 已經開著，`land.mjs` 會沿用它但不改 body，先跑 `gh pr edit pilot/integration --body-file .scratch/pilot/pr-body.md`。
  2. 用 Bash `timeout: 600000` 跑 `node scripts/land.mjs pilot/integration --keep-branch --title '<batch key 與標題>' --body-file .scratch/pilot/pr-body.md`。它依序 push、找或開 PR、等 CI、`gh pr merge --merge`（不刪分支），再在 stage worktree 把 `pilot/integration` 以 `--ff-only` 跟上 `origin/main` 後 push，並讓主 checkout 的 `main` 跟上；不用 `git branch -f`，它會把 upstream 改成 `origin/main`。
  3. 最後一行是 `LANDED <pr> <merge sha>` 就把 `current:` 設成 `pushed <sha>`，接著做 Close；`STOP checks-timeout` 下一輪重跑；`STOP behind-main`（`pilot/integration` 沒包含 origin/main，push 事件的 CI 會跑舊 workflow）照 Stage 開 `pilot/stage-sync-main`、`merge --no-ff origin/main`、跑 Regression、照 Integrate 合入後重跑本步；其他 `STOP <原因>` 變成 gate。`WARN main-not-synced` 不擋，Close 開頭會再檢查。

- **Counterpart.** 下面 Close 處理每個成員時，在證據留言之後跑 `gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs`（[對應單](../../GLOSSARY.md)；沒有輸出就略過）。每印一行 `COUNTERPART <owner>/<repo>#<m>`，就把交接寫進 `.scratch/pilot/counterpart-<n>.md`：成員 `ron03wlb/ron-skills#<n>`、ron-skills 的 merge SHA 與 PR 網址、這個成員改了什麼、對方要做的下一步，再跑 `gh issue comment <m> --repo <owner>/<repo> --body-file .scratch/pilot/counterpart-<n>.md`；同一張對應單可能有好幾個成員（例如 #28、#29、#30 都指向同一張），所以留言要寫出成員 `ron03wlb/ron-skills#<n>`，略過條件也要兩個都比：`gh issue view <m> --repo <owner>/<repo> --json comments --jq '[.comments[].body | select(contains("<merge sha>") and test("ron03wlb/ron-skills#<n>\\b"))] | length'` 不是 0 時略過，留言失敗就變成 gate。給人的回報列出每張對應單和留言網址（#53）。

- **Close.** Push gate 印出 `LANDED`、batch 的 merge 進到 `origin/main` 之後馬上做，不等人。先確認主 checkout 的 `main` 已經跟上：`git -C /home/ron/code/ron-skills merge-base --is-ancestor origin/main main` exit 0，不是就跑 `git -C /home/ron/code/ron-skills merge --ff-only origin/main`。再對每個 `done` 成員照 [Evidence and closing](issue-run.md#evidence-and-closing) 依序處理，已經做過的步驟略過，所以中斷後可以重跑：證據留言（附 PR 網址與 merge SHA；`gh issue view <n> --json comments --jq '.comments[].body' | grep -c <merge sha>` 不是 0 時略過）；照 Counterpart 到對應單交接；`gh issue close <n>`（PR 的 `Closes #<n>` 已經關掉時 `gh issue view <n> --json state` 是 `CLOSED`，略過）；`orca-ide terminal close --terminal <handle>` 關掉成員的 terminal（handle 在 batch checkpoint；`orca-ide terminal list --worktree branch:issue/<n>-<slug> --json` 裡沒有它時略過）；`orca-ide worktree rm --worktree branch:issue/<n>-<slug>` 移除 worktree（`git -C /home/ron/code/ron-skills worktree list` 裡已經沒有時略過；rm 之後跑 Bare guard，時機 `close #<n>`）；`git -C /home/ron/code/ron-skills branch -d issue/<n>-<slug>` 刪本機分支（`git -C /home/ron/code/ron-skills rev-parse --verify -q refs/heads/issue/<n>-<slug>` 沒有輸出時略過）；`git -C /home/ron/code/ron-skills ls-remote --exit-code --heads origin issue/<n>-<slug>` exit 0 才跑 `git -C /home/ron/code/ron-skills push origin --delete issue/<n>-<slug>`，exit 2（遠端沒有，worker 不 push）略過，其他 exit code 變成 gate。成員關掉後，若它有母單（`gh api repos/ron03wlb/ron-skills/issues/<n>/parent --jq .number`，沒有母單時回 404）而母單的 `sub_issues_summary.completed == total`，就關閉母單，留言列出每張子單和它的 `state_reason`（`gh api repos/ron03wlb/ron-skills/issues/<母單>/sub_issues --jq '.[] | "#\(.number) \(.state_reason)"'`）；`completed` 與 `not_planned` 都算結束。全部成員處理完，`current:` 設成 `closed`。

- **Handoff.** 條件達到時（見 Defaults），coordinator 先在 `decisions.md` 記一筆原因、停掉自己的背景工作，再在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-handoff.mjs --session "$CLAUDE_CODE_SESSION_ID" --pid "$CLAUDE_PID" --reason <原因>`（腳本 540 秒內必定結束：逾時印 `STOP timeout`，收到 SIGTERM、SIGINT 印 `STOP signal <名稱>`，都會先還原）。它確認 `coordinator` 的 pid 是自己後改寫成 handoff 行，新開分頁 `issue-pilot coordinator` 送出 `/loop /issue-pilot`，等新 session 寫入 `pid ` 行。最後一行 `HANDED_OFF <handle>` 才算交接完成，這時才在 `sessions.md` 追加 handoff 行（`sessions.md` 有本 session 的 handoff 就代表已退役，提早記會讓 STOP 後的自己誤判退役）；`STOP <原因>` 時 `coordinator` 已還原、新開的分頁已關掉，照常繼續當 coordinator（`STOP not-coordinator` 表示已經有別的 coordinator，不要再交接）。

- **Project tick hooks.** 預設：沒有。

- **Retro collect.** 預設：沒有；`/retro-collect` 停下並說明原因。
