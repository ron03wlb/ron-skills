# issue-run 檢查與 review 細則

[issue-run.md](issue-run.md) 的 `## Checks` 指到這裡，`## Review` 指到判斷題。各條目用 `node scripts/adapter-line.mjs '<條目名>'` 單獨取。

- **Template copies.** 改正本後先 `cp` 副本、第一次 `bin/check` 才在 `tests/template-copies.test.mjs` 報 sha256 不符，各多跑一輪（#201，兩次 retro）。正本旁的範本測試與 `tests/<名稱>.test.mjs` 是兩份：後者跑的是 `scripts/` 副本，只跑正本旁那份會漏（#454：`tests/pilot-land.test.mjs` 的 sync-main 測試只在完整 `bin/check` 才紅）。改範本時兩份都跑；copy-templates 對有後者的副本多印 `ALSO_TESTED tests/<名稱>.test.mjs`。新範本要在 copy-templates 指令加 `--register`（只在 ron-skills 本身有效）：沒帶時它印 `SKIP_UNLISTED <檔>`、`COPIED 0` 且 exit 0，不登記也不複製，不要再手寫清單佔位項目（#420：七個 worker 各自用 python 或 `node -e` 手加）。copy-templates 也同步 `tests/helpers/` 底下 fake-orca、real-tmpdir 與 Orca 樣本的鏡像，不手動 `cp`（#429）；`--staged` 只把 COPY、UPDATE 的清單項目記成 HEAD，SAME 的項目不動（#436）。 copy-templates 明列範本時，setup-workflow SKILL.md Templates 表那列漏了相依會在 stderr 印 `SKILL_BRINGS_MISSING <範本> <相依>`（不改 exit code）：commit 前把相依補進該列括號，不等 pre-commit 的 `tests/skill-brings.test.mjs`（#631：等 slot 805 秒才報）。
- **Pre-commit output.** pre-commit 跑 `bin/check --changed`（只跑和變更路徑有關的子集，不能當 acceptance 的證據），成功時在 stderr 印：`CHECK_SUBSET steps …｜full <原因>` 與最後一行 `CHECK_PASS_SUBSET tests …`（退回完整套件時是 `CHECK_PASS tests …`），這棵樹剛通過完整 `bin/check` 而跳過時印 `CHECK_STAMP_FRESH <tree>`，要 commit 的樹和 HEAD 的樹相同（只改訊息的 `--amend`、`--allow-empty`）時不跑檢查、印 `CHECK_TREE_UNCHANGED <tree>`（#621：只改訊息的 amend 排 heavy-slot 等滿 SLOT_TIMEOUT 而失敗；那棵樹先前 commit 時已通過）；`git commit … > <log> 2>&1` 的 log 裡就有，不必另讀 hook 或 `check-pass` 檔。證據直接引這一行；`CHECK_STAMP_FRESH` 時附先前單獨跑那次的 `CHECK_PASS` 行（#512：四個 worker 各多花兩三次呼叫確認 `bin/check` 有沒有跑）。子集測試檔數 ≤ `CHECK_SLOT_FREE_TESTS`（預設 10）時不經 heavy slot，多印 `CHECK_SLOT_SKIP tests <n>`；經 slot 而 `SLOT_TIMEOUT`（hook 附上 `heavy-slot.mjs status`）時不要直接重跑 commit，先在要 commit 的樹上跑完整 `bin/check`，通過後再 commit 就是 `CHECK_STAMP_FRESH`（#605：重跑 commit 又等滿 30 分鐘）。
- **Result line format.** 改範本腳本結果行的格式（檔頭 stdout 段列的行）之前，先 `grep -rn '<結果行前綴>' skills docs tests scripts` 列出每一處測試斷言與文件，再動手；結果行由另一支腳本轉印時（例如 `pilot-probe.mjs` 的 `workerState` 經 `pilot-land.mjs` 印出），那支的檔頭與 `PILOT-STORE.md` 那一列也在清單裡（#504：`STOP capacity` 改格式漏了兩處斷言、五行文件，多一輪修正與 `bin/check`）。`tests/pilot-store-usage.test.mjs`（`docs-rules`）比對 `PILOT-STORE.md` Canonical scripts 表的用法欄與範本 `USAGE`、結果行欄與範本檔頭 stdout 段（#456）；`pilot-probe`、`pilot-watch`、`pilot-idle-wait`、`pilot-dispatch` 的結果行沒有反引號、不在結果行檢查範圍，改它們的結果行時 Spec reviewer 自己對照那一列。diff 新增 CLI 旗標或結果行時，Spec reviewer 跑 `grep -rn '<腳本名>' skills docs` 列出每個呼叫端逐一確認（#456：`issue-run/SKILL.md` 的 `--pool` 沒帶新旗標）。
- **Import check.** 改了範本的 import 或 export 之後，先對每支 import 它的範本跑 `node --check <檔>`（毫秒級，ESM 頂層撞名當場報 `SyntaxError: Identifier '<名>' has already been declared`），再跑單檔測試（#504：`pilot-dispatch.mjs` 自己的 `stopLine` 和新 import 的同名，等幾分鐘的測試才報）。
- **Edit scripts.** 多行的編輯腳本（Python、node）先用 Write 寫進 scratchpad 再執行，不寫成 heredoc：內文含 JS、`$`、反引號時，Claude Code 的內建安全檢查會擋下整條指令，多一輪改寫（#525）。Issue 留言內文同理（[issue-run.md](issue-run.md) Evidence 段，#444）。
- **Case-sensitive names.** review 判斷題：以名稱判斷檔案在不在、而名稱的大小寫有意義時（連結目標、條目名），對 `readdirSync` 的檔名清單比對，不用 `existsSync`／`statSync`：macOS 的 APFS 不分大小寫，`[[Open]]` 會找到 `open.md`，本機 Linux 的 regression 全綠，到 CI 的 `checks-macos` 才紅（#478：`memory-audit.mjs`，多花約 70 分鐘）。

- **Size budgets.** 改了 `docs/agents/pilot*.md`、`docs/agents/issue-run*.md` 或 `skills/engineering/issue-run/PILOT-*TEMPLATE.md` 後，先跑 `node scripts/check-adapter-size.mjs` 與 `node --test tests/pilot-split.test.mjs tests/setup-workflow-stations.test.mjs`（秒級，都在 `bin/check` 的 docs-rules 步驟，超出時印 `<size>/<cap> bytes，超 <n>`，照數字一次刪夠），再起整條 `bin/check`（#420、#567：PILOT-TEMPLATE 預算原本要等整條 tests 才報，五個 worker 各多跑一輪）。

- **Entry survival.** fresh 重派的成員（checkpoint 有 `-prior` 分支或 note 的 `prior:` 行）整併完，在工作樹跑 `node scripts/entry-survival.mjs <整合分支那一邊的 commit>`（通常是 `$(git merge-base HEAD pilot/integration)`；秒級，只讀 git 與 `scripts/adapter-size-budget.json` 列的檔加 `skills/engineering/issue-run/*-TEMPLATE.md`）：base 的每一行 `- **<條目>.**` 只去掉行尾空白比對原文，在這些檔的聯集裡都找不到時印 `ENTRY_LOST <檔> <條目>`（名稱也不在）或 `ENTRY_CHANGED <檔> <條目>`（名稱在、文字不同），都沒有時印 `ENTRY_SURVIVAL_OK <條目數>`，exit 1／0；條目搬到聯集裡的別份檔不報。它不分辨正常改寫與被蓋掉：worker 把每行抄進 checkpoint 逐條註明，review-only verifier 的 prompt 要 verifier 自己在 candidate 跑同一條指令（不只讀 worker 抄的輸出：漏抄或補回前跑的看不出來），對照 checkpoint 的註明，對每行比對 prior 的 diff（`git diff <base> <prior sha> -- <檔>`）判斷，prior 沒改過的條目出現在輸出裡就是被蓋掉，算阻擋（#558：#344 整檔 `git checkout --theirs` 蓋掉 #346 的 **Brief check.**、#326 的 **Pool.**，只有逐條比對的 verifier 抓到）。
