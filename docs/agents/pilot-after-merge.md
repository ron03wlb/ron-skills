# Pilot：合入之後

[pilot.md](pilot.md) 的 pointer 指到這裡時才讀：Stage 印 `MERGED`、Probe 印 `IN_MAIN`、`RESUME_PUSH` 或 `NOT_IN_MAIN`，或 Handoff 的條件達到。下文的 `<主 checkout>`、`<stage worktree>`、Bare guard、Decisions、Gates 與 pilot.md、[pilot-exceptions.md](pilot-exceptions.md) 的同名條目相同。

- **Push gate.** `pilot/integration` 的 tip 等於最後一次 Regression 通過的 SHA。通過後 coordinator 在主 checkout 跑第 1 步的一行入口。`pilot-land.mjs push`、`pilot-land.mjs sync-main` 與 `pilot-pr-body.mjs` 從主 checkout 的入口跑，它們自己轉到 stage worktree 的同名腳本（`push` 也用那裡的 `pilot-pr-body.mjs` 與 `land.mjs`），不必算路徑（#275：每任 coordinator 都手寫 porcelain 加 awk，只比 `pilot/integration` 時停在 `pilot/stage-*` 會撈空）：stage worktree 停在 `pilot/integration`，就是要推的內容，推的 batch 改了這幾支腳本時，`main` 上的舊版會誤判（#239：batch 193 讓 `pilot-pr-body.mjs` 接受 `sync-main` 寫的 regression 行，`main` 上的舊版印 `STOP regression 193`）；不看 Probe 有沒有印 `ADAPTER_AHEAD`。
  1. 用 Bash `run_in_background` 跑、等完成通知 `node scripts/pilot-land.mjs push --title '<batch key 與標題>' --check-command 'bin/check --upstream' --resolver scripts/pilot-resolve.mjs`（setup-workflow 正本的副本；sync-main 的 Regression 加上等 CI 會超過 Bash 的 600 秒），不要再手打 `pilot-pr-body.mjs`、`gh pr edit`、`land.mjs`、`sync-main` 幾步（#395：batch 342 stage 之後 `origin/main` 才前進，多了兩次背景等待與三次喚醒）。它依序：先跑 `pilot-pr-body.mjs <主 checkout> --out .scratch/pilot/pr-body.md`，印 `PR_BODY …` 才往下：它從 `current: merged` 的 batch checkpoint 列出這個 PR 裡的全部 batch、各自的 staged SHA、最後的 `regression:` 行和每個 Issue 成員的 `Closes #<n>`（請求分支成員沒有 Issue，列分支名稱），結尾帶署名；不要再跑迴圈抽 checkpoint、heredoc 手寫或用 sed 插列（#145）。`STOP no-merged-batch` 表示沒有待推的 batch，`STOP regression <key>` 表示那個 batch 最後的 Regression 不是它的 staged SHA 通過（結尾的 `sync-main` 行略過不算，見第 3 步），這時它就是最後一行、不 land，變成 gate。接著跑第 2 步的 `land.mjs`（多帶 `--check-command`），PR 已經開著時它以 `gh pr edit` 換上新的標題與 body（印 `PR_UPDATED <pr>`）。`land.mjs` 印 `STOP behind-main`（stage 之後 `origin/main` 才前進）時不印那行，改印 `PUSH_BEHIND_MAIN pilot/integration`，照第 3 步的 `sync-main` 同步（印 `RECORDED`、`SYNCED`），通過後重產 body、再 land 一次；同步的 STOP 就是最後一行，不 land。其餘情況最後一行與 exit 是 `land.mjs` 的；都照第 3 步處理。
  2. `push` 內部跑的是 `node scripts/land.mjs pilot/integration --keep-branch --title '<batch key 與標題>' --body-file .scratch/pilot/pr-body.md`。它依序 push、找或開 PR、等 CI、`gh pr merge --merge`（不刪分支），再在 stage worktree 把 `pilot/integration` 以 `--ff-only` 跟上 `origin/main` 後 push，並讓主 checkout 的 `main` 跟上；不用 `git branch -f`，它會把 upstream 改成 `origin/main`。
  3. 最後一行是 `LANDED <pr> <merge sha>` 時先在主 checkout 重跑 Sessions 指令，對印出的 `SOURCE_CHANGED`、`SOURCE_MISSING` 照 Sources 重讀，再接著做 Close，不手改 `current:`：剛合入的 batch 可能改了 Close、Handoff 的指令，Reconcile 開頭讀到的是合入前的版本（#260：batch 245 讓 `pilot-close.mjs` 必須帶 `--repo`，同一輪照舊條目跑，印用法、exit 1）；Close 做完會寫成 `closed`；Close 之前中斷時，下一輪 Probe 印 `IN_MAIN` 並由 `--apply` 把 `merged` 寫成 `pushed`；`STOP checks-timeout <pr>`（等 CI 超過 Bash 的 600 秒上限，剛開出 PR 時常見）當輪立刻在背景重跑第 1 步同一條指令一次，它重產 body、沿用同一個 PR 接著等；第二次還是 `STOP checks-timeout` 才留給下一輪重跑（#221：batch 192 第一次就逾時，當輪重跑得到 `CHECKS_PASSED` 後合入，等下一輪會讓 Handoff 多擋約 20 分鐘）；`land.mjs` 的 `STOP behind-main`（`pilot/integration` 沒包含 origin/main，push 事件的 CI 會跑舊 workflow）由第 1 步自己接著跑 sync-main；同步之後 `origin/main` 又前進、最後一行仍是 `STOP behind-main` 時，下一輪重跑第 1 步。要單獨同步時在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-land.mjs sync-main --check-command 'bin/check --upstream' --resolver scripts/pilot-resolve.mjs`，不再手打 `switch -C`、`merge`、解衝突、`bin/check`、`merge --ff-only`、`branch -d`（#193）：它 fetch 後在 stage worktree 讓 `pilot/integration` 包含 `origin/main`（只是落後時快轉，印 `SYNCED <sha> ff`；已包含印 `SYNCED <tip> current`；分叉時先過 Stage 的 load 關卡，再在 `pilot/stage-sync-main` 合入 `origin/main`，衝突照 Stage conflict 的解法解，再跑 Regression），通過就先對每個 `current: merged`、merge SHA 在這次合併裡、還沒推上 `origin/pilot/integration` 也不在 `origin/main` 的 batch 追加 `regression: <sha> exit 0 sync-main <CHECK_PASS 行>`、再快轉 `pilot/integration`（印 `RECORDED <key>`，下一輪 Probe 照常印 `RESUME_PUSH`；已推的 batch 保留舊 regression 行、不印 `RECORDED`，Probe 照舊印 `NOT_IN_MAIN <key> tip …`，#523；`pilot-pr-body.mjs` 略過這行驗 staged SHA，再把它接在該 batch 那一列後面），最後一行印 `SYNCED <sha> <CHECK_PASS 行>`（單獨跑的話再從第 1 步重跑）；`STOP conflict sync-main <檔>=main:<種類> …`（已 abort，stage worktree 乾淨；每個衝突檔一項，種類同 Stage conflict，修的批次照 **Integration branch.** 找，#589）與 `STOP regression sync-main <exit>`（完整輸出在 `.scratch/pilot/reg-sync-main.log`）、`STOP checkpoint …`、`STOP load <load> <門檻>` 都不動 `pilot/integration`，前兩者變成 gate，`STOP checkpoint` 照 Integrate 的同名 STOP 處理，`STOP load` 照 Stage 的同名 STOP 下一輪重跑（#178），`STOP drift`（合併期間整合分支前進了）同樣下一輪重跑；`STOP ci-failed <pr> <job 網址>`（CI 有跑起來而失敗）先用 `gh run view <run> --log-failed` 讀失敗的 job，失敗的測試檔（`✖`、`not ok`、`NODE_TEST_RERUN <檔> FAIL` 指到的檔）都不在 `gh pr diff <pr> --name-only` 裡時當成偶發：`gh run rerun <run> --failed` 一次，再在背景重跑第 1 步同一條指令，並把 run 網址與判斷記進 `decisions.md`（#258：PR 255、259 各一次，`NODE_TEST_LOST` 後的 `NODE_TEST_RERUN … FAIL` 與 macOS 上語言 hook 的計時測試 `✖`，都是 PR 沒改的檔，重跑後通過）；失敗的檔在 diff 裡、log 看不出是哪個檔，或重跑後又 `STOP ci-failed`，才變成 gate；其他 `STOP <原因>` 變成 gate。`WARN main-not-synced` 不擋，Close 開頭會再檢查。
  4. `STOP ci-not-started <pr> <原因> repo <可見性>[（額度提示）] <run 網址>`：失敗的 job 全都 0 個 step，GitHub Actions 沒有啟動它們（#132）。`<原因>` 是 check-run annotation 的第一句（讀不到時是 `unknown`，含空白，網址取行尾）；repo 是 private 時 `<可見性>` 後面緊接全形括號的提示：帳號下所有 private repo 共用 Actions 額度，到 Billing & plans → Usage 查看。不要原樣重跑（job 一樣不會啟動）。`main` 開了 branch protection（#402：required checks `checks`、`checks-macos`，含 administrators），這兩個 check 沒綠的 PR `gh pr merge` 一律拒絕，所以不論 `<原因>` 都不改用 `--local-checks`（本機檢查過了也會停在 `STOP merge`）：開 gate 交給人，付款、額度與 runner 由人處理，不關保護、不直推 `main` 繞過；人恢復 CI 並重跑那個 run（`gh run rerun <run>`）後，再在背景重跑第 1 步同一條指令。

- **Counterpart.** 跨 repo 的[對應單](../../GLOSSARY.md)交接由 Close 的 `scripts/pilot-close.mjs` 在證據留言之後做：它把成員本文交給 `scripts/pilot-counterpart.mjs`，每張印出的 `COUNTERPART` 都用 `<主 checkout>/.scratch/pilot/counterpart-<n>.md` 的內容到那張對應單留言。指令依對應單的 host 選：裸的 `<owner>/<repo>#<m>` 是 github.com，印 `COUNTERPART <owner>/<repo>#<m>`；GitLab（含自架的 http、IP，例如 spay2 在 `http://192.168.200.202`）與 GitHub Enterprise 的對應單在本文寫成 issue 網址（`http://192.168.200.202/spay/spay2/-/issues/692`），印 `COUNTERPART <path>#<m> <github|gitlab> <repo>`；GitLab 對應單寫成裸 ref 時 `gh` 讀不到，Close 印 `STOP <n> counterpart <ref> …`，提示改寫成 issue 網址（改成員本文後重跑）。腳本帶 `--file <交接檔>` 時每張後面多一行 `COMMAND <指令>`，取自 setup-workflow 的 gh／glab 對照表（`scripts/lib/hosts.mjs`，人看的是 [HOSTS.md](../../skills/engineering/setup-workflow/HOSTS.md)，旗標的 `--help` 核對紀錄也在那裡）：GitHub 是 `gh issue comment <m> --repo <repo> --body-file <檔>`，GitLab 是 `glab issue note <m> -R <專案網址> -m "$(cat <檔>)"`（`glab issue note` 沒有 `-F`／`--body-file`）；Close 執行的與交給人的是同一行。寫入被擋下時（auto mode 分類器以 External System Writes 擋、沒有權限、沒裝或沒登入 `glab`，或讀不到 GitLab 對應單的留言）Close 不停：每張印 `HANDOFF <n> <ref> ! <指令>`、這一步印 `MANUAL <n> counterpart`，照常往下關單、收尾；coordinator 把交接檔路徑和那行指令（前面加 `!` 就能在人的 prompt 直接跑）列給人，不自己在 wrapper 外重跑（直接跑的跨 repo 寫入不放行，見 Permissions）。整個 `pilot-close.mjs` 被擋下時也一樣：先用 `gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs --file <交接檔>` 取得 `COMMAND` 行交給人，Close 照常往下做。交接內容要 coordinator 自己寫：跑 Close 前先看成員本文（`gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs`，沒有輸出就不用寫），有對應單就寫好這個檔：成員 `ron03wlb/ron-skills#<n>`、ron-skills 的 merge SHA 與 PR 網址、這個成員改了什麼、對方要做的下一步。檔案不在，或沒寫出 merge SHA 與 `ron03wlb/ron-skills#<n>`，腳本會印 `STOP <n> counterpart …`，寫好後重跑。同一張對應單可能有好幾個成員（例如 #28、#29、#30 都指向同一張），所以略過條件兩個都比：對應單已經有同時含 merge SHA 與 `ron03wlb/ron-skills#<n>` 的留言就略過。給人的回報列出每張對應單和留言網址（#53）。

- **Close.** Push gate 印出 `LANDED`、batch 的 merge 進到 `origin/main` 之後馬上做，不等人：在主 checkout 跑 `node scripts/pilot-close.mjs <key> <pr> <merge sha> --repo ron03wlb/ron-skills`，不要再手寫 shell function（batch-40-51 手寫的版本用了 `branch -D`，orca 的錯誤也被 `2>/dev/null` 吞掉）。它先照 Bare guard 跑一次 `scripts/pilot-unbare.sh`（時機 `close #<key>`，上一輪可能中斷在 Orca 設成 bare 之後），再確認 merge SHA 已在 `origin/main`、主 checkout 在 `main` 上，`git -C <主 checkout> merge-base --is-ancestor origin/main main` 不是 0 就 `merge --ff-only origin/main`；再對 batch checkpoint 每個 `done` 成員照 [Evidence and closing](issue-run.md#evidence-and-closing) 依序做，每一步先看做過沒有，做過就略過，所以中斷後用同一行指令重跑：`evidence` 證據留言（附 PR 網址、merge SHA 與 `regression:` 行；留言已含 merge SHA 時略過）；`counterpart` 照 Counterpart 到對應單交接（交接檔要 coordinator 先寫好，沒有時 STOP；留言被擋下時印 `HANDOFF` 行與 `MANUAL <n> counterpart`，不停）；`close` 關 Issue（PR 的 `Closes #<n>` 已經關掉時略過）；`terminal` 用 `"$ORCA_CLI_COMMAND" terminal close --terminal <handle>` 關成員的 terminal（worktree 已移除或 `"$ORCA_CLI_COMMAND" terminal list --worktree path:<worktree>` 裡沒有它時略過）；`worktree` 用 `"$ORCA_CLI_COMMAND" worktree rm --worktree path:<worktree>` 移除 worktree（`<worktree>` 取自 `git worktree list`；Orca 開的 worktree 用 `branch:` 選擇器找不到，#49），rm 之後跑 Bare guard（時機 `close #<n>`），再以 `git worktree list` 確認真的不在；`branch` 用 `git -C <主 checkout> branch -d issue/<n>-<slug>` 刪本機分支（一律 `-d`：沒合進 `main` 就讓 git 拒絕；分支設了 upstream 時 `-d` 只比 upstream，所以先以 `merge-base --is-ancestor <分支> main` 檢查，沒合入就 STOP；Orca rm 已經一起刪掉時略過）；`remote` 在 `ls-remote --exit-code --heads origin issue/<n>-<slug>` exit 0 時 `push origin --delete`，exit 2（遠端沒有，worker 不 push）略過，其他 exit code STOP；`parent` 在成員有母單、母單還開著而且 `sub_issues_summary.completed == total` 時，留言列出每張子單和它的 `state_reason`（`completed` 與 `not_planned` 都算結束）再關閉母單。子行程的 stdin 都接 `/dev/null`；stderr 照常顯示，只濾掉 WSL 上 Orca 每次都印的 crashpad 錯誤行（`registration_protocol_win.cc`）。每一步印一行 `DONE <n> <step>` 或 `SKIP <n> <step>`（開頭 `main` 那步的 `<n>` 是 batch key；checkpoint 不在、沒有 `current:` 行或沒有 `done` 成員時只印 `STOP <key> checkpoint …`；有 `done` 成員的 branch 欄是空的或不是 `issue/<這一列的 n>-<slug>` 時，在 Bare guard 與任何寫入之前只印 `STOP branch-malformed <n> <JSON 字串的值>`（#120），把 checkpoint 那一列改對再重跑；這些都沒有 DONE／SKIP 行），請求分支成員（Issue 欄 `-`，見 Requests）沒有 Issue：只做 `terminal`、`worktree`、`branch`、`remote`，不留言、不關單、不呼叫 `gh` 與 `gh-tracker.mjs`，結果行的 `<n>` 與 Bare guard 的時機（`close <分支>`）用分支名稱，branch 欄要是 `retro/<x>`，否則同樣 `STOP branch-malformed - <值>`。全部成員做完它把 `current:` 設成 `closed`，最後一行印 `CLOSED <key>`（exit 0）。任何一步失敗都印 `STOP <n> <step> <原因>`（exit 4）並停在那一步：`counterpart` 缺交接檔時照 Counterpart 寫好再重跑；`branch` 的 STOP 表示這個分支有沒合進 `main` 的 commit，分支留著，回報人；其他 STOP 變成 gate。exit 2 是用法錯誤或沒有 `ORCA_CLI_COMMAND`。

- **Handoff.** 條件達到時（Probe 印 `HANDOFF_DUE` 或 compaction，見 Defaults），照 issue-pilot SKILL 的 Handoff 時機做（CoS item 134：spay2-7a 把 push gate、regression 當成不安全點一再延後，期間停止 Stage，19 張 ready、0 個 worker）：這個 session 沒有前景工作（還在跑的前景 Bash、寫到一半的 store 檔或 checkpoint、正在 inline 做的 stage 或衝突判斷、開著等人回答的問題）就 MUST 在這一輪結束時交接；push gate、regression、`scripts/pilot-land.mjs`、watcher、worker 這些背景工作 NEVER 算不安全點，不停、也不等它們結束；有前景工作時最多延後一輪，延後的那一輪 MUST 照 Decisions 記 `handoff deferred: <前景步驟>`，而且照常 Pick、Dispatch、Stage，NEVER 因為準備交接讓 ready 的單閒置；下一輪仍是 `HANDOFF_DUE` 就 MUST 交接，NEVER 再延後。交接時 coordinator 先照 Decisions 記一筆原因，還在跑的背景工作逐項寫進同一筆（task id 與輸出檔、指令、預期結果，這筆就是交接備忘，後繼第一輪照它看完結果，結束前不重跑那個 batch 的 land 或 push），停掉自己等待用的背景工作（watcher、regression waiter、idle wait；正在 land 或 push 的不停），再在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-handoff.mjs --session "$CLAUDE_CODE_SESSION_ID" --pid "$CLAUDE_PID" --reason <原因>`（setup-workflow 正本的副本；本 repo 沒有「整合分支合併進行中」的檢查，所以不帶 `--held-check`；要交給已經開著的 session 時加 `--to <分頁標題或 handle>`。腳本 540 秒內必定結束：逾時印 `STOP timeout`，收到 SIGTERM、SIGINT 印 `STOP signal <名稱>`，都會先還原）。它確認 `coordinator` 的 pid 是自己後改寫成 handoff 行，新開分頁 `issue-pilot coordinator` 送出 `/loop /issue-pilot`（或送給 `--to` 的 session），等新 session 寫入 `pid ` 行。最後一行 `HANDED_OFF <handle> [name <name>]` 才算交接完成（`name` 是接手 session 寫進 coordinator 檔的 name，別的 session 拿它 `SendMessage`；沒有 name 欄時只印 handle，#372），腳本這時已在 `sessions.md` 附加 handoff 行，coordinator 不再手動附加；`STOP <原因>` 時 `coordinator` 已還原、這次新開的分頁已關掉、`sessions.md` 沒動，照常繼續當 coordinator（`STOP not-coordinator` 表示已經有別的 coordinator，不要再交接；`STOP to-not-found`、`to-ambiguous`、`to-self` 是 `--to` 沒對到唯一一個別的 session，改用 handle 或不帶 `--to` 重跑）；`STOP orca timeout <步驟> <毫秒>ms`（例如 `STOP orca timeout terminal list 10003ms`）指出逾時的 Orca 步驟，單獨的 `STOP timeout` 才是總預算；`STOP tui-timeout <handle>` 時 stderr 的 `SCREEN_TAIL <handle>` 是新分頁關掉前的畫面尾巴，卡在啟動對話框（例如 Settings Warning 的設定錯誤）就先修好再重跑，#535、#536）。
