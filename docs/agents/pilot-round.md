# Pilot 每輪步驟：ron-skills

[pilot.md](pilot.md) 的必讀核心（14000 bytes，`scripts/adapter-size-budget.json`）放不下的每輪步驟條目（#344）。pilot.md 留同名的一行 pointer，寫明哪一步要讀；到那一步時用 `node scripts/adapter-line.mjs '<條目名>'` 只取那一條，不整份讀。

- **Sessions.** Entry 指令（SKILL 的 adapter's entry command）是在主 checkout 跑 `node scripts/pilot-register.mjs <主 checkout> --entry --name <ListAgents 印的 session 名稱> --loop yes|no --sources-file docs/agents/pilot-sources.txt`（pid、session 取 `$CLAUDE_PID`、`$CLAUDE_CODE_SESSION_ID`），第一行就是 Entry 判定，不必先讀 `coordinator`、`sessions.md` 或自己 `kill -0`（#592）：`ENTRY coordinator` 已登記、照常跑；`ENTRY retired → <terminal>`（exit 4）已交接給 `<terminal>`，什麼都不做；`ENTRY yield <name> pid=<pid>`（exit 4，什麼都沒寫）是別的 coordinator 活著，照 SKILL 交給它。退役與 yield 都先判；第一行不是 `ENTRY` 的只有 `STOP sources-file`（照本條末尾處理）與鎖逾時的 `CHECKPOINT_LOCKED`（exit 3，什麼都沒寫，稍後重跑）。之後每輪 Reconcile 一開始、跑 Probe 之前跑同一條但不帶 `--entry`（它不判 yield，會直接覆寫 `coordinator`）：它寫 `coordinator`（pid 不變時保留 `since`）、`sessions.md` 的 start 行只附加一次，最後記錄 Sources 的清單檔；印出的 `SOURCE_CHANGED`、`SOURCE_MISSING` 照 Sources 處理；`ADAPTER_FILE <存檔路徑> <路徑>` 是 adapter ref 那份比 `main` 新的 adapter 檔，已 fetch 並存好：讀 `<存檔路徑>`，不讀主 checkout 的 `<路徑>`（#467）；`NAME_CHECK <現名> registered <--name>`（照常登記、exit 0）表示 `--name` 不是這個 pid 現在的 session 名稱，重取 ListAgents 名稱、以它重跑同一條（#364）；`STOP retired` 表示這個 session 已交接出去，照 Entry 什麼都不做；`STOP sources-file <path>`（exit 4，什麼都沒寫）表示主 checkout 沒有清單檔（例如還在 #240 之前的 `main`），回報人，這一輪不做其他事。不手寫 `coordinator` 與 start 行，也不把來源逐個抄成位置參數（#240：session 76bb4905 漏抄了 4 個 `pilot-*.md`）。

- **Sources.** 來源清單在 `docs/agents/pilot-sources.txt`（一行一個，相對主 checkout 或絕對路徑，`~` 由腳本展開；空行與 `#` 開頭的行略過），這裡不再逐一列檔名。adapter 新增 coordinator 要讀的檔（例如 Pilot 段新連到一份 `pilot-*.md`）時，在同一個 commit 裡往清單檔加一行；下一輪 Sessions 指令就對它印 `SOURCE_CHANGED`。來源檢查就是每輪的 Sessions 指令：它讀清單檔，最後以 `pilot-sources --record` 記錄這份清單，印出的每行 `SOURCE_CHANGED <path>`、`SOURCE_MISSING <path>` 就重讀那個檔案，沒有這兩種行就是都沒變；`SOURCE_CHANGED` 下面有縮排行（`  entry <名稱>`、`  heading <標題>`、`  outside`，快照存在 `.scratch/pilot/source-snapshots/`）時只重讀列出的條目、標題底下的段落或第一個標題前的內容，不必再 `git log`、`git show` 找改了什麼；長條目的縮排行底下還有再縮排的片段行（`    …<前文>[-<刪除>-]{+<新增>+}<後文>…`，詞級 diff）時讀片段就好，不重讀整個條目、也不再自己跑 `git diff --word-diff`；片段行是 `    (diff <n> chars, reread)` 時才重讀整個條目（#236、#239）；沒有縮排行（沒有舊快照，或只改了空行、單位的順序）就重讀整份；pointer 指去的那幾份只有這個 session 讀過時才重讀，沒讀過的等 pointer 指到時再讀；但第一輪與 compaction 之後仍照 SKILL 的 Sources 全部重讀（pilot.md 以外的 `pilot-*.md` 仍等 pointer 指到才讀），記錄可能是前任 session 留下的。同一輪不要再單獨跑 `node scripts/pilot-sources.mjs <主 checkout> --record …`：記錄已經被 Sessions 指令改寫，它什麼都印不出來，改過的檔案就漏讀了；只有那一輪沒跑 Sessions 指令時才單獨跑它。

- **Defaults for `preferences.md`.** 本 repo 同時跑的 worker 最多 4 個（Dispatch 的 `--repo-cap 4`）；整台機器同時跑的 worker 合計最多 4 個（`$PILOT_MACHINE_WORKER_CAP`，沒設時 4；這類變數設在 `~/.claude/settings.json` 的 `env`，見 Probe lines），含 investing 等其他 repo 的 pilot／cycle，fresh 重派也算在內；合計讀全機帳本（Probe 的 `--capacity` 寫入、Dispatch 的 `--capacity` 檢查並在派出後加上派出人數）；還沒寫帳本的 repo（`scripts/` 沒有 `pilot-capacity.mjs` 或沒帶 `--capacity`，例如 investing）不在帳本裡，派工前另把它在跑的 worker 加進來（investing 先跑 `node scripts/pilot-capacity.mjs env INVESTING_DATA_ROOT`，再讀 `$INVESTING_DATA_ROOT/.local/agent-notes/cycle/state.md` 的 Batch in flight 裡「開跑」的子代理；其他 repo 看 `ListAgents` 裡該 repo 的 busy session，#295），合計加上這批人數超過上限就不 Pick、不 Dispatch。依據見 `scripts/pilot-capacity.mjs` 檔頭：10 核機器上同時 8 個 worker 時 load 約 90，計時測試失敗（#178）。每批最多 2 個 Issue；worker 指令見 Dispatch；只有 coordinator 合進 batch 與整合分支；push、開 PR、合進 `main` 都由 coordinator 照 Push gate 做，不交給人（worker 不 push、不開 PR）；每個 session 合入 2 批、context 到 Handoff context: 200000，或遇到 compaction 就 handoff：批數不自己數，讀 Probe 的 `HANDOFF_COUNT <n>/2`（`--handoff-after 2`），印 `HANDOFF_DUE` 才算達到，前任派的 batch 不算（#368：investing 66e552ea 把前任派的 381、383 算進來）；context 讀 Probe 的 `HANDOFF_CONTEXT <tokens>/200000`，到門檻時印 `HANDOFF_DUE context=<tokens>`，印 `HANDOFF_CONTEXT ?/200000 WARN …` 時量不到，自己看 context 判斷（CoS item 88：context 超過 150k 的 session 占全部原始量 88%）；達到後沒有前景工作就在這一輪交接，背景工作不算不安全點，最多延後一輪且延後時照常 Stage 與派工（見 [pilot-after-merge.md](pilot-after-merge.md) 的 Handoff）。

- **Pool.** `node scripts/issue-pool.mjs --integration pilot/integration`（setup-workflow 正本的副本）把開著的 Issue 逐張分桶印成 `<桶> #<n> <標題>`（有母單的 ready 行寫成 `ready #<n> parent #<p> <標題>`，#397），`ready` 桶已經排好序（`retro` label 的先、`priority` label 的先、直接或間接 block 最多開著的單的先、號碼小的先），照印出的順序挑，略過已經在某個開著的 batch checkpoint 裡的 Issue。ready 單另有 `PREREQ <n> <內容>` 行的，本文的 Operator prerequisite 不是「無」：先查環境或開 gate，滿足了才派，不要派出去讓 worker 在 preflight 停下（#352，investing#190：#133、#138）。`PICK_OVERLAP <n> <m> <檔|**<條目>.**>` 行是提示 `#<n>` 可能改到 `#<m>`（另一張 ready 單，或某個 worktree 的分支）改的檔或條目：互相重疊的兩張 ready 單不挑進同一批，和在跑或 done 成員重疊的延後；它依本文推測，不保證準（#355 本文沒提 `orca-session-send.mjs` 卻改了它），由 coordinator 判斷，腳本不自動延後，Probe 的 `OVERLAP` 仍是底線（#591）。進行中只數 `claimed`；main 暫停旗標有效時 landed 桶收成一行 `LANDED_COUNT <數量> pilot/integration`（#379）；`stale` 桶預設收成一行 `STALE <數量>`，要看是哪幾張時加 `--stale`（#550）；`landed` 是已指派、工作已在 `pilot/integration`（最近一則認領之後有 `DONE` 結果行，或分支已合入）只等進 `main` 的單，不算 worker，也不要當 `stale` 釋放（#352，investing#269）。`blocked` 行寫了狀態與 blocker（`blocked #247 needs-triage by #151 <標題>`，blocker 已在整合分支時接 `(landed pilot/integration)`）：`needs-triage`、`unlabeled` 的 blocked 單照樣先照 Readiness 補齊，不必等 blocker（investing retro 1120b 的 #434…#438）。池子沒有 `ready` 行（Probe 印 `POOL_EMPTY`）時跑 `node scripts/issue-pool.mjs --pickable-blocked --integration pilot/integration`（唯讀），不要逐張手查 blocked 行的 blocker：`PICKABLE <n>` 是開著的 blocker 都已在 `pilot/integration`、範圍也沒再開，當 `ready` 單挑（`needs-triage` 的先補齊）；`WAIT <n> <blocker>:<原因>`（`not-integrated`、`open-scope`、`other-repo`）留在桶裡（#501，investing retro 1122a：手寫 `gh api` 迴圈每輪約 40 次呼叫）。帶 `retro` label 的 ready Issue 先挑：它是 `/retro-collect` 判定太大、交給 worker 的 retro 候選；候選清單本身掛 `retro-candidates`，留給 `/retro-collect`，不進池子。`ready` 桶就是[池子](../../GLOSSARY.md)：標 `ready-for-agent`，不是母單、沒有開著的 `blocked_by`、沒被[認領](../../GLOSSARY.md)、沒有開著的 PR 指向它（`in-review` 桶，單獨跑的 `/issue-run` 做完在等合併，#284），也沒有 `ready-for-human`、`needs-info`、`needs-triage`、`retro-candidates`（這些各有自己的桶，桶的優先序寫在腳本檔頭）；`stale`（認領超過 24 小時沒有新留言或新指派）不會自動釋放，回報人決定要不要取消指派。有 sub-issue 的是母單（`parent` 桶）：母單只分組、不派工也不驗收，pilot 一律挑它的子單（`/to-spec` 會給母單掛 `ready-for-agent`，不排除就會跟子單重複派工）。人手動跑 `/issue-run <母單>` 時仍照上游展開子單。`needs-triage` 的先照 [Readiness](issue-run.md#readiness) 補齊，變成 `ready-for-agent` 才挑。Probe 印 `STAGEABLE` 時，這一輪的 Pick 延到 Land 之後：新 worker 的 `bin/check` 推高 load，Stage 會印 `STOP load` 或跑很久（#392）；成員有 `OVERLAP` 時更不能先派：還沒 stage 的 done 成員日後衝突重做，`pilot-dispatch.mjs --fresh` 的 overlap 檢查會撞上剛派出的新單，只能 `blocked-by` 到它、延後一整輪（#218：同一輪已印 `WORKER 193 DONE` 與 `OVERLAP 178 193`，卻先派了 batch 107-130，之後 #193 重派印 `STOP 193 overlap … 130 …`）。

- **Triage brief.** coordinator 把 `needs-triage` 單（或拆單）交給子代理細化時，prompt 就是下面縮排的幾行，代入 `<n>…`、`<主 checkout>`、`<adapter checkout>`、`<stage worktree>`（其他 `<…>` 由子代理自己填），再補上單號與這一輪知道的事；repo 事實不憑記憶重寫（#381、investing#379：一個 session 手寫五次 30–40 行 brief，每次重複路徑，子代理仍踩到 brief 沒寫的主 checkout 防護 hook 與舊版腳本）。自己細化時照 [pilot-exceptions.md](pilot-exceptions.md) 的 **Triage.**。
  細化 ron03wlb/ron-skills 的 Issue <n>…：`/triage` 設了 `disable-model-invocation`，Skill tool 叫不動，改讀 `~/.claude/skills/triage/SKILL.md` 與同目錄的 `AGENT-BRIEF.md` 照做；每則留言開頭放 AI 聲明、用繁體中文，一個分類 label 加一個狀態 label；標 `ready-for-agent` 前先照 `docs/agents/issue-run.md` 的 Readiness 確認：驗收與做法的每份輸入都能從本 repo、tracker 或公開來源取得（只在別的 checkout 或別台機器的維持 `needs-info`，#116），本文的跨 repo 對應單用 `gh issue view <n> --json body --jq .body | node scripts/pilot-counterpart.mjs --adapter docs/agents/issue-run.md` 檢查；這些都過、範圍與驗收清楚才標 `ready-for-agent`，同時留一則 agent brief；要拷問或要人選的標 `needs-info` 或 `ready-for-human`，brief 不留「挑不出來就停下」的分岔。brief 的 Key interfaces 點名要加字的檔若受預算管（`scripts/adapter-size-budget.json` 有列，含 `PILOT-TEMPLATE.md#after:-->` 這種只算本文的條目），先跑 `node scripts/check-adapter-size.mjs --headroom`，把該檔的 `HEADROOM <檔> <剩餘> <目前>/<上限>` 抄進 brief；剩不到要加的量時直接指定放到 `PILOT-ROUND-TEMPLATE.md` 或拆出去的檔（#647：brief 叫 worker 加在只剩 56 bytes 的 PILOT-TEMPLATE，到 `bin/check` 才發現）。
  每條指令寫成 `cd <主 checkout> && <指令>`。adapter 讀 `<adapter checkout>` 的 `docs/agents/`（平常是主 checkout；這一輪 Probe 印了 `ADAPTER_AHEAD` 就是 `<stage worktree>`），Probe 列成 `SCRIPT_AHEAD` 的腳本用 `node <stage worktree>/<路徑>` 跑。
  可能卡住的指令用 Bash 工具的 `timeout: 600000` 限時，不用 `timeout` 指令（macOS 沒有）。留言內文與暫存檔用 Write 工具寫到 `<主 checkout>/.scratch/`，再用 `--body-file` 交出，不用 heredoc（#444）。
  只寫 tracker，一律經 `node scripts/gh-tracker.mjs`：留言與 label（`comment`、`edit --add-label/--remove-label`），拆單時先跑 `node scripts/worktree-overlap.mjs <檔案>…` 與 `gh issue list --state open --search "<檔名> in:title,body"` 查重疊，再開新單並掛 sub-issue 與 `blocked-by`（`create`、`sub-issue add`、`blocked-by add`，或一份 `batch`）；不改、不 commit、不 push repo 檔，不開 worktree、不認領、不開 gate。
  讀 Issue 一律 `gh issue view <n> --json number,title,body,labels,comments`（只帶 `--comments` 在非 tty 沒有本文，#428）。主 checkout 的 `scripts/claude-hook-main-checkout.mjs` 擋會讓 `git status` 不乾淨的寫入（改追蹤檔、新增沒被 gitignore 的檔），gitignored 的 `.scratch/` 放行。
  最後每張單一行：`TRIAGED <n> <label>`、`NEEDS_INFO <n> <缺什麼>` 或 `HUMAN <n> <要人選的問題>`。

- **Dispatch.** 派工前先在主 checkout 對每個成員跑 `node scripts/issue-pool.mjs claim <n> --integration pilot/integration`（session 取 `$CLAUDE_CODE_SESSION_ID`）：印 `LANDED <n> <sha>` 表示它的工作已在 `pilot/integration`（`(#<n>)` commit、分支已合入，或已指派、最近認領之後有 `DONE` 而且那個 sha 是 `pilot/integration` 的祖先），不認領也不派，從這一批拿掉，等那個 SHA 進 `origin/main` 後照 Close 收尾（合入它的 batch 關了就不用再關，#352，investing#240 的 #145）；印 `CLAIMED <n>` 才派，前面多一行 `DONE_NOT_LANDED <n> <sha>` 是 DONE 的 sha 沒進整合分支（stage 衝突沒合進去），照常派（#644）（同一個 session 重派會再認領一次，順便更新 `stale` 的時間）；認領者是這台機器上先前的 coordinator session（handoff 之前派的，`.scratch/pilot/sessions.md` 有它的 handoff 行），而 claim 的是現任 coordinator 時，腳本直接以那個 session 接手，印 `CLAIMED <n> takeover <session>`，照樣派；`STOP <n> claimed <機器>／<session>` 表示別的機器或 session 已經在做，這個成員不派、從這一批拿掉；`STOP <n> claimed <登入名>` 是有人手動指派（沒有認領留言，或指派換了人），回報人。接著在主 checkout 用 Bash `timeout: 600000` 跑 `node scripts/pilot-dispatch.mjs <key> <n>:<slug>... --capacity --repo-cap 4`（成員依號碼順序，如 `node scripts/pilot-dispatch.mjs 23-46 23:pilot-probe 46:pilot-dispatch --capacity --repo-cap 4`；`--fresh` 重派也帶這兩個旗標（派工路徑漏帶時腳本也預設照 `--capacity --repo-cap 4` 檢查並回報帳本，只有顯式 `--no-capacity` 才略過，coordinator 不用它，#534），只寫草稿、不派工的 `--fresh`（沒帶 `--note`）不帶任何容量旗標；腳本 540 秒內必定結束）。它先數本 repo 開著的 batch checkpoint 的 `running` 列（這次要派的成員自己的列不算）、加上這次要派的人數比 `--repo-cap`，再合計全機帳本、加上這次要派的人數（`--fresh` 是 1）比 Defaults 的上限：超過就只印 `STOP capacity repo <合計>/<上限>` 或 `STOP capacity <合計>/<上限> [<repo>=<n>...] +<人數>`（列出帳本裡計入的列，看出佔名額的是誰；terminal 已 exited 的成員 Probe 不計，#408）、exit 4，不寫 checkpoint、不建 worktree、不開分頁，並放掉這個 session 認領的成員、各印 `RELEASED <n>`，這一批留到下一輪。不超過時先印 `CAPACITY ok repo <合計>/<上限>`、`CAPACITY ok <合計>/<上限>`；有成員派出時最後印 `REPORTED ron-skills …`：派出人數已加進帳本 ron-skills 那一列（主 checkout 的目錄名），同一輪再派一批時合計已含它們；每輪第一次派工前仍要先跑過這一輪的 Probe。它會寫 batch checkpoint 的表頭（已存在就不動）和每個成員一行（重跑時同一個 Issue 的那行就地換掉），每個成員印一行 `DISPATCHED <n> <handle>`、`HOLD <n> blocker <m>[,<m>…] unstaged`，或 `STOP <n> <原因> row=<kept|stop|running>`（行尾的 `row=` 是這一行之後成員列的狀況：`kept` 沒動、`stop`、`running` 是改寫成的 state，以它為準，不必背哪種 STOP 改不改列，investing#481；原因只在這一行，要留就記進 `decisions.md`；`STOP <n> send <handle>` 是 `row=running`：確認不了不代表 worker 沒在跑，交給 Probe 判定，不要重派或手動補送，#354）。`HOLD`（這是 dispatch 的成員行，不是 Probe 的 `HOLD`）：成員開著的 blocker <m> 本機分支 `issue/<m>-*` 有 commit 不在 `pilot/integration`（blocker 的最新候選還沒 stage，investing#486），什麼都沒建、成員列沒動、認領保留；等 <m> 這一輪 Stage、Integrate 之後用同一個 key 只帶它重跑。Bare guard 還原時另印 `UNBARE <主 checkout>`。exit 0 全部派出、4 有成員 STOP 或 HOLD。不要自己手寫 `"$ORCA_CLI_COMMAND" worktree create`、`terminal create` 或裸 `terminal send` 的迴圈：Orca CLI 會吃掉 stdin，`while read` 只派到第一個成員；裸 `terminal send` 會回 accepted，文字卻停在輸入框沒提交。

- **Brief check.** worker 的 brief 就是 `/issue-run <n> --worker <checkpoint>` 加上 Issue 本文，不跑這條（路徑由 triage 的 `--paths` 查過）。tooling fix unit 的 brief：先用 `node scripts/brief-check.mjs --skeleton` 印出帶標籤的骨架（`目標：`、`範圍：`、`驗收：`、`驗證：`、`TIMEBOX：<n> 分鐘`、`禁止：`、`回報：`、`Standing orders：` 已填主 checkout 的 `preferences.md`），寫進 `.scratch/pilot/briefs/<檔>` 填好內容，再跑 `node scripts/brief-check.mjs <brief> [--batch <key>] [--iid <n>]`：印 `BRIEF_OK <brief>`（exit 0）才派；`BRIEF_REJECTED … missing=<欄位,…>`（exit 1）時補 brief 再跑，不改 worker 的 prompt（#346）。

- **Resume.** 請 `stop`／`done` 的 worker 繼續（gate 解決後照答案做、Stage 衝突要它先合入整合分支）一律跑 `node scripts/pilot-batch.mjs <主 checkout> resume <key> <n> --note <指示>`，不用裸 `terminal send` 加手改列：它先讀畫面最後一個結果行，經 `orca-session-send` 送達 note 後才在鎖內把列改回 `running`、清 candidate、`started` 設為現在，表格下方加 `resumed: #<n> <時間> <結果行|->`，印 `RESUMED <key> <n>`；Probe 遇到畫面最後一個結果行還是那一行時不算結果，舊 `STOP`／舊 SHA 的 `DONE` 不會被 `--apply` 寫回，也不印假 `STUCK`。印 `STOP <key> missing`、`STOP <n> state …`（送出前的檢查：成員不在或不是 `stop`／`done`）或 `STOP <n> orca|send|tui-timeout …` 時 note 沒送到、檔案沒動，修好原因再跑（同一個成員第二次 `tui-timeout` 起改照本條末段，不再重跑）；`STOP <n> orca terminal_handle_stale` 是分頁已不在（例如重開機），沒有原因可修：改用同一個 key 重派，`issue-pool.mjs claim <n> --integration pilot/integration` 後跑 **Dispatch.** 的 `pilot-dispatch.mjs <key> <n>:<slug> --capacity --repo-cap 4`，worktree 與未 commit 的檔都保留（#665）；印 `STOP <n> delivered …` 或 `CHECKPOINT_LOCKED`（resume 只在送達後拿鎖）時 note 已送到、檔案沒動，手改列，不要重跑（會送兩次）。代決 worker 的 `STOP decision` 而採用它已回報的 candidate 時跑 `node scripts/pilot-batch.mjs <主 checkout> accept <key> <n> <sha>`（`<sha>` 必須是該列分支的 HEAD），印 `ACCEPTED <key> <n> <sha>` 後列成為 `done`，照常 Stage，不重派（#347 曾因此多派一個 worker）；印 `STOP <n> sha <分支 HEAD>|missing` 時分支已不是那個 candidate（或沒有這個分支），檔案沒動：先讀分支上多出的 commit 再決定 accept 哪個 SHA 或重派。同一個成員 `resume` 連續兩次印 `STOP <n> tui-timeout` 時不再重試（#593：#395 連跑三次才開 gate）：讀 stderr 的 `SCREEN_TAIL`，畫面是閒置輸入列（空 `❯`、沒有 spinner、沒有對話框）時，原因是 Orca 的 `tui-idle` 條件沒滿足（#395 的 footer 有 `← 1 agent`，因果未確認；就緒由 Orca 判斷，本 repo 不重判），改走 `node scripts/pilot-dispatch.mjs <key> --fresh …`（先不帶 `--note` 產生草稿、再帶 `--note` 重跑，照 [pilot-conflict.md](pilot-conflict.md) 的 **Fresh redispatch.**）；prior 工作樹有未提交改動時，不帶 `--note` 的草稿那一步就把它們備份成 `.scratch/pilot/backup/issue-<n>-dirty*.patch` 並 stash，列在草稿的「prior 未提交的改動」段（#625；帶 `--note` 時才遇到的改動另印 `DIRTY_BACKUP <n> <patch>`），fresh worker 從那裡取回，不必開 gate，只有 `STOP <n> backup <原因>` 才停下處理；畫面是對話框（Settings Warning 等）時照 `SCREEN_TAIL` 的既有處理。
