08 常見坑

換了專案也會再踩的坑。專案自己的坑（特定資料庫、特定 CI、特定測試環境）寫在專案的文件裡，不放這裡。

工具與環境

依平台分組：WSL、macOS 專屬的坑各自一組，其餘放通用。原生 Windows 不支援（見支援平台），不列在這裡。

WSL

這幾項只在 WSL 發生，但每項的做法都標了「其他平台無害」：照做不會出錯，所以不必依平台分支（例如 core.bare 的檢查在每個平台都無條件跑）。

症狀原因做法
Orca worktree create 回 runtime_unavailable 或 runtime_timeout，重試後多出一個 <name>-2從 WSL 呼叫時，回應早於實際完成只呼叫一次，用 git worktree list 輪詢確認；絕不重試。其他平台無害
Orca worktree create --repo path:<WSL 路徑> 回 repo_not_found（帶 --agent 時變成 agent_session_operation_unknown）WSL 下 Orca 以 Windows UNC 路徑記錄 repo不帶 --repo，在該 repo 的 checkout 執行，讓 Orca 從 cwd 推斷。其他平台無害
Orca 的 worktree 操作（create、rm）之後，主 checkout 在 git worktree list 顯示 (bare)，git status 回 must be run in a work tree從 WSL 建立或移除 worktree 時，Orca 把主 repo .git/config 的 core.bare 改成 true，不一定在指令當下發生每個 tick 開頭與每次 worktree create、worktree rm 之後，在主 checkout 跑 git rev-parse --is-bare-repository，印出 true 就執行 git config core.bare false（setup-workflow 的 pilot-unbare.sh 正本；claude-hook-unbare.sh 掛 PreToolUse 在 session 中途也還原，Orca＋WSL 時帶入）。其他平台無害
WSL 裡 headless Chromium 截圖的中文變方框WSL 預設沒有中文字型把 Noto Sans TC 放進 ~/.local/share/fonts/、在 fontconfig 加 fallback、fc-cache -f。其他平台無害

macOS

症狀原因做法
測試在 macOS 比對路徑失敗，期望 /var/folders/… 實際是 /private/var/folders/…macOS 的 os.tmpdir() 在 /var 底下，而 /var 是 /private/var 的 symlink；git 與 realpath 回的是解開後的路徑測試的暫存目錄先取 realpath 再比對（ron-skills 用 realTmpdir()）
bin/ 下的腳本在 macOS 報 declare: -A: invalid optionmacOS 內建的 /bin/bash 是 3.2bin/ 只用 bash 3.2 語法；複雜的邏輯改寫成 node
sed -i 's/…/…/' <檔> 在 macOS 報 invalid command code 或把下一個參數當成備份後綴BSD 版 sed -i 一定要接備份後綴參數，GNU 版不接兩邊都通的寫法是 sed -i.bak '…' <檔> 再刪掉 .bak，或改用 node；可攜性檢查兩邊專屬的寫法都擋，只放行 -i.bak
管線後面接 paste -sd+，在 macOS 只印出 usageBSD paste 要明寫 - 才讀 stdin寫成 paste -sd+ -，兩邊都通
讀 /proc 的腳本在 macOS 拿不到資料macOS 沒有 /proc不讀 /proc；改用環境變數標記或 ps，平台判斷用 process.platform
兩個只差大小寫的檔名在 macOS checkout 後只剩一個macOS 預設的檔案系統不分大小寫不讓 repo 裡出現只差大小寫的路徑；可攜性檢查會擋

通用

症狀原因做法
agent 讀 Issue 拿到空白gh issue view <n> --comments 在非 tty 環境（agent 的 Bash 工具）不輸出任何東西一律 gh issue view <n> --json number,title,body,labels,comments；寫進 docs/agents/issue-tracker.md
which orca 有東西，Orca 指令卻都失敗Linux 上的 orca 是 GNOME 螢幕閱讀器Orca 可用與否只看 ORCA_CLI_COMMAND 是否設定
orca terminal send 回 accepted，worker 的輸入框卻是空的；重送後收到黏成兩份的 promptTUI 剛就緒時輸入停在 draft 沒提交，--screen 看不到 draft用會讀 draft、確認畫面出現 prompt 才回報送達的送出腳本；draft 已有 prompt 時只補 Enter
git stash pop 套上了別的 session 的改動stash 清單是所有 worktree 共用的worktree 之間不用 stash 搬東西；要暫存就用 WIP commit，非用 stash 不可時加唯一訊息、記下 SHA、以 git stash apply <sha> 還原
本機全綠，CI 一跑就紅本機的上游 checkout（fork）落後上游acceptance 對上游最新版跑一次（ron-skills：bin/check --upstream）
背景工作看起來像 timeout背景行程繼承了忽略 SIGINT 的設定先在前景與背景各單獨重跑一次，再判斷是不是負載
貼到終端的 SQL 或多行設定執行結果不對換行被轉成 CRLF，或被終端折行以檔案交付，請人用檔案執行，不要貼上

權限與規則

症狀原因做法
每次啟動 Claude Code 都警告 allows any option at its *allow 規則的 * 在中間（git -C * fetch），能夾帶 git 選項* 只放最後；git 寫入包進腳本或 pilot_git.py（見 04 權限規則）
agent 說它需要一條新的 allow 規則.claude/settings.json 只有人能改人審過再加；不要讓 agent 自己編輯 settings
規則寫在 memory 或 skill 裡，agent 還是一再違反文字規則沒有強制力做成檢查或入口（見 07 規則沉澱）
/loop /<skill> 叫不起來skill 設了 disable-model-invocation，Skill tool 呼叫不了被 /loop 驅動的 skill 不設這個旗標
改了一行註解，測試就紅那個檔被其他檔以 hash 釘住改既有檔前先查是否被釘住；adapter 的 Review 段列出釘住的檔

流程

症狀原因做法
開了一堆空的 worktree，看板與 worktree 對不上開單就建 worktree，或兩套看板各自記狀態認領時才建；只用 tracker 的 label 當看板
Issue 關了，改動卻還不在主線合併與結案之間隔著 push，人忘了兩段式結案：第二次先查 SHA 已在遠端才關單（見 04）
換人或換標題後，又試了一次早就證明不行的做法撤回的方案只留在舊對話或留言裡被重開、回歸或長尾的 Issue，開工前先彙整已撤回的方案寫進 checkpoint
兩個 session 同時合入，結果對不上整合分支與回歸是共用資源合入只有一個入口且有 lock（見 04）
回歸通過了，合入後卻是紅的回歸跑在 stage 時的 SHA，之後整合分支又有新 commit回歸只對那個 SHA 有效；整合分支有新 commit 就重新 stage、重跑
worker 印了 DONE 之後又醒來，回報「沒事可做」它自己排的 /loop 喚醒或背景工作還在worker 印完最後一行就停掉自己的 loop 與背景工作
長時間跑同一個 coordinator，判斷越來越差context 一直 compactioncoordinator 刻意短命：合入幾批或遇到 compaction 就交棒
