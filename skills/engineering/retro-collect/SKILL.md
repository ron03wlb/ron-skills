Every session's `/retro` runs in **collect mode** when the repo's adapter has a **Retro collect** entry: it opens one Issue labelled `retro-candidates` listing its candidates and implements nothing. Those Issues come from any session (`/issue-pilot`, `/issue-run`, `--pool`, a manual one) on any machine. You turn every open `retro-candidates` Issue into one retro unit. A `retro` Issue is different: a candidate too large for that unit, handed to a worker through the pilot pool. Project facts come from the repo adapter `docs/agents/issue-run.md`: the **Retro collect** entry of its Pilot section (in the file the Pilot section points to, when it points to one) names the checkout to run from, the claim command, the worktree and its target branch, the checks, and the landing, and its **Tracker** section gives the tracker commands; with no **Retro collect** entry, stop and say so. Run from the checkout the entry names. `$ARGUMENTS` may name Issue numbers to restrict the run to.

## Steps

1. **Roster.** List the open Issues labelled `retro-candidates` with the adapter's tracker (on GitHub `gh issue list --state open --label retro-candidates --json number,title`), restricted to `$ARGUMENTS` when given. Claim each one with the entry's claim command; one another session already holds is being collected there, so leave it out and name it in the report. Done when every listed Issue is claimed by this session or left out, and at least one is claimed; with none, report that and stop.

2. **Plan.** Read every claimed Issue in full, comments included. Write `.scratch/retro/plan-<MMDD><letter>.md` with one line per candidate of every Issue: `adopted` (merged with its duplicates from other Issues, citing every `#<n>` and item number), `covered <commit, branch, or #n>` (already on the entry's target branch, in another worktree's unmerged diff, or in another open Issue: check per the `retro` skill's concurrent-edit step), or `dropped <reason>` (the Issue itself or a later comment advised against it). Done when every candidate of every Issue has exactly one line.

3. **Implement.** Every `adopted` line is implemented: the standing order is that retro candidates are adopted without asking item by item. Use one worktree created as the **Retro collect** entry says; changes to user-level skills go to `~/code/ron-skills` per its README. Independent file sets may go to parallel subagents in that worktree, each owning disjoint files, running ref-moving git (checkout, switch, reset, stash) only in its own scratch clone, and reporting the adapter sentences its change needs; you apply the adapter and doc edits yourself. A candidate that adds a check is done only with the `retro` skill's proof: the real past mistake as a fixture and the check failing on it. A candidate too large for this unit (it needs its own design, dependency order, or a worker's full run) becomes its own Issue labelled `retro` plus one category label (`bug` or `enhancement`, per the adapter's triage labels), written to the adapter's readiness standard and labelled ready when it meets it, after the `retro` skill's tracker-duplicates search; mark its line `blocked → #<n>`. Done when each `adopted` line is marked `done <file>` or `blocked → #<n>` in the plan.

4. **Land.** Confirm `git symbolic-ref HEAD` in the worktree still names the retro branch, run the **Retro collect** entry's checks on the worktree, commit with a `chore: retro …` subject, recheck concurrent edits against the entry's target branch, then merge and push as the entry says. Done when the merge is on the remote target branch, or a check failed and you reported its output.

5. **Close.** Comment on each claimed Issue with the landed commit and what each of its candidates became (`done`, `covered`, `dropped`, `blocked → #<n>`), then close it, unless the landing already closed it (a `Closes #<n>` line); a candidate handed to a `retro` Issue lives on there. Report the landed commit, each plan line's outcome, every `retro` Issue opened, and every Issue left out in Roster.
