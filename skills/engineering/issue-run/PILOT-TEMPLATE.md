# Pilot: {{repo}}

Project settings for the user-level `/issue-pilot` coordinator (`/loop /issue-pilot`). Every section of `docs/agents/issue-run.md` still applies under the pilot; this file holds only what differs. Every file under `.scratch/pilot/` (batch checkpoints included) follows the `issue-pilot` skill's `PILOT-STORE.md` (`~/.claude/skills/issue-pilot/PILOT-STORE.md`), which also lists each script's commands and result lines; only this repo's values are written here. Every script named below is a setup-workflow template copy in `scripts/`.

- **Coordinator checkout.** `<main checkout>` below is this repo's main checkout: the parent of `git rev-parse --path-format=absolute --git-common-dir` (the same answer from any worktree). Substitute the absolute path when running. `.scratch/pilot/` lives there and is gitignored. Orca commands are written `"$ORCA_CLI_COMMAND"`; without that variable, report to the human instead of guessing a command name.

- **Bare guard.** `scripts/pilot-unbare.sh <main checkout> <when>` restores `core.bare` if an Orca worktree operation set it. Probe, Dispatch, Stage and Close run it themselves (printing `UNBARE <checkout>` when it fixed something); run it by hand only when one of them exits non-zero. Outside WSL it normally prints nothing.

- **Sessions.** On becoming coordinator, and at the start of every Reconcile before the Probe, run in the main checkout `node scripts/pilot-register.mjs <main checkout> --name <session name from ListAgents> --loop yes|no --sources-file docs/agents/pilot-sources.txt` (pid and session default to `$CLAUDE_PID`, `$CLAUDE_CODE_SESSION_ID`). `STOP retired` means this session already handed off: do nothing else. Treat its `SOURCE_CHANGED` and `SOURCE_MISSING` lines per Sources.

- **Sources.** The list is `docs/agents/pilot-sources.txt`, one path per line. Reread each file the Sessions command prints as `SOURCE_CHANGED` (only the entries or headings listed under it, when it lists any) or `SOURCE_MISSING`. When this adapter starts pointing at another file the coordinator must read, add it to the list in the same commit.

- **Decisions, requests, hold.** Append to `decisions.md` only with `node scripts/pilot-decision.mjs <main checkout> --decision <text> --reason <text> --evidence <text> --result <text>` (no `|` in a field; `--repair` when the table looks broken). List and mark requests with `node scripts/pilot-request.mjs <main checkout> list`, `apply <line no> [--note <text>]`, `decline <line no> --reason <text>`. Set, clear and show the hold with `node scripts/pilot-hold.mjs <main checkout> set <reason>`, `clear`, `show`.

- **Gates.** Open with `node scripts/pilot-gate.mjs <main checkout> open --title <text> --issue <#n or -> --question <text> --options <text> --default <text> --parked <text> [--hold <n>] [--script <file>]` (see below for `--script`; add `--hold <n>` when the gate holds back batch member #n, so the probe prints `HELD <n> G<k>` instead of `STAGEABLE` and `pilot-land.mjs` stops with `STOP held <n> G<k>` until the gate is resolved), resolve with `resolve G<n> --how <text>`, list with `list`. A gate is how every product question reaches the human. When the human must run commands, write the steps to a file and add `--script <file>`: the gate keeps a rerunnable `.scratch/pilot/gates/G<n>.sh` that survives a handoff, and `open` appends ` 執行：! bash <that path>` to the question, to run from the main checkout, since `G<n>` is unknown before it runs. Start each step with `step <label>`; write a read-only query as `x="$(<command>)" || true` then check its output, so a query that exits non-zero does not end the script; and have a step that changes state check that state first and skip when it is already done, since a rerun after a failure starts from the top.

- **Defaults for `preferences.md`.** At most {{worker cap}} workers from this repo at once (Dispatch's `--repo-cap`), and the machine-wide total stays within `$PILOT_MACHINE_WORKER_CAP`, shared with other repos' coordinators through the ledger the Probe's `--capacity {{repo}}` writes and Dispatch's `--capacity` checks and raises by the members it dispatched. At most {{batch size}} Issues per batch. Only the coordinator merges into a batch and the integration branch. Push, the PR and the merge into `{{main}}` are the human's (Push gate). Hand off after 2 merged batches or after a compaction.

- **Integration branch.** Local `pilot/integration`, made from `{{main}}` by `/setup-workflow`. It moves only in the stage worktree. To make it contain `origin/{{main}}` (after a branch landed straight into `{{main}}`, or on `land.mjs`'s `STOP behind-main`), run `node scripts/pilot-land.mjs sync-main --main {{main}} --check-command '{{check}}'` in the main checkout with Bash `timeout: 600000`: it fast-forwards when it can, otherwise merges `origin/{{main}}` on `pilot/stage-sync-main` and runs the regression first.

- **Stage worktree.** `<stage worktree>` is the worktree in `git -C <main checkout> worktree list --porcelain` whose branch is `pilot/integration` or `pilot/stage-*`. `pilot-land.mjs` creates it through Orca (`pilot-stage`) when there is none. The main checkout stays on `{{main}}`: the coordinator only fetches, reads state, and fast-forwards `{{main}}` there.

- **Pool.** Run `node scripts/issue-pool.mjs --integration pilot/integration` [optional: with `--skip-labels <label>,...` when the adapter's Pool section sets `Skip labels: <label>,...`] and pick from its `ready` lines in the printed order, skipping Issues already in an open batch checkpoint. A `ready` Issue with a `PREREQ <n> <text>` line waits until the environment check passes or a gate settles it; do not dispatch it before. Only `claimed` lines are workers in progress; `landed` Issues are already on `pilot/integration` and close with it. [optional: Never pick a whole Spec (an Issue that still needs splitting): open a gate asking the human to run `/to-tickets` on it, and pick its tickets once they are ready.] `needs-triage` Issues, including `blocked` lines that show `needs-triage` or `unlabeled`, are refined per Readiness first; `/triage` cannot be invoked through the Skill tool, so the coordinator reads `~/.claude/skills/triage/SKILL.md` and follows it. A product question becomes a gate and the Issue `ready-for-human`. Give a `NO_CATEGORY <n>` Issue a category the same way, or report it.

- **Batch.** The batch checkpoint is `.scratch/pilot/batch-<key>.md`, created by Dispatch; each Issue's own checkpoint stays in its worktree. Move or park members before staging with `node scripts/pilot-batch.mjs <main checkout> move <key> <n> [--state stop]`, `park <key> <n> --after <m> --reason <text>`, `unpark <n>`, as the Probe's `MOVE` and `UNPARK` lines say.

- **Brief check.** No command: a worker's brief is `/issue-run <n> --worker <checkpoint>` plus the Issue body.

- **Dispatch.** First claim each member in the main checkout with `node scripts/issue-pool.mjs claim <n> --integration pilot/integration`; dispatch only on `CLAIMED <n>` (or `CLAIMED <n> takeover <session>`), and leave a member claimed by another session out of the batch. `LANDED <n> <sha>` means its work is already on `pilot/integration`: leave it out of the batch; once that SHA is on `origin/{{main}}`, close the Issue with the tracker's close command and a comment naming the SHA (the batch that landed it may already have closed it). Then, after this tick's Probe, run in the main checkout with Bash `timeout: 600000` `node scripts/pilot-dispatch.mjs <key> <n>:<slug>... --capacity --repo-cap {{worker cap}}` (members in number order). It prints `DISPATCHED <n> <handle>` or `STOP <n> <cause>` per member, then `REPORTED {{repo}} <running> <total>/<cap>` once it added the dispatched members to the ledger, so a second dispatch in the same tick counts them; when this repo or the machine is full it prints only `STOP capacity repo <total>/<cap>` or `STOP capacity <total>/<cap>` and `RELEASED <n>` for each claim of this session it released: leave the batch for the next tick, and release by hand with `node scripts/gh-tracker.mjs edit <n> --remove-assignee @me` only a member it printed `WARN release <n> edit …` for (on `WARN release <n> claim-check …`, rerun the claim first to see whose claim it is). `STOP <n> worktree-branch <path> <branch>` means an older flow left worktree `issue-<n>` on another branch: rename that branch (create it there first when the worktree is detached) to `issue/<n>-<slug>` and dispatch again; the worker continues from that branch. `STOP orca-unavailable <line>` (no member) means the Orca CLI failed its `worktree list` before anything was created: keep the claims and rerun the same command next tick.

- **Watch.** While workers run, start `node scripts/pilot-watch.mjs --batch <key>` in the background (one `--batch` per open batch; all are watched): result lines already on screen at start do not count; a new `DONE <n> <sha>` or `STOP <n> <cause>` from a running member prints `RESULT <key> <handle> <line>`, an exited terminal with no new one prints `EXITED <key> <handle>` (stuck), and it exits, waking the coordinator to run the Probe and start it again while members still run. It shares the Probe's result-line parsing (indented lines, TUI prompt rows, backslashes in the screen JSON); do not write your own watcher. To read a worker's screen: `node scripts/pilot-probe.mjs --tail <handle>` (the last 40 lines; `--lines <n>` changes it). Stuck-after is the default 90 minutes; the watcher does not judge it, so still schedule the next wakeup.

- **Idle wait.** Nothing in flight and the idle streak at the `issue-pilot` Report and sleep threshold: start `node scripts/pilot-idle-wait.mjs <main checkout> --main {{main}}` in the background instead of a `ScheduleWakeup`. It reads the probe (read-only), `.scratch/pilot/gates.md`, and `pilot/integration`'s HEAD every 300 seconds and exits on the first change (`WAKE probe <new line>`, `WAKE gates …`, `WAKE integration <old> <new>`) or after 3600 seconds (`IDLE_TIMEOUT`); either exit is the next wake. `ERROR probe …` (exit 1, three failed probe rounds in a row): schedule 1800 seconds and report the line.

- **Agent rows.** The member rows of the batch checkpoint; subagents a worker spawns are not recorded.

- **Probe.** Each Reconcile, after Sessions, run in the main checkout `node scripts/pilot-probe.mjs <main checkout> --apply --status --capacity {{repo}} --main {{main}}` [optional: plus the adapter's Pool section's `--skip-labels <label>,...`]. Act on its lines as `PILOT-STORE.md` and the `issue-pilot` skill describe: `WORKER` results are written back by `--apply`; `STAGEABLE <key>` goes to Stage; `HELD <n> G<k>` waits for that gate (stage nothing in that batch); `MOVE`, `PARKED`, `UNPARK` go to Batch (a `MOVE` that lists `done` members moves those out, without `--state stop`); `UNBLOCKED <key> <n>` means a stopped member's blockers are all closed, so redispatch it fresh when its stop was waiting on them, ahead of the `PARKED` handling for that member; `IN_MAIN <key>` goes to Close; `RESUME_PUSH` and `NOT_IN_MAIN` go to the Push gate; `OVERLAP` lines are reported, not filtered; `REQUEST`, `GATE` and `HOLD` are handled before Pick; `POOL_READY` means run the Pool command; `POOL_TRIAGE` means refine those `needs-triage` Issues per Pool, which makes the tick not idle; `HUMAN_NO_GATE <n> <summary>` is a `ready-for-human` Issue no open gate asks about: open one with the Gates command (`--issue #<n>`, the question from the summary, the most conservative option as default) and ask it in this tick's Report with `AskUserQuestion`; `ADAPTER_AHEAD` lines end with ` ｜ ` and the command that prints the integration branch's copy, read instead of a diff; `SCRIPT_AHEAD <path> run-in <stage worktree>` (printed with `ADAPTER_AHEAD`) names a `scripts/` file that adapter names and the main checkout lacks or holds an older copy of: run it as `<stage worktree>/<path>` from the main checkout this tick, since an old copy can fail silently (a watcher reading only the last `--batch`); `SCRIPT_AHEAD <path> sync-main` means the stage worktree lacks it too, so run Integration branch's `sync-main` first; `HOOK_BEHIND <path>` names a script a `.claude/settings.json` hook runs whose main-checkout copy is behind `pilot/integration`: when that hook blocks or fails, reproduce with `git -C <main checkout> show pilot/integration:<path>` before reporting it, and drop it when that version passes; `HUMAN_LANDED <n> <sha>` is a `ready-for-human` Issue whose work already landed on `pilot/integration`: read its last comment and that commit before asking the human, never ask them to run a step that already ran, and name the SHA in this tick's Report (and in the gate's question when `HUMAN_NO_GATE` lists it too); `BLOCKER_OPEN_SCOPE <n> #<m> <label>` means blocker `#m` landed on `pilot/integration` but still carries `<label>` and is unassigned or had its body edited after its last assignment, so `#n` is not dispatchable (when `#m` is assigned and its edit history shows the last edit was the coordinator's own, such as a `COUNTERPART_BARE` rewrite before Close, ignore the line and open nothing): only `#m`'s old scope is done; when `#m` is assigned it closes with its batch, so open a new Issue for the rewritten scope and make `#n` blocked by it; `SCOPE_CHANGED <key> <n> <edited at>` means a `done` member's Issue body was edited after its worker started: read what changed before Stage; when the edit history shows the last edit was the coordinator's own (such as a `COUNTERPART_BARE` rewrite), ignore the line and open nothing; otherwise open a new Issue for scope the candidate lacks, blocked by this one, and add it as a blocker of the Issues waiting on this one; neither line blocks Stage. When it exits non-zero, run the Bare guard by hand, report its stderr, and do not stage or merge this tick.

- **Hold flag.** `pilot-land.mjs` checks `.scratch/pilot/hold` right before Integrate and prints `STOP hold`.

- **Stage, regression, integrate.** One command in the main checkout with Bash `timeout: 600000`: `node scripts/pilot-land.mjs <key> --main {{main}} --check-command '{{check}}'`. It stages every `done` member by number on `pilot/stage-<key>`, runs the check entry at the staged SHA (log in `.scratch/pilot/reg-<key>.log`), checks the hold, and fast-forwards `pilot/integration`, printing `MERGED <key> <sha>`. [optional, without a resolver module: It resolves only `docs/agents/workflow-templates.json` conflicts and stops on any other with `STOP conflict …`; redispatch that member fresh with `node scripts/pilot-dispatch.mjs <key> --fresh <n>:<slug>` or open a gate.] `STOP load` reruns next tick; `STOP regression <exit>`: read the log, fix, rerun the same command.

- **Push gate.** Once `pilot/integration`'s tip is the last SHA that passed regression: run `node scripts/pilot-pr-body.mjs <main checkout> --out .scratch/pilot/pr-body.md` from the main checkout (it hands over to the stage worktree's copy, the content being pushed, so there is no path to work out) and continue only on `PR_BODY …`. Then hand the human, as a gate, the command `! node scripts/land.mjs pilot/integration --keep-branch --main {{main}} --check-command '{{check}}' --title '<batch keys and title>' --body-file .scratch/pilot/pr-body.md`, run in the main checkout. Do not run `land.mjs` yourself. When the human reports `LANDED <pr> <merge sha>`, rerun the Sessions command and go to Close; on `STOP behind-main` run the Integration branch's `sync-main` and start the Push gate again; any other `STOP` stays with the human.

- **Close.** Once the merge is on `origin/{{main}}`, run in the main checkout `node scripts/pilot-close.mjs <key> <pr> <merge sha> --repo {{owner/repo}}`. It posts the evidence comment, closes each `done` member, closes its terminal, removes its worktree and local and remote branch, and closes a parent whose sub-issues are all done, skipping steps already done, so it can be rerun; the last line is `CLOSED <key>`. When fast-forwarding the main checkout would remove a tracked file under a path the `Protected paths:` line of `docs/agents/issue-run.md` declares, it prints `STOP <key> main` and changes nothing: hand the listed files to the human, and rerun once they are moved aside. It is not in the allow list: when the permission prompt or auto mode blocks it, hand the same command to the human.

- **Handoff.** When Defaults says so, record the reason with Decisions, stop background work, and run in the main checkout with Bash `timeout: 600000` `node scripts/pilot-handoff.mjs --session "$CLAUDE_CODE_SESSION_ID" --pid "$CLAUDE_PID" --reason <reason>` (no `--held-check`: add one only when the repo has an "integration merge in progress" check). Only `HANDED_OFF <handle> [name <name>]` completes it (`name` is the new coordinator's session name for SendMessage, absent when its coordinator line has none); on `STOP <reason>` keep coordinating.

- **Project tick hooks.** None.

- **Retro collect.** None: `/retro` implements its own adopted items in this repo.

- **Retro trigger.** None: the human types `/retro-collect`.
