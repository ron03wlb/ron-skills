# issue-run adapter template

Copy into a repo as `docs/agents/issue-run.md` and fill each section with commands that exist in that repo. Point at the repo's own docs and scripts rather than restating them; leave a section out to take its default.

Keep `docs/agents/issue-run.md` and the Pilot section's first file (`docs/agents/pilot.md`) as **required cores** of at most 14000 bytes each: every worker reads the first whole, every coordinator the second, and each pays again after compaction. A section or entry that only one step or one case needs (one script's result-line handling, a step's full command and outputs, a rare case) moves to a split file in the same directory, at most 58000 bytes so one Read holds it; the core keeps a one-line pointer of the same name saying when to read it, and the reader fetches only that entry with `node scripts/adapter-line.mjs '<entry>'`, which prints a `- **<entry>.**` entry, or a heading's section, from the files `scripts/adapter-size-budget.json` lists. What stays in a core is what every run or every tick needs before it acts: the sections a worker always passes through, and the Pilot entries that define paths, branches, and batches. The check entry runs `node scripts/check-adapter-size.mjs` against that table; give each split file its 58000 line there.

## Platforms

The platforms the team runs this repo's workflow on, as `/setup-workflow` detected them (each teammate's platform is added when they run it): any of `macOS`, `WSL2`, `Linux` (for example `macOS, WSL2`). Native Windows is not supported; use WSL2. Every command this adapter names must run on each listed platform, and a workaround for one platform says which.
Default: the platform `/setup-workflow` ran on.

## Tracker

How to read an Issue with comments and its blocking relations, and the write rules for bodies and comments. Name the tracker host `/setup-workflow`'s Host step detected (`github`, `gitlab` or `local`, with its hostname) and take each command from the `gh`/`glab` table in [HOSTS.md](../setup-workflow/HOSTS.md); `glab` flags differ (`glab issue note` takes only `-m`, no `--body-file`).
Default: `docs/agents/issue-tracker.md` from `/setup-matt-pocock-skills`.
On a GitHub tracker at L3, also write the tracker project's URL (`https://<host>/<owner>/<repo>`) here as the section's only GitHub project URL: the setup-workflow `gh-tracker.mjs` copy reads its write target from it, and exits 2 without one.

## Delivery

How a candidate reaches the shared branch on the code host: the code host the Host step detected (`github` or `gitlab`, with its hostname; it may differ from the tracker host), its CLI, the PR or MR create, read, wait-for-CI and merge commands from [HOSTS.md](../setup-workflow/HOSTS.md), and where CI is configured (`.github/workflows/` or `.gitlab-ci.yml`).
Name both **CI runners** (CI 執行端) and when to switch. Remote (GitHub Actions, GitLab pipeline) is the default. Local applies only when the remote did not start (billing, no runner: `land.mjs` prints `STOP ci-not-started`): run the `## Checks` entry on the tip SHA to merge, with a clean tree, and comment the SHA and its result line on the PR; on GitHub that is `node scripts/land.mjs <branch> --local-checks <sha> --check-command '<check entry>'`. A remote run that started and failed never falls back to local. With the setup-workflow `land.mjs` (GitHub only), the delivery command is `node scripts/land.mjs <branch> --body-file <file>`.
Default: none when the code host is `local` (no remote): there is no PR, MR or remote CI, the local runner is the only one, and the human merges locally.
**Protected paths** (optional): tracked paths whose main-checkout working copy must survive a merge that deletes them, such as private files only that checkout has. Declare them on one line of this adapter that starts with `Protected paths:`, each path in backticks and literal (not a pathspec), for example ``Protected paths: `private` `notes/local.md` ``. Before fast-forwarding the main checkout, the setup-workflow `land.mjs` and `pilot-close.mjs` read that line from the main checkout's adapter and refuse when the fast-forward would delete, rename, or change the type of a tracked file under one of them: `land.mjs` leaves the checkout behind with `WARN main-not-synced 快轉會刪掉被保護的路徑 <files>…` and still prints `LANDED` (the PR is merged), and `pilot-close.mjs` prints `STOP <key> main`. The human moves those files aside, then fast-forwards by hand or reruns the Close. A `Protected paths:` line with no backticked path is refused the same way; `pilot-close.mjs --protect-path <path>` adds paths for one run. Default: none, and both scripts fast-forward as before.

## Readiness

The ready state, a preflight command that must exit 0, and the command that refines a not-ready Issue.
Default: the `ready-for-agent` label from `docs/agents/triage-labels.md`; no preflight; refine with `/triage`.

## Claim

The command that marks a ticket in progress.
Default: none.

## Worktrees and checkpoint

Where each ticket's worktree and branch come from, the run's integration branch, and the checkpoint path and format.
Default: `implement-spec`'s integration branch and per-ticket worktrees; checkpoint at `.scratch/issue-run-<first-ref>/state.md` with one row per ticket (ticket, blockers, branch, worktree, state, merged SHA).

## Checks

The commands per kind of change, and how to attribute a failure.
Default: typecheck and the touched test files while building; the full suite once on the run's branch; attribute by rerunning on the base.
When the check entry can run past 90 seconds, say how to run it so it is not moved to the background (in Claude Code, Bash `timeout: 600000`); any duration written here is measured, not estimated.
Also name the baseline suites a behavior-preserving refactor runs green before its first change, and the history command for reopened or regressed Issues (tracker, git, transcripts).

## Review

The review command and its output, and what the skill's [Review rules](SKILL.md#review-rules) need: where non-blocking findings go as follow-ups, the files pinned by hash, the safety-fact classes, the high-risk classes with the scenario driver and verifier runner, and the cross-model command.
Default: the `code-review` skill on the run's branch; follow-ups in the Issue's report; no pinned files; the default safety-fact classes; no high-risk classes.

## Candidate and acceptance

What counts as the candidate (a squashed commit, the branch tip) and the acceptance run pinned to its SHA.
Default: the run's branch tip; acceptance is the full suite on that SHA.

## Evidence and closing

Where evidence is posted, and the human's next actions.
Default: a comment on each Issue; the human pushes and closes.

## Gated tickets

How to recognise a gated ticket (a body marker, a label), its procedure up to the handoff state, where its evidence goes, the human's execution and closing steps, and the discovery rule when a code ticket turns out to need one.
Default: no gated tickets; any need for one found mid-run is a stop.

## Stops

Repo-specific stop conditions on top of the skill's.

## Tab state (分頁狀態)

What this session's Orca tab title says, when it changes, and the commands that change it. The rules below are the default; a project writes here only what differs. In an Orca chat (`ORCA_STRUCTURED_SESSION` and `ORCA_AGENT_SESSION_ID` set, no `ORCA_TERMINAL_HANDLE`) `tab-state.mjs` and its hook rename the chat with `orca chat rename` instead; a chat has no close command, so `/retro-collect` never closes it. Without Orca (neither): none, and `tab-state.mjs` with valid arguments exits 0 without output.

- **Format.** Every title starts with a state prefix `<state>｜` (分頁狀態), one of `處理中` (still working, including waiting on the user's answer or approval), `待 Retro` (the work is done; waiting for the user to run `/retro` in this tab), or `待關閉` (`/retro` has finished; `/retro-collect` or the user closes the tab). Issue work is `<state>｜<issue> <topic>｜<stage>｜<action>`, for example `處理中｜#21 雙池採集｜實作｜補 TPEx 舊版格式`, then `待 Retro｜#21 雙池採集｜已合入 PR #130` and `待關閉｜#21 雙池採集`. `<issue>` keeps the tracker's own form (`#21` on GitHub, `ENG-123` on Linear) and names only the Issue being worked now; `<topic>` is a stable short name for it; `<stage>` is one of `調查 / 規劃 / 實作 / 驗證 / 修正 / 收尾` and appears only while `處理中`; `<action>` stays within about 12 characters. Other work, a pilot coordinator included, is `<state>｜[<category>] <topic>`, with `<category>` one of `設定 / 研究 / 討論 / 維運 / 雜項` (`處理中｜[維運] issue-pilot coordinator`). Append ` ⏸` only while `處理中` and blocked on the user's approval of an action; an ordinary end of turn gets no marker. Write the topic and action in the language the repo uses for user-visible messages, keeping file, function, and command names verbatim. The state, stage, and category words stay as listed in any language: the hook matches the state prefix literally, and fixed stage and category words keep titles comparable across sessions.
- **When to rename.** At session start, once the Issue or topic is known; on each stage or state change; on switching Issues; and on entering or leaving an approval wait. Set the whole title with `node scripts/tab-state.mjs <state> --topic "<everything after the prefix>"`: at session start (`處理中`) because the recorded title may still be the previous session's on the same handle, later for a new stage, action, Issue, or ` ⏸`, and on leaving `處理中` to keep a segment besides the topic (`待 Retro --topic "#21 雙池採集｜已合入 PR #130"`). `node scripts/tab-state.mjs <state>` without `--topic` replaces only the prefix when `<state>` is `處理中`; for any other state it keeps just `<state>｜<topic>`, dropping every `｜` segment after the topic and the ` ⏸`. Every switch the hook makes itself replaces only the prefix and keeps the rest of the title, stage and action included, so a title the hook moved to `待 Retro` can still carry them; the hook checks only the prefix, so such a title passes until the session resets it.
- **Worktree name.** When creating or entering an Issue worktree, give Orca the stable part only: `orca worktree set --worktree path:<path> --display-name "<issue> <topic>" --issue <n>` (Linear: `--linear-issue <id>`; GitLab: `--gitlab-issue <n>`).
- **State switches.** With the setup-workflow `tab-state.mjs` and `claude-hook-tab-state.mjs`: `待 Retro` once the delivery is merged (`land.mjs` prints `LANDED`; not the pilot coordinator's `--keep-branch` landing), when a pilot worker writes its `DONE` result line (before the coordinator merges it), once a coordinator's handoff completes (`HANDED_OFF`), or, for other work, once the user confirms the topic is done; opening a PR is not enough. A session that only answered questions (clean worktree, no commit) instead goes straight to `待關閉` once the user confirms, without `/retro` (#399). `待關閉` when `/retro` finishes: its adopted items are merged or filed, or its candidates went to the collect flow; `/retro`'s last step switches it. The hook makes the detectable switches (`LANDED`, `HANDED_OFF`, `DONE`) itself and, on `Stop`, exits 2 when the title has no valid prefix. A project adds, overrides, or disables hook triggers in `docs/agents/tab-state.json` (format in the hook's header).

## Pool

The tracker pool every level reads: `scripts/issue-pool.mjs`, which `/setup-workflow` copies at L1. `/issue-run --pool [<N>]` (under `/loop`, self-paced) claims and runs its `ready` lines one at a time in one session, `/issue-queue` lists its buckets, and at L3 the Pilot Pool and Dispatch lines name it too. It reads GitHub and GitLab trackers only; with a `local` Markdown tracker there is no pool, so `--pool` and `/issue-queue` stop. Given `--integration <branch>` (at L3 the Pilot section's integration branch), the pool and `claim` also see work already on that branch: an assigned Issue whose result is `DONE` or whose commits are on the branch is listed as `landed`, not `claimed` or `stale`, and counts as no worker; a `blocked` line marks such a blocker `(landed <branch>)`; and `claim <n>` prints `LANDED <n> <sha>` and claims nothing, so the Issue goes straight to closing once the branch reaches main. A `PREREQ <n> <text>` line marks a `ready` Issue whose operator prerequisite is not `無`: check the environment or open a gate before dispatching it.
- **Claim timeout.** The hours after which an assigned Issue with no new comment or assignment is listed as `stale` instead of `claimed`. A stale claim is never released automatically: `/issue-queue` shows it, and releasing it is the human's call. Write `Claim timeout: <h> hours` here to change it; `/issue-queue` then passes `--stale-hours <h>` to `issue-pool.mjs`; a Pilot section that names its own pool query adds the same flag there. The other claim windows are fixed in the script: on an assigned Issue, another session's latest claim comment blocks a new claim at any age; on an unassigned one, it blocks only within 5 minutes of being written (a claim still in flight). An assigned Issue whose latest claim comment is not from an assignee always blocks. A blocking claim is taken over in two cases only: a pilot coordinator that succeeded a handed-off coordinator on this machine (per `.scratch/pilot/sessions.md`) takes over that coordinator's claims, and `--take-stale`, for a flow that waits for no one (such as a Retro collect entry's claim), takes over one whose session on this machine has not written its transcript for an hour.
- **Categories.** The category labels an Issue must carry for the pool not to report it as `NO_CATEGORY` (the bucket names are fixed in the script, apart from the skip-label buckets below). Write `Categories: <label>,...` here when the triage categories differ; `/issue-queue` then passes `--categories <label>,...`, and a Pilot section that names its own pool query adds the same flag there.
- **Skip labels.** Labels on Issues that are never implemented, such as a recurring report, which the pool treats like `retro-candidates`: such an Issue gets a bucket named after the label, listed right after `retro-candidates`, so it never reaches `ready` or `needs-triage`, is never reported as `NO_CATEGORY`, and the Pilot Probe neither lists it in `POOL_READY` or `POOL_TRIAGE` nor counts it as a newer Issue for a "do this last" Issue. `retro-candidates` and `parent` are built in; write `Skip labels: <label>,...` here for the others; `/issue-queue` and `/issue-run --pool` then pass `--skip-labels <label>,...`, and a Pilot section adds the same flag to the `issue-pool.mjs` command in its **Pool** entry and to the `pilot-probe.mjs` command in its **Probe** entry.

Default: claim timeout 24 hours; categories `bug`, `enhancement`; no skip labels beyond the built-in ones.

## Issue queue

What `/issue-queue` reads beyond the Tracker, Readiness, Pool, and Pilot sections: `Parent hints: off` turns off its parent hints and the per-parent review. Default: on. Its worker cap is the Pilot section's; with no Pilot section (L1, L2) or no cap named there, the cap is `不限`.

## Detect

The names `/setup-workflow`'s `detect.mjs` reads when this repo's integration branch or stage commits do not follow its fixed rules (a branch named `integration`, with or without a prefix; a subject containing `pilot/stage-` or `stage batch-`). Each is one line of its own in this section, written in this file and not in a file it points to: start a line with `Integration branch:` followed by the branch name, and a line with `Stage commit:` followed by a JavaScript regex matched against commit subjects (for example `feature/ron/#24846` and `^merge: 整合 `). A leading `- ` and backticks around the value are optional, any other markup (bold, `* `) is not read as a declaration, and a `#` is part of the value. A declaration replaces the fixed rule for that item only: the branch counts when it exists locally or on `origin`, and it becomes the base for `IN_FLIGHT`; a subject scan keeps its range (90 days, 300 commits). A branch that does not exist or a regex that does not compile makes that signal `missing`, with the declaration in its evidence.
Default: no declarations; the fixed rules apply. A declaration changes what is detected, not what is installed: a new resident pilot still needs a GitHub tracker. The `claude-hook-main-checkout` copy also reads `Integration branch` as the only branch the main checkout may switch back to.

## Pilot

A filled-in skeleton for every entry below, wired to the setup-workflow template scripts, is [PILOT-TEMPLATE.md](PILOT-TEMPLATE.md): copy it to `docs/agents/pilot.md` and [PILOT-ROUND-TEMPLATE.md](PILOT-ROUND-TEMPLATE.md), which holds the longest step entries in full, to `docs/agents/pilot-round.md`, and link both from this section, `pilot.md` first; when `pilot.md` still outgrows the core budget above, move more whole step entries to `pilot-round.md` and leave their pointers. What `/issue-pilot` needs on top of the sections above: pool query, worker cap and batch size, dispatch, watch and probe commands, stage, regression, integrate, close, and handoff. The files under `.scratch/pilot/`, batch checkpoints included, follow [PILOT-STORE.md](../issue-pilot/PILOT-STORE.md): write only the values that differ per project here, never a file format. Besides those, name:

- **Hold flag.** Which landing commands check `.scratch/pilot/hold` right before they merge.
- **Stage, regression, integrate.** The command that merges a batch's `done` members onto a stage branch, runs the regression at the staged SHA, and fast-forwards the integration branch, plus which conflicts it may resolve itself. Default: with the setup-workflow templates, one command, `node scripts/pilot-land.mjs <key> --check-command '<check entry>'` (`--check-command` defaults to `bin/check`; add `--integration <branch>` when the integration branch is not `pilot/integration`, and the same flags on the Push gate's `pilot-land.mjs sync-main`, with `--main <branch>` when the main branch is not `main`); its result lines are in [Canonical scripts](../issue-pilot/PILOT-STORE.md#canonical-scripts). On its own it resolves only a `docs/agents/workflow-templates.json` conflict (by recomputing the copies) and stops on every other conflict with `STOP conflict`. A project that resolves more (ron-skills: `- **<name>.**` entries, table rows, its flow-site stamps) passes `--resolver <module>`, a path from the repo root to an ES module that may export `resolveFile(tree, path, kinds)` (the merged text of a conflicted file, adding the technique's name to the `kinds` Set, or `undefined`), `conflictKind(tree, path)` (the kind for `STOP conflict`, or `undefined` for the default `code`/`other`), `KINDS` (the order of technique names in `RESOLVED`), and `STAMP_FILES` with `restamp(tree, files)` (project stamp files, recomputed and `git add`ed after every other file; `false` when it cannot).
- **Close.** The command that closes each `done` member once the batch's merge is on the main branch: evidence comment, counterpart handoff, close, terminal, worktree, branch, remote branch, parent. Default: with the setup-workflow templates, `node scripts/pilot-close.mjs <key> <pr> <merge sha> --repo [<host>/]<owner>/<repo>` (the project URL of the Tracker section; `--main <branch>` when it is not `main`), which writes through `scripts/gh-tracker.mjs` beside it when present and skips each step already done, so it can be rerun.
- **Push gate.** What the coordinator runs once the integration branch tip is the last SHA that passed regression: the PR body command, then push, open the PR or MR, and merge, or hand those to the human. Default: hand the push to the human; with the setup-workflow templates, `pilot-pr-body` writes the PR body from the merged batch checkpoints ([Canonical scripts](../issue-pilot/PILOT-STORE.md#canonical-scripts)).
- **Brief check.** A command that refuses a brief missing goal, scope, acceptance, verify, timebox, forbidden, report, or the standing orders path. Default: with the setup-workflow templates, `node scripts/brief-check.mjs <brief> [--batch <key>] [--iid <n>]` (`BRIEF_OK` exit 0, `BRIEF_REJECTED … missing=<fields>` exit 1); `--paths <issue body> [--root <repo>]` prints `BRIEF_PATH_MISSING <path>` for each backticked repo path that does not exist (advisory, exit 0; run it before labelling ready); `--skeleton` prints a passing labelled skeleton to fill in.
- **Triage brief.** Optional: the prompt template for a subagent that refines `needs-triage` Issues at the `issue-pilot` skill's Pick, with this repo's facts filled in once (how to bound a command that may hang, the tracker write command, triage traps seen before) and `<…>` placeholders the coordinator substitutes per tick (the main checkout, and the stage worktree when the probe reports the adapter ahead of the main checkout). Default: the coordinator writes that prompt itself; with the setup-workflow templates, [PILOT-ROUND-TEMPLATE.md](PILOT-ROUND-TEMPLATE.md)'s entry.
- **Watch.** The background command the coordinator starts while workers run, which exits on the first new `DONE <n> <sha>` or `STOP <n> <cause>` (result lines already on screen at start do not count) or an exited terminal, naming the batch, and the read-only command that prints a worker's screen. It must share the probe's result-line parsing (indented lines, TUI prompt rows, backslashes in the screen JSON) and watch every open batch. Default: none; the coordinator reads each worker's screen once per wakeup. With the setup-workflow templates: `node scripts/pilot-watch.mjs --batch <key>` (repeatable) and `node scripts/pilot-probe.mjs --tail <handle>`.
- **Idle wait.** Optional: the background command the coordinator starts instead of a `ScheduleWakeup` once its idle streak reaches the `issue-pilot` skill's Report and sleep threshold, which exits 0 on the first change in the probe's output (a line the start did not print), the gate file, or the integration branch's HEAD, or at its time cap, and non-zero on an error (the coordinator then schedules 1800 seconds). Default: none, and an idle coordinator sleeps 3600 seconds; with the setup-workflow templates, `node scripts/pilot-idle-wait.mjs <main checkout>`.
- **Agent rows.** Where the checkpoint records each spawned agent (parent, handle, start time, stuck-after), and which probe line reports a parent still waiting past its child's stuck-after.
- **Sessions.** The register command: writes `.scratch/pilot/coordinator` and appends the session's start line to `.scratch/pilot/sessions.md`. Default: the coordinator writes both itself; with the setup-workflow templates, `node scripts/pilot-register.mjs <checkout> --name <session name> --loop yes|no <source>...`.
- **Sources.** The rule files the coordinator re-reads when they change: the source list `pilot-sources` hashes (`node scripts/pilot-sources.mjs <checkout> --record <source>...`), the same list passed to the register command. Default: `AGENTS.md`, this adapter and any file its Pilot section points to, and the `issue-pilot` skill.
- **Decisions, requests, hold.** The commands that write `decisions.md`, mark `requests.md` lines, and set or clear `hold`. Default: the coordinator writes them by hand per [PILOT-STORE.md](../issue-pilot/PILOT-STORE.md); with the setup-workflow templates, `pilot-decision`, `pilot-request`, and `pilot-hold` ([Canonical scripts](../issue-pilot/PILOT-STORE.md#canonical-scripts)).
- **Gates.** The commands that open, resolve, and list `gates.md` entries. Default: the coordinator writes them by hand per [PILOT-STORE.md](../issue-pilot/PILOT-STORE.md); with the setup-workflow templates, `pilot-gate` ([Canonical scripts](../issue-pilot/PILOT-STORE.md#canonical-scripts)).
- **Coordinator checkout.** The checkout the coordinator runs in and keeps `.scratch/pilot/` under, for a project whose coordinator does not live in the main checkout. Default: the repo's main checkout.
- **Adapter ref.** Optional: the ref the coordinator reads this adapter from, as the entry's first backticked value, when the local integration branch can trail it (another machine pushes it), for example `origin/develop`. A ref that starts with a remote's name is fetched before it is read, and the setup-workflow `pilot-probe` fetches and compares it for `ADAPTER_AHEAD`. Land the entry on the main branch: both read it from the main checkout's copy, so an entry only on the integration branch is not seen. Default: the local integration branch.
- **Coordinator model.** Optional: the model the coordinator session that a handoff opens starts with, declared once as one line `Coordinator model: <model id>` (the value may sit in backticks; a `- **Coordinator model.** ` entry holding that line is fine) in this Pilot section or a file it links. The setup-workflow `pilot-handoff` reads it from the main checkout's copy and opens the new tab with `claude --model <model id>` instead of bare `claude`. Only that new tab takes it: workers, a `--to` handoff to a session already open, and every other session `orca-session-split` opens keep bare `claude` and the global model. A value with characters other than letters, digits, `.`, `_`, and `-`, or two different values, prints `WARN coordinator-model-invalid <value>` or `WARN coordinator-model-conflict <values>` on stderr and the handoff goes on with bare `claude`. Default: none; the new coordinator runs bare `claude`.
- **Decisions command.** Optional: the read-only command that lists what awaits the human (open gates, undecided items). `/issue-pilot` runs it for Report and Notify, and when the human asks what awaits them.
- **Project tick hooks.** Scripts the coordinator runs each tick after Drain and before Pick, in order, from the coordinator checkout, for project checks ron-skills does not model (a daily collection dispatch, a quota check). Exit 0 continues; any other exit opens a gate with the script's output and skips Pick and Dispatch for that tick. Default: none; the step is skipped.
- **Env sync.** Optional: the command that prepares a new worktree's environment (installs dependencies, for example `uv sync --quiet` or `npm ci`) before its worker starts, for a project whose checks fail in a worktree nobody synced. Declare it once, as one line `Env sync: ` followed by the command in backticks (a `- ` list item is fine) or as an entry `- **Env sync.** ` followed by the backticked command, in this Pilot section or a file it links such as `docs/agents/pilot.md`. The setup-workflow `pilot-dispatch` runs it with `sh -c` inside each member's worktree once the worktree exists and before it opens the terminal, on a redispatch into an existing worktree too (before it closes that worktree's old terminals), so the command must be safe to rerun; a non-zero exit prints `STOP sync <n> exit <code>` with the command's output on stderr, opens no terminal, and records the row as `stop`. A declaration without a backticked command, or declared twice, exits 2 before anything is touched. Default: none; worktrees start without a sync.
- **Retro collect.** What `/retro-collect` needs to turn the open `retro-candidates` Issues into one retro unit: the checkout it runs from, the command that claims each collected Issue, the retro worktree's name, branch, and target branch, the checks, and how it merges and pushes. `/retro` runs in collect mode only when this entry exists. A project that keeps its candidates outside the tracker also declares, in this entry, a `Roster command:` (what `/retro-collect` lists and reads, in place of the `retro-candidates` Issues and the claim), a `Collect command:` (run by `/retro` with `<session>` replaced by the session id; its first line is `COLLECT <file>`, write the candidates there and implement nothing, or `NORMAL`, this session implements as usual), and a `Close command:` (what `/retro-collect` runs after landing, in place of its comments, closes, and tab closing); all three or none, and the entry states the roster's output, the candidate file's format, and how the close command's placeholders are filled. A declared roster that a **Retro trigger** entry counts also declares `Roster due: <TOKEN>[,<TOKEN>…]`: the roster output lines whose first word is one of them are the uncollected retros, each aged by the first ISO 8601 time on its line, else the modification time of the first existing file the line names, else counted without an age. Without them, candidates go to the tracker (ADR 0003). `/retro-collect` writes its report's owner-veto part (each candidate's outcome and the `retro` Issues it opened) to `.scratch/retro/reports/<YYYY-MM-DD>-<key>.md` in the checkout this entry names, so a project reads its own collections there. Default: none; `/retro-collect` stops and says so.
- **Retro trigger.** Optional: turns on the automatic collection at the `issue-pilot` skill's Retro trigger step, which runs every tick whether or not **Project tick hooks** names any script, and names its due command. ## Permissions

The `.claude/settings.json` allow rules an unattended `/issue-pilot` tick needs, and where git runs.
Default: none; every git write prompts.

Tracker writes and the push decision use the setup-workflow templates (its `gh-tracker.mjs` row): allow `Bash(node scripts/gh-tracker.mjs:*)` for the coordinator's comments, labels and closes, and allow `Bash(node scripts/land.mjs:*)` and `Bash(node scripts/pilot-close.mjs:*)` only when the human answered yes to `/setup-workflow`'s push question; `node scripts/check-coordinator-permissions.mjs [--push]` in the check entry keeps the rules matching that answer.

When the pilot runs git in worktrees other than its cwd, do not write `Bash(git -C * <subcommand>)`. A `*` before the subcommand also matches extra git options, so `git -C <path> -c core.sshCommand=<cmd> fetch origin` passes, and Claude Code warns "allows any option at its `*`" on every session start; anchoring the path (`git -C /root/feature-ron-* …`) still warns. Keep each `*` at the end of a rule, after the arguments git parses as options:

1. Copy [templates/pilot_git.py](templates/pilot_git.py) to the repo's `scripts/pilot_git.py` and set its two constants (branch prefix, base branch). The main checkout and worktree root are not constants: the main checkout is `PILOT_GIT_MAIN_CHECKOUT`, else the parent of `git rev-parse --path-format=absolute --git-common-dir` run in the script's directory (the same answer from the main checkout or any linked worktree); the worktree root is `PILOT_GIT_WORKTREE_ROOT`, else `~/orca/workspaces/<main checkout directory name>`. Set either variable only when the detected path is wrong on that machine. It runs `git -C` itself after checking the target and arguments: the main checkout gets only `fetch`, `rev`, `log`; writes (`sync`, `stage`, `push`) only go to `<worktree root>/<prefix>*`; no argument may start with `-`; `push` only targets `<prefix>*` branches.
2. Allow `Bash(python3 scripts/pilot_git.py:*)` and remove any `Bash(git -C …)` rule.
3. Write the adapter's git steps as `python3 scripts/pilot_git.py <subcommand> <checkout> …`, and add a test that every adapter command has a matching rule and no adapter step calls `git -C` directly (Growth: `tests/test_pilot_permissions.py`).
4. Start a new session and confirm no permission warning is printed.

A repo that already wraps its git steps in delivery scripts (spay2: `node scripts/batch-land.mjs`, `bash scripts/push-pinned.sh feature/ron/*`) needs no `pilot_git.py`; the same rule applies to those scripts' allow rules.
