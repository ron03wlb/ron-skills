# Pilot step entries: {{repo}}

The full step entries that do not fit in `pilot.md`'s 14000-byte core. Each has a same-named pointer there saying which step reads it; fetch one with `node scripts/adapter-line.mjs '<entry>'` instead of reading this file whole.

- **Pool.** Run `node scripts/issue-pool.mjs --integration pilot/integration` [optional: with `--skip-labels <label>,...` when the adapter's Pool section sets `Skip labels: <label>,...`] and pick from its `ready` lines in the printed order, skipping Issues already in an open batch checkpoint. A `ready` Issue with a `PREREQ <n> <text>` line waits until the environment check passes or a gate settles it; do not dispatch it before. Only `claimed` lines are workers in progress; `landed` Issues are already on `pilot/integration` and close with it. [optional: Never pick a whole Spec (an Issue that still needs splitting): open a gate asking the human to run `/to-tickets` on it, and pick its tickets once they are ready.] `needs-triage` Issues, including `blocked` lines that show `needs-triage` or `unlabeled`, are refined per Readiness first; `/triage` cannot be invoked through the Skill tool, so the coordinator reads `~/.claude/skills/triage/SKILL.md` and follows it. A product question becomes a gate and the Issue `ready-for-human`. Give a `NO_CATEGORY <n>` Issue a category the same way, or report it.

- **Triage brief.** When a subagent refines `needs-triage` Issues at Pick (or splits one), its prompt is the indented lines below with `<n>...`, `<main checkout>`, `<adapter checkout>` and `<stage worktree>` substituted (the other `<…>` are the subagent's to fill), plus the Issue numbers and what this tick learned; do not restate the repo facts from memory (investing#379: five hand-written triage briefs in one session each repeated the paths, and subagents still hit the write guard and an outdated script none of them named).
  Refine Issue(s) <n>... in {{owner/repo}}: `/triage` cannot be invoked as a skill, so read `~/.claude/skills/triage/SKILL.md` and its `AGENT-BRIEF.md` and follow them; open every comment with the AI disclaimer, give one category label and one state label, and mark `ready-for-agent` only when every input is reachable and scope and acceptance are clear, leaving an agent brief.
  Run every command as `cd <main checkout> && <command>`. Read the adapter in `<adapter checkout>` (the main checkout, or `<stage worktree>` on a tick whose Probe printed `ADAPTER_AHEAD`), and run a script the Probe listed as `SCRIPT_AHEAD` as `node <stage worktree>/<path>`.
  Bound a command that may hang with {{timeout cmd}}. Write comment bodies and temporary files with the Write tool under `.scratch/`, and pass them by file, never through a heredoc.
  Write only to the tracker, through {{tracker write}}: comments and labels, plus, when splitting, the new Issues and their sub-issue and blocking relations; do not edit, commit or push repo files, open worktrees, claim Issues, or open gates.
  {{triage traps}}
  End with one line per Issue: `TRIAGED <n> <label>`, `NEEDS_INFO <n> <what is missing>`, or `HUMAN <n> <question>`.

- **Brief check.** A worker's brief is `/issue-run <n> --worker <checkpoint>` plus the Issue body, and gets no check. For a tooling fix unit's brief, first print a labelled skeleton with `node scripts/brief-check.mjs --skeleton`, write it to `.scratch/pilot/briefs/<file>` and fill it in, then run `node scripts/brief-check.mjs <brief>`: dispatch only on `BRIEF_OK <brief>` (exit 0); on `BRIEF_REJECTED … missing=<fields>` (exit 1) fix the brief and rerun.

- **Dispatch.** First claim each member in the main checkout with `node scripts/issue-pool.mjs claim <n> --integration pilot/integration`; dispatch only on `CLAIMED <n>` (or `CLAIMED <n> takeover <session>`), and leave a member claimed by another session out of the batch. `LANDED <n> <sha>` means its work is already on `pilot/integration`: leave it out of the batch; once that SHA is on `origin/{{main}}`, close the Issue with the tracker's close command and a comment naming the SHA (the batch that landed it may already have closed it). Then, after this tick's Probe, run in the main checkout with Bash `timeout: 600000` `node scripts/pilot-dispatch.mjs <key> <n>:<slug>... --capacity --repo-cap {{worker cap}}` (members in number order). It prints `DISPATCHED <n> <handle>` or `STOP <n> <cause>` per member, then `REPORTED {{repo}} <running> <total>/<cap>` once it added the dispatched members to the ledger, so a second dispatch in the same tick counts them; when this repo or the machine is full it prints only `STOP capacity repo <total>/<cap>` or `STOP capacity <total>/<cap> [<repo>=<n>...] +<add>` (the counted ledger rows) and `RELEASED <n>` for each claim of this session it released: leave the batch for the next tick, and release by hand with `node scripts/gh-tracker.mjs edit <n> --remove-assignee @me` only a member it printed `WARN release <n> edit …` for (on `WARN release <n> claim-check …`, rerun the claim first to see whose claim it is). `STOP <n> worktree-branch <path> <branch>` means an older flow left worktree `issue-<n>` on another branch: rename that branch (create it there first when the worktree is detached) to `issue/<n>-<slug>` and dispatch again; the worker continues from that branch. `STOP sync <n> exit <code>` means the adapter's **Env sync** command failed in that member's worktree (its output is on stderr; no terminal was opened): fix the environment there and dispatch the member again with the same key; when it cannot be fixed this tick, release the claim with `node scripts/gh-tracker.mjs edit <n> --remove-assignee @me` and report it instead of redispatching every tick. Exit 2 with a message naming `Env sync` means the adapter's declaration is malformed (no backticked command, or declared twice): nothing was dispatched; fix the adapter line and rerun. `STOP orca-unavailable <line>` (no member) means the Orca CLI failed its `worktree list` before anything was created: keep the claims and rerun the same command next tick.

- **Probe.** Each Reconcile, after Sessions, run in the main checkout `node scripts/pilot-probe.mjs <main checkout> --apply --status --capacity {{repo}} --main {{main}} --handoff-after 2` [optional: plus the adapter's Pool section's `--skip-labels <label>,...`]. Act on its lines as `PILOT-STORE.md` and the `issue-pilot` skill describe: `WORKER` results are written back by `--apply`; `STAGEABLE <key>` goes to Stage; `HELD <n> G<k>` waits for that gate (stage nothing in that batch); `MOVE`, `PARKED`, `UNPARK` go to Batch (a `MOVE` that lists `done` members moves those out, without `--state stop`); `UNBLOCKED <key> <n>` means a stopped member's blockers are all closed, so redispatch it fresh when its stop was waiting on them, ahead of the `PARKED` handling for that member; `IN_MAIN <key>` goes to Close; `RESUME_PUSH` and `NOT_IN_MAIN` go to the Push gate; `OVERLAP` lines are reported, not filtered; `CONFLICT <key> <n> <m|integration> <file…>` (right after `STAGEABLE <key>`) names the files a real merge of that pair conflicts on: a forecast that changes nothing about Stage (the Stage command still resolves what it can and stops on the rest, whose handling needs its source and kind fields), reported so no new work touching those files is dispatched before the pair is settled; `BUDGET <file> <total> <limit> <n…>` means those members together push `<file>` past its size budget though each fits alone: handle it before Pick, have a running member's worker put the new text in the split file the pointer names, and move a `done` member out before Stage; `REQUEST`, `GATE` and `HOLD` are handled before Pick; `POOL_READY` means run the Pool command; `POOL_TRIAGE` means refine those `needs-triage` Issues per Pool, which makes the tick not idle; `HUMAN_NO_GATE <n> <summary>` is a `ready-for-human` Issue no open gate asks about: open one with the Gates command (`--issue #<n>`, the question from the summary, the most conservative option as default) and ask it in this tick's Report with `AskUserQuestion`; `ADAPTER_AHEAD` lines end with ` ｜ ` and the command that saves the adapter ref's copy (the integration branch, or the Pilot **Adapter ref** entry's ref, fetched first when remote) under `<main checkout>/.scratch/pilot/adapter/`: run it and Read the saved file instead of a diff or printed `git show` output; `SCRIPT_AHEAD <path> run-in <stage worktree>` (printed with `ADAPTER_AHEAD`) names a `scripts/` file that adapter names and the main checkout lacks or holds an older copy of: run it as `<stage worktree>/<path>` from the main checkout this tick, since an old copy can fail silently (a watcher reading only the last `--batch`); `SCRIPT_AHEAD <path> sync-main` means the stage worktree lacks it too, so run Integration branch's `sync-main` first; `HOOK_BEHIND <path>` names a script a `.claude/settings.json` hook runs whose main-checkout copy is behind `pilot/integration`: when that hook blocks or fails, reproduce with `git -C <main checkout> show pilot/integration:<path>` before reporting it, and drop it when that version passes; `HUMAN_LANDED <n> <sha>` is a `ready-for-human` Issue whose work already landed on `pilot/integration`: read its last comment and that commit before asking the human, never ask them to run a step that already ran, and name the SHA in this tick's Report (and in the gate's question when `HUMAN_NO_GATE` lists it too); `BLOCKER_OPEN_SCOPE <n> #<m> <label>` means blocker `#m` landed on `pilot/integration` but still carries `<label>` and is unassigned or had its body edited after its last assignment, so `#n` is not dispatchable (when `#m` is assigned and its edit history shows the last edit was the coordinator's own, such as a `COUNTERPART_BARE` rewrite before Close, ignore the line and open nothing): only `#m`'s old scope is done; when `#m` is assigned it closes with its batch, so open a new Issue for the rewritten scope and make `#n` blocked by it; `SCOPE_CHANGED <key> <n> <edited at>` means a `done` member's Issue body was edited after its worker started: read what changed before Stage; when the edit history shows the last edit was the coordinator's own (such as a `COUNTERPART_BARE` rewrite), ignore the line and open nothing; otherwise open a new Issue for scope the candidate lacks, blocked by this one, and add it as a blocker of the Issues waiting on this one; neither line blocks Stage. When it exits non-zero, run the Bare guard by hand, report its stderr, and do not stage or merge this tick.
