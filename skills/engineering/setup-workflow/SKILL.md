# Setup workflow

Bring the target repo (the cwd, or the path in `$ARGUMENTS`) at most one **level** up the ron-skills delivery workflow: L1 basic, L2 gates, L3 resident pilot, as the guide at `docs/workflow/` in ron-skills defines them. Everything is **present first, write after the human confirms**: steps 1–3 are three stations, each presenting its evidence and stopping until the human confirms it (platforms, hosts, target level); step 4 reads the extensions; step 5 asks the human to confirm the write list; only steps 6–9 write.

With `health` as the first word of `$ARGUMENTS`, run only the [Health check](#health-check) on the target repo (the path after it, or the cwd) and skip the steps below.

`<skill>` below is this skill's directory (`readlink -f ~/.claude/skills/setup-workflow`); `<ron-skills>` is the repo that holds it (`git -C <skill> rev-parse --show-toplevel`). Each script documents its usage and output lines in its header comment.

## Steps

Steps 1–3 are the three **stations**: Environment, Host, Level, in that order. Each runs its read-only check, presents the evidence, asks its questions, and stops; the next station starts only after the human confirms this one.

1. **Environment.** Run `node <skill>/scripts/detect.mjs <repo> --env`. It reads only this machine and the repo's CI pins: `ENV platform` (`macos`, `wsl` for WSL2, `linux`), one `REQUIRED` line per required tool (Node at the major version the repo's CI pins, git 2.31 or later, and `python3` only when a template to copy is a `.py`), one `OPTIONAL` line per optional tool (Orca, Codex), and a last line `ENV ok` or `ENV stop <n>`. Present the evidence and ask which platforms the rest of the team runs this repo on (supported: macOS, WSL2, Linux); the confirmed list (e.g. `macOS, WSL2`) goes into the adapter's `## Platforms` in step 7. Stop and wait for the human: this station and every later step until step 6 write nothing. Edge cases:
   - `ENV stop <n>` (exit 1): a required tool is missing or at the wrong version, or this is native Windows (pointing to WSL2). End the run here with nothing written and give the human each `FIX` line; setup never installs or switches a runtime. Rerun `/setup-workflow` once fixed.
   - A missing optional tool is only recorded, not a stop: what it unlocks (`L3` without Orca, the `codex` extension without Codex) cannot be picked in steps 3–4. Say so here, so the human can install it and rerun this station before going on.

   Done when the station printed `ENV ok` and the human confirmed the evidence and named the team's platforms.

2. **Host.** Run `node <skill>/scripts/detect.mjs <repo> --host`. It reads only the repo's `docs/agents/issue-tracker.md` and `origin`: `HOST tracker` and `HOST code` lines, each `github`, `gitlab` or `local` with its hostname, one `CLI` line per CLI those hosts need (`gh`, `glab`), and a last line `HOST ok` or `HOST stop <n>`. [HOSTS.md](HOSTS.md) has the rules and the `gh`/`glab` command table the adapter's Tracker and Delivery sections are written from. Present the evidence and ask the human to confirm the tracker host and the code host. Stop and wait for the human; write nothing. Edge cases:
   - The two hosts differ (e.g. Issues on GitHub, code on a GitLab, or github.com against a GitHub Enterprise host): name both explicitly in the question, since the Tracker section is written for one and Delivery for the other.
   - Either host is `local` (no remote, or a local Markdown tracker): say what it drops, since a `local` code host gets no Delivery section, so no PR/MR, no remote CI and no `land.mjs`. Ask whether a remote is still to come; if it is, the human adds it and reruns this station.
   - A self-hosted GitLab over http or an IP counts as `gitlab`; a host that is neither GitHub nor GitLab (e.g. Bitbucket) is not supported, so tell the human rather than guessing.
   - `HOST stop <n>`: a needed CLI is missing or logged out. End the run like step 1's stop, with nothing written, and give the human each `FIX` line.

   Done when the station printed `HOST ok` and the human confirmed the tracker host and the code host.

3. **Level.** Run `node <skill>/scripts/detect.mjs <repo>`. Each `SIGNAL` line is one level signal with its evidence; `MISSING` lists the unmet signals per level; each `GAP` line is a gap that is not a level signal (`ci`: the code host is not `local` but there is no CI file, or no CI file calls the check entry); the line before last is `RECOMMEND <Ln>` and the last line is `LEVEL <Ln>`.

   | Level | Signals (all of the previous level, plus) |
   | --- | --- |
   | L0 | no tracker setup, or no Issue delivery (`docs/agents/issue-run.md` missing) |
   | L1 | `tracker`: `docs/agents/issue-tracker.md`; `adapter`: `docs/agents/issue-run.md`; `check`: its `## Checks` names one command that exists (before the adapter exists: `bin/check`, `npm run check` or `make check`) |
   | L2 | `integration`: an `integration` branch; `hook`: a pre-push (or, second best, pre-commit) hook that runs the check entry; `worktrees`: Issue-numbered branches in worktrees or merges |
   | L3 | `pilot`: the adapter has `## Pilot`; `pilotCommits`: a `pilot/stage-*` or `stage batch-*` commit in the last 90 days |

   The same run measures the repo without thresholds as `EVIDENCE` lines (contributors in the last 90 days, coexisting Issue branches and worktrees, open Issues, CI, gated work), and each level above the detected one prints its entry conditions from the `docs/workflow/` README's level table as `QUESTION <level> <id> ... <question>` lines plus one `ENTRY <level> met|unmet` line (L3's Orca condition is step 1's `OPTIONAL orca`, measured, not asked). Present the signals and evidence, ask the next level's questions, then rerun `detect.mjs <repo>` with one `--answer <id>=yes|no` per answer (`--answer sessions=yes --answer incident=no`); an unanswered question counts as unmet, and a question whose condition is already measured as met (an existing tracker doc or check entry) is not printed. The target is the `RECOMMEND` line: the next level when its `ENTRY` is met, otherwise the detected level. Present the target with the entry conditions it rests on and ask the human to confirm it. Stop and wait for the human; write nothing. Edge cases:
   - `check` is missing: end the run here with nothing written, before asking any question. The single check entry comes first, built by the human (`docs/workflow/03-level1.md` step 3); rerun `/setup-workflow` once it exists. The `buildCheck` question ("willing to build one") is therefore never a way past this stop: a yes still means build it first, then rerun.
   - Staying put is a valid recommendation, and a repo at L3 always stays at L3. With the target equal to the detected level, steps 4–5 cover only the extensions and template gaps.
   - The human asks to jump more than one level: never more than one level per run unless the human explicitly asks, and then list every unmet signal and entry condition of each level skipped and of the target level (the `MISSING` lines and the `ENTRY` lines' unmet ids) as conditions still owed, and have the human confirm the jump with that list in view.
   - A level step 1 marked unavailable (L3 without Orca) is not a target, even when the human answers its questions yes.
   - A `hook` met by pre-commit carries a note: keep it in the findings as a gap, since only pre-push checks the SHA being pushed. A `GAP ci` goes into the findings too; it never lowers the level.

   Done when the human confirmed the target level, holding every signal's evidence.

4. **Extensions.** The step 3 run also prints one `EXTENSION` line per extension: the detection evidence, the adapter section to fill, and the templates to bring. Confirm each against the repo (read the evidence files) and drop false positives; an extension step 1 marked unavailable is dropped with that reason.

   | Extension | Signal | Adapter section | Templates |
   | --- | --- | --- | --- |
   | `gated` | `*.sql`, a `migrations/` or `changelog/` dir, or an adapter `## Gated tickets` | Gated tickets: the human-only steps on a shared target (SQL, data repair), their handoff evidence | — |
   | `externalEnv` | a compose file, or `testcontainers` in a build manifest | Checks (the env the suite needs) and Stops (the stop code when the env is unreachable) | — |
   | `multiModule` | build manifests in two or more directories | Checks: which tests to run per touched module | — |
   | `customTriage` | a project skill under `.claude/skills/` named for triage, grading or refining | Readiness: that skill replaces `/triage` | — |
   | `codex` | `.codex/`, or Codex named in `AGENTS.md` or the adapter | Review, and the implementer when Codex builds tickets | `run-codex-review.mjs` |

   Then pick the templates for the target level and the confirmed extensions from [Templates](#templates). Done when every extension is confirmed present or absent, each with its evidence, and you have the adapter sections to fill and the template list.

5. **Confirm.** Present in one message: the three stations' confirmed results (platforms, hosts, target level), extensions with evidence, every file you will write or change (the tracker, label and domain-doc files, `docs/agents/issue-run.md` sections, `scripts/` copies, `.claude/settings.json` hooks, the remote CI file), the output of `node <skill>/scripts/copy-templates.mjs <repo> --dry-run <template>...`, and, when the target level is L2 or above, the output of `node <skill>/scripts/ci.mjs <repo> --dry-run`. First rerun the environment station as `node <skill>/scripts/detect.mjs <repo> --env --copy <template>...` (the repo before `--copy`, which takes every argument after it): a stop there (`python3` for a `.py` template) ends the run like step 1, with nothing written. When the target level is L3, ask in the same message whether the agent may push and land on its own (the adapter's Pilot **Push gate** and **Permissions**). The default is no: push, PR merge and closing stay with the human. The answer decides the `.claude/settings.json` allow rules and the `--push` flag, as the `gh-tracker.mjs` row in [Templates](#templates) says, so list both in the write list. Ask the human to confirm or adjust the write list. Done when the human confirmed (at L3, with the push answer); with no confirmation, stop here having written nothing.

6. **Tracker, labels, domain docs.** Read `setup-matt-pocock-skills`'s SKILL.md (`readlink -f ~/.claude/skills/setup-matt-pocock-skills`) and carry out its sections yourself within this run, skipping any whose output already exists and matches; the human answers its questions here, never in a second command. Then create the five triage labels on the tracker with [HOSTS.md](HOSTS.md)'s **Create a label** command for the tracker host (`docs/workflow/03-level1.md` step 4 has the loop). Done when `docs/agents/issue-tracker.md`, `triage-labels.md` and `domain.md` exist and the tracker's read command prints an Issue from the agent's Bash.

7. **Adapter.** Write `docs/agents/issue-run.md` from `<ron-skills>/skills/engineering/issue-run/ADAPTER.md` as the skeleton: fill the sections the target level needs (L1: Platforms with the list step 1 confirmed, Tracker and Delivery with the hosts step 2 confirmed and their commands from [HOSTS.md](HOSTS.md) (no Delivery for a `local` code host), Readiness, Checks, Candidate and acceptance, Evidence and closing; L2: Worktrees and checkpoint and Review too, and in Delivery the two CI runners and when to switch, as ADAPTER.md's Delivery says; L3: Pilot and Permissions) plus each confirmed extension's section, in English, with commands that exist in this repo. Keep an existing adapter's sections and fill only the gaps. Its `## Checks` names the check entry step 3 found. Done when every command the adapter names runs from the repo root, and every Pilot command was run once here.

8. **Copy templates.** Run `node <skill>/scripts/copy-templates.mjs <repo> <template>...`. It copies each template with its runtime dependencies and tests into `scripts/` and records each copy's template path, the last ron-skills commit that changed that template, and the copy's sha256 in `docs/agents/workflow-templates.json`; it refuses a template with uncommitted changes, since the recorded commit would not match the content. Exit 3 (`CONFIRM_OVERWRITE`) means an existing file differs: show the human the printed diff, and rerun with `--yes` only after they confirm. Wire each copy as its row in [Templates](#templates) says, and add the copied tests to the repo's check entry. Done when `copy-templates.mjs <repo> --verify` prints `VERIFIED <n>` and the check entry exits 0.

9. **Remote CI.** Only when the target level is L2 or above: run `node <skill>/scripts/ci.mjs <repo>` for the remote CI runner. It writes the minimal CI for the code host (`.github/workflows/checks.yml` on GitHub, `.gitlab-ci.yml` on GitLab: `push` and PR/MR pipelines run the check entry, Node pinned to this machine's version, the same rule the `check-node-version.mjs` template checks) and prints `CI_WRITTEN <file>`; a `local` code host gets none (`CI_SKIPPED local`). A repo that already has CI files is left untouched: `CI_KEPT <file>` when one calls the check entry, otherwise `GAP ci <reason>`, which goes into the report for the human. Done when it printed one of those last lines.

10. **Report.** Report the detected and new level, every file written, the commands with exit codes, and the gaps left: unmet signals of the target level, `GAP ci` from step 3 or step 9, and declined extensions.

## Health check

For a repo already imported: compare its adapter, docs and copies with what it actually runs, and report the gaps. It only reads; write nothing, even for a gap with an obvious fix.

1. Run `node <skill>/scripts/health.mjs <repo>`. Each gap is one `FINDING <kind> ...  # <evidence>` line (file:line, or the manifest with its recorded commit and the sha256s); the last line is `HEALTHY` (exit 0) or `FINDINGS <n>` (exit 1). A file it cannot read while scanning is skipped with a `health: 略過讀不到的 <path>：<code>` line on stderr. On exit 2, with no last line, the check did not run: a flag was passed, the target is not a git repo, or `detect.mjs` or `check-portability.mjs` failed; report its stderr and stop.

   | Kind | Gap | Handling to recommend |
   | --- | --- | --- |
   | `level` | a non-table line of a tracked or unignored Markdown file mentions exactly one level and names this repo (in the adapter, saying 等級 or level is enough), and that level differs from the one `detect.mjs` finds | correct the doc to the detected level, citing the `SIGNAL` evidence |
   | `divergence canonical-newer` | the copy still matches `workflow-templates.json`, but the canonical script has changed since | overwrite with `copy-templates.mjs <repo> --yes <template>` once the human confirms |
   | `divergence local-modified` | the copy no longer matches the recorded sha256 | carry the change back to the canonical script in ron-skills first |
   | `divergence both-modified` | both of the above; the indented diff (copy → canonical) follows the line | show the diff and leave the decision to the human |
   | `divergence stale-record` | the copy and the canonical script are identical, but neither matches the recorded sha256 | rerun `copy-templates.mjs <repo> <template>` to refresh the record |
   | `divergence unreadable` | the manifest itself, or the copy or canonical script an entry names, cannot be read (permissions) | fix the permissions and rerun the check |
   | `divergence missing-copy`, `missing-canonical`, `invalid-entry`, `invalid-manifest` | the manifest records a copy or canonical path that no longer exists or is not a file, has an entry without `template` or `sha256`, or is not a file holding a valid JSON object with an object `copies` | recopy, or drop the entry, as the human decides |
   | `cross-repo` | the adapter, `.claude/settings.json`, `scripts/`, `bin/` or the git hooks use an absolute home path into another repo | copy the file into this repo (as a template when it is generic), or pass the path in through an env var |
   | `missing-section <section>` | the adapter has no `## Platforms`, or the code host is not `local` (`origin` points to a network host) and it has no `## Delivery`; the evidence is the adapter path alone, since an absent section has no line (a `## ` line inside a code fence does not count) | rerun `/setup-workflow` and fill the section station by station; there is no migration script |
   | `platform <rule>` | the adapter's `## Platforms` lists macOS, and a file under `scripts/`, `bin/` or the git hooks breaks a rule of the canonical `check-portability.mjs`, which reads only those files (file:line, or the file for a case clash) | apply the fix the finding names, or mark the line `portability-ok: <reason>` |

2. **Report.** The `level` and `cross-repo` rules match text, so read each finding's evidence line and drop a false positive (a repo name that is also a common word, a path in an example, a `~` path inside shell quotes such as `"~/x"` or `'~/x'`, which bash does not expand) with the reason. List each remaining finding with its evidence and the handling above, every file the stderr says was skipped as not checked, then the script's last line verbatim. Done when every finding is listed or the run printed `HEALTHY`.
