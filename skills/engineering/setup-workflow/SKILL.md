# Setup workflow

Bring the target repo (the cwd, or the path in `$ARGUMENTS`) to the fullest ron-skills delivery workflow this machine supports, in one run, as the guide at `docs/workflow/` in ron-skills describes it. **Detect, don't ask**: the platform, the hosts and the target come from the checks below, and the human is asked only in the edge cases each step names. **The PR is the confirmation**: every write lands on a branch in its own worktree, and the run ends by opening a PR (an MR on GitLab); the human merging it is the only sign-off.

**Talk to the human in their language.** Every message the human sees (progress lines, the rare question, the report, the PR body) is in the language the human's instructions require (their global or project `CLAUDE.md`/`AGENTS.md`), or else the language they write in. Never name the levels (L0–L3) or print bare signal ids to the human: say what the setup does in plain words (for example "agent 常駐在這個 repo，自己挑單、派工、合入 integration 分支；你只做產品決策、push 和合併"). Levels stay internal: the scripts print them and the adapter uses them.

With `health` as the first word of `$ARGUMENTS`, run only the [Health check](#health-check) on the target repo (the path after it, or the cwd) and skip the steps below.

`<skill>` below is this skill's directory (`readlink -f ~/.claude/skills/setup-workflow`); `<ron-skills>` is the repo that holds it (`git -C <skill> rev-parse --show-toplevel`). Each script documents its usage and output lines in its header comment.

## Steps

Steps 1–4 only read; steps 5–10 write, all inside the worktree step 5 opens.

1. **Environment.** Run `node <skill>/scripts/detect.mjs <repo> --env`. It reads only this machine and the repo's CI pins: `ENV platform` (`macos`, `wsl` for WSL2, `linux`), one `REQUIRED` line per required tool (Node at the major version the repo's CI pins, git 2.31 or later, and `python3` only when a template to copy is a `.py`), one `OPTIONAL` line per optional tool (Orca, Codex), one `TEMPLATES <name> yes|no <templates>` line per platform-dependent template set (`bareGuard`: `yes` on WSL with Orca, see [Templates](#templates)), and a last line `ENV ok` or `ENV stop <n>`. Do not ask about platforms: the platforms for the adapter's `## Platforms` (step 7) are the detected one plus any an existing adapter already lists; a teammate on another platform adds theirs by running `/setup-workflow` there. Edge cases:
   - `ENV stop <n>` (exit 1): a required tool is missing or at the wrong version, or this is native Windows (pointing to WSL2). End the run here with nothing written and give the human each `FIX` line; setup never installs or switches a runtime. Rerun `/setup-workflow` once fixed.
   - A missing optional tool is only recorded, not a stop: without Orca there is no resident pilot, without Codex no `codex` extension. Say so in the report, in plain words, with the install hint.

   Done when the station printed `ENV ok`.

2. **Host.** Run `node <skill>/scripts/detect.mjs <repo> --host`. It reads only the repo's `docs/agents/issue-tracker.md` and `origin`: `HOST tracker` and `HOST code` lines, each `github`, `gitlab` or `local` with its hostname, one `CLI` line per CLI those hosts need (`gh`, `glab`), and a last line `HOST ok` or `HOST stop <n>`. [HOSTS.md](HOSTS.md) has the rules and the `gh`/`glab` command table the adapter's Tracker and Delivery sections are written from. Take the two hosts as detected; ask the human only in these cases, in one question:
   - Either host is `local` (no remote, or a local Markdown tracker): a `local` code host gets no Delivery section, so no PR/MR, no remote CI and no `land.mjs`. Ask whether a GitHub or GitLab remote is coming; if it is, the human adds it and reruns `/setup-workflow`.
   - The two hosts differ (Issues on GitHub, code on a GitLab, or github.com against a GitHub Enterprise host): name both and ask the human to confirm, since the Tracker section is written for one and Delivery for the other.
   - A host that is neither GitHub nor GitLab (e.g. Bitbucket) is not supported: tell the human and stop. A self-hosted GitLab over http or an IP counts as `gitlab`.
   - `HOST stop <n>`: a needed CLI is missing or logged out. End the run like step 1's stop, with nothing written, and give the human each `FIX` line.

   Done when the station printed `HOST ok` and any edge case above was answered.

3. **Target.** Run `node <skill>/scripts/detect.mjs <repo>`. Each `SIGNAL` line is one level signal with its evidence; `MISSING` lists the unmet signals per level; each `GAP` line is a gap that is not a level signal (`ci`: the code host is not `local` but there is no CI file, or no CI file calls the check entry); `EVIDENCE` lines measure the repo for the report; the line before last is `TARGET <Ln>  # <reasons>` and the last line is `LEVEL <Ln>`.

   | Level | Signals (all of the previous level, plus) |
   | --- | --- |
   | L0 | no tracker setup, or no Issue delivery (`docs/agents/issue-run.md` missing) |
   | L1 | `tracker`: `docs/agents/issue-tracker.md`; `adapter`: `docs/agents/issue-run.md`; `check`: its `## Checks` names one command that exists (before the adapter exists: `bin/check`, `npm run check` or `make check`) |
   | L2 | `integration`: an `integration` branch; `hook`: a pre-push (or, second best, pre-commit) hook that runs the check entry; `worktrees`: Issue-numbered branches in worktrees or merges |
   | L3 | `pilot`: the adapter has `## Pilot`; `pilotCommits`: a `pilot/stage-*` or `stage batch-*` commit in the last 90 days |

   The target is the `TARGET` line, never asked and never limited to one level per run: a repo already at L3 stays there; with Orca and a GitHub tracker it is L3 (the resident pilot: the agent picks, dispatches and integrates Issues, and push and the merge to the default branch stay with the human); otherwise L2 (one worktree per Issue, an integration branch, the pre-push check and remote CI). Setting up a level means writing everything each level up to it needs (steps 6–9). Signals that only use creates (`worktrees`, `pilotCommits`) stay missing after setup; the report says they appear once Issues are delivered. Edge cases:
   - `check` is missing: build the single check entry yourself in step 8 as `bin/check` (`#!/usr/bin/env bash`, `set -euo pipefail`, then the repo's existing lint, type-check, test and build commands found in its manifests, in that order), before the copied checks are added to it. Say in the report which commands it chains.
   - A `hook` met by pre-commit carries a note: keep it in the report as a gap, since only pre-push checks the SHA being pushed. A `GAP ci` goes into the report too; it never lowers the level.

   Done when you hold the target and every signal's evidence.

4. **Extensions.** The step 3 run also prints one `EXTENSION` line per extension: the detection evidence, the adapter section to fill, and the templates to bring. Confirm each against the repo yourself (read the evidence files) and drop false positives with the reason; an extension step 1 marked unavailable is dropped with that reason. Do not ask the human.

   | Extension | Signal | Adapter section | Templates |
   | --- | --- | --- | --- |
   | `gated` | `*.sql`, a `migrations/` or `changelog/` dir, or an adapter `## Gated tickets` | Gated tickets: the human-only steps on a shared target (SQL, data repair), their handoff evidence | — |
   | `externalEnv` | a compose file, or `testcontainers` in a build manifest | Checks (the env the suite needs) and Stops (the stop code when the env is unreachable) | — |
   | `multiModule` | build manifests in two or more directories | Checks: which tests to run per touched module | — |
   | `customTriage` | a project skill under `.claude/skills/` named for triage, grading or refining | Readiness: that skill replaces `/triage` | — |
   | `codex` | `.codex/`, or Codex named in `AGENTS.md` or the adapter | Review, and the implementer when Codex builds tickets | `run-codex-review.mjs` |

   Then pick the templates for every level up to the target and the confirmed extensions from [Templates](#templates). Done when every extension is confirmed present or absent, each with its evidence, and you have the adapter sections to fill and the template list.

5. **Branch.** Open the branch every write goes to, in its own worktree so the main checkout stays on the default branch: `git -C <repo> worktree add -b setup-workflow <repo>-setup-workflow <default branch>` (pick another branch or path when one exists). From here `<repo>` in the commands means that worktree. Rerun the environment station as `node <skill>/scripts/detect.mjs <repo> --env --copy <template>...` (the repo before `--copy`, which takes every argument after it): a stop there (`python3` for a `.py` template) ends the run like step 1. Push and merge stay with the human: grant no `land.mjs` or `pilot-close.mjs` allow rule and do not ask; the human can widen that later. Done when the worktree exists on the new branch and the rerun printed `ENV ok`.

6. **Tracker, labels, domain docs, language.** Read `setup-matt-pocock-skills`'s SKILL.md (`readlink -f ~/.claude/skills/setup-matt-pocock-skills`) and carry out its sections yourself within this run, skipping any whose output already exists and matches. Answer its questions from what you detected instead of asking: the tracker is step 2's tracker host; the triage labels are the five defaults; domain docs are single-context unless it found monorepo signals, then multi-context; when neither `CLAUDE.md` nor `AGENTS.md` exists, create `CLAUDE.md`. Then create the five triage labels on the tracker with [HOSTS.md](HOSTS.md)'s **Create a label** command for the tracker host (`docs/workflow/03-level1.md` has the loop). When the human's language is not English, add a `### Language` section to the same agent file stating that every user-facing message is in that language (progress lines between tool calls too) while code, paths and technical terms stay in English; for Traditional Chinese, also bring `claude-hook-language.mjs` (its row in [Templates](#templates)). Done when `docs/agents/issue-tracker.md`, `triage-labels.md` and `domain.md` exist, the language section is in place when needed, and the tracker's read command prints an Issue from the agent's Bash.

7. **Adapter.** Write `docs/agents/issue-run.md` from `<ron-skills>/skills/engineering/issue-run/ADAPTER.md` as the skeleton: fill the sections every level up to the target needs (L1: Platforms with step 1's list, Tracker and Delivery with step 2's hosts and their commands from [HOSTS.md](HOSTS.md) (no Delivery for a `local` code host), Readiness, Checks, Candidate and acceptance, Evidence and closing; L2: Worktrees and checkpoint and Review too, and in Delivery the two CI runners and when to switch, as ADAPTER.md's Delivery says; L3: Pilot and Permissions, with push and land handed to the human) plus each confirmed extension's section, in English, with commands that exist in this repo. Keep an existing adapter's sections and fill only the gaps. Its `## Checks` names the check entry. Done when every command the adapter names runs from the repo root, and every Pilot command was run once here.

8. **Copy templates and gates.** Run `node <skill>/scripts/copy-templates.mjs <repo> <template>...`. It copies each template with its runtime dependencies, tests and test fixtures into `scripts/` and records each copy's template path, the last ron-skills commit that changed that template, and the copy's sha256 in `docs/agents/workflow-templates.json`; it refuses a template with uncommitted changes, since the recorded commit would not match the content. Exit 3 (`CONFIRM_OVERWRITE`) means an existing file differs: this is the one write that needs the human, so show the printed diff and rerun with `--yes` only after they confirm. Wire each copy as its row in [Templates](#templates) says, and add the copied tests to the check entry. When the target is L2 or above, also set up the gates the L2 signals look for: the pre-push hook from `docs/workflow/04-level2.md` (`.githooks/pre-push`, executable, running the check entry on the pushed SHA, with `report-push-scope.mjs` wired as its row says), `git config core.hooksPath .githooks` (say in the report that each clone runs it once), and the integration branch `pilot/integration` from the default branch. Done when `copy-templates.mjs <repo> --verify` prints `VERIFIED <n>` and the check entry exits 0.

9. **Remote CI.** Only when the target is L2 or above: run `node <skill>/scripts/ci.mjs <repo>` for the remote CI runner. It writes the minimal CI for the code host (`.github/workflows/checks.yml` on GitHub, `.gitlab-ci.yml` on GitLab: `push` and PR/MR pipelines run the check entry, Node pinned to this machine's version, the same rule the `check-node-version.mjs` template checks) and prints `CI_WRITTEN <file>`; a `local` code host gets none (`CI_SKIPPED local`). A repo that already has CI files is left untouched: `CI_KEPT <file>` when one calls the check entry, otherwise `GAP ci <reason>`, which goes into the report. Done when it printed one of those last lines.

10. **PR.** Commit everything in the worktree, push the branch and `pilot/integration` (when step 8 made it), and open a PR (MR on GitLab) into the default branch with [HOSTS.md](HOSTS.md)'s create command. Write the body in the human's language and plain words: what the agent can do in this repo once it is merged, what stays with the human, every file written grouped by purpose, the check entry's exit code, and the gaps. Then remove the worktree (the branch stays). With a `local` code host, commit only and say the branch name. Done when the PR or MR URL is printed, or, on a `local` code host, the commit exists.

11. **Report.** In the human's language and plain words: the PR link and that merging it completes the setup; what the agent will do on its own and what stays with the human; the platform and hosts detected; anything missing (Orca, Codex) and what it would add; the gaps (`GAP ci`, a pre-commit-only hook, signals that appear only with use); and that Claude Code must be restarted after the merge for the new hooks to load.

## Health check

For a repo already imported: compare its adapter, docs and copies with what it actually runs, and report the gaps. It only reads; write nothing, even for a gap with an obvious fix.

1. Run `node <skill>/scripts/health.mjs <repo>`. Each gap is one `FINDING <kind> ...  # <evidence>` line (file:line, or the manifest with its recorded commit and the sha256s); the last line is `HEALTHY` (exit 0) or `FINDINGS <n>` (exit 1). A file it cannot read while scanning is skipped with a `health: 略過讀不到的 <path>：<code>` line on stderr. On exit 2, with no last line, the check did not run: a flag was passed, the target is not a git repo, or `detect.mjs` or `check-portability.mjs` failed; report its stderr and stop.

   | Kind | Gap | Handling to recommend |
   | --- | --- | --- |
   | `level` | a non-table line of a tracked or unignored Markdown file mentions exactly one level and names this repo (in the adapter, saying 等級 or level is enough), and that level differs from the one `detect.mjs` finds | correct the doc to the detected level, citing the `SIGNAL` evidence |
   | `divergence canonical-newer` | the copy still matches `workflow-templates.json`, but the canonical script has changed since | overwrite with `copy-templates.mjs <repo> --yes <template>` once the human confirms |
   | `divergence local-modified` | the copy no longer matches the recorded sha256 | carry the change back to the canonical script in ron-skills first |
   | `divergence both-modified` | both of the above; the indented diff (copy → canonical) follows the line | show the diff and leave the decision to the human |
   | `divergence stale-record` | the copy and the canonical script are identical, but neither matches the recorded sha256 | rerun `copy-templates.mjs <repo> <template>` to refresh the record |
   | `divergence unreadable` | the manifest itself, or the copy or canonical script an entry names, cannot be read (permissions) | fix the permissions and rerun the check |
   | `divergence missing-copy`, `missing-canonical`, `invalid-entry`, `invalid-manifest` | the manifest records a copy or canonical path that no longer exists or is not a file, has an entry without `template` or `sha256`, or is not a file holding a valid JSON object with an object `copies` | recopy, or drop the entry, as the human decides |
   | `cross-repo` | the adapter, `.claude/settings.json`, `scripts/`, `bin/` or the git hooks use an absolute home path into another repo | copy the file into this repo (as a template when it is generic), or pass the path in through an env var |
   | `unwired-hook` | a `claude-hook-*` copy the manifest records (tests aside) appears in no hook `command` of `.claude/settings.json`, so it never runs | wire it as its row in [Templates](#templates) says, or drop the copy |
   | `missing-section <section>` | the adapter has no `## Platforms`, or the code host is not `local` (`origin` points to a network host) and it has no `## Delivery`; the evidence is the adapter path alone, since an absent section has no line (a `## ` line inside a code fence does not count) | rerun `/setup-workflow`, which fills the missing section; there is no migration script |
   | `platform <rule>` | the adapter's `## Platforms` lists macOS, and a file under `scripts/`, `bin/` or the git hooks breaks a rule of the canonical `check-portability.mjs`, which reads only those files (file:line, or the file for a case clash) | apply the fix the finding names, or mark the line `portability-ok: <reason>` |

2. **Report.** The `level` and `cross-repo` rules match text, so read each finding's evidence line and drop a false positive (a repo name that is also a common word, a path in an example, a `~` path inside shell quotes such as `"~/x"` or `'~/x'`, which bash does not expand) with the reason. List each remaining finding with its evidence and the handling above, every file the stderr says was skipped as not checked, then the script's last line verbatim. Done when every finding is listed or the run printed `HEALTHY`.
