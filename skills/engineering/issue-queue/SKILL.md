The human's view of the pool. `/issue-pilot` and `/issue-run --pool` take Issues from it unattended; `/issue-queue` shows the human what is in it, what is stuck, and what still needs a decision, and changes the tracker only when the human says so. Run it by hand or under `/loop /issue-queue`.

Project facts come from the repo adapter `docs/agents/issue-run.md`: its **Tracker** section gives the tracker commands (on GitHub, `gh` reads as below; writes through the adapter's wrapper when it names one), its **Readiness** section the ready state, its **Pilot** section (or the file it points to) the worker cap, its **Pool** section the claim timeout and category labels, and its **Issue queue** section whether parent hints are on. The buckets come only from the repo's `scripts/issue-pool.mjs`, the same list the pilot and `--pool` read. When step 0 printed nothing and the repo has no `scripts/issue-pool.mjs`, stop and tell the human to run `/setup-workflow`; never bucket Issues another way.

The pilot's own refinement (its Pool and Probe steps relabelling and reopening on their own) is unchanged: this skill adds a human entry beside it and never edits the pilot, `/triage`, or any other skill.

Arguments, optional: `/issue-queue <n> [<n>...]` limits step 5 (Refine) to those Issues; every other step reports the whole pool as usual.

## Steps

0. **Repo skill.** Run `test -f .claude/skills/issue-queue/SKILL.md && echo REPO_SKILL` as the first command of every run, a run resumed after context compaction included (a compaction summary kept only this user-level text and the agent ran a script the repo does not have, retro spay2 61dc190f#4). When it prints `REPO_SKILL`, the repo skill is the one to follow: read that file whole with the Read tool (`allow_large`; a repo skill can exceed the Bash output cap, retro spay2 b0db621f#2, ef1e0ca7#3), follow it with these arguments, and stop reading this file. Done when the command ran and, on `REPO_SKILL`, the repo file was read.

1. **Pool.** Run `node scripts/issue-pool.mjs --stale` (without `--stale` the script folds the `stale` bucket into one `STALE <count>` line, and step 4 needs each Issue), with `--stale-hours <h>` when the adapter's Pool section sets `Claim timeout: <h> hours`, `--categories <label>,...` when it sets `Categories: <label>,...`, `--skip-labels <label>,...` when it sets `Skip labels: <label>,...`, and `--integration <branch>` when its Pilot section names an integration branch, and keep its output: one `<bucket> #<n> <title>` line per open Issue (a `blocked` line also carries the Issue's triage state and its open blockers, `blocked #<n> <state> by #<m>,... <title>`, a blocker already on the integration branch marked `(landed <branch>)`; a `ready` line of an Issue with a parent also carries the parent, `ready #<n> parent #<p> <title>`, written `<owner>/<repo>#<p>` when the parent is in another repo; while the main checkout's `.scratch/pilot/main-paused` flag is in effect, the `landed` bucket is one `LANDED_COUNT <count> <branch>` line instead), then a `PREREQ <n> <text>` line per `ready` Issue whose operator prerequisite is not `無`, then at most one `NO_CATEGORY <n> <n>...` line. Done when the command exited 0; on any other exit, report its stderr and stop.

2. **Limit line.** The report's first line is `進行中 <N>／上限 <M>`. `<N>` is the number of step 1 lines starting with `claimed ` (count them with `grep -c '^claimed '`, not by eye; a `stale` claim, a `landed` Issue (assigned, but its work is already on the integration branch and only waits for the main branch), and an assigned `ready-for-human` Issue, which the script puts in `stale`, `landed`, and `human`, are listed in their buckets, not counted). `<M>` is the adapter's worker cap, the concurrent-worker limit in its Pilot section's defaults; when the adapter names no cap, or says the count is unlimited, `<M>` is `不限`. Done when the line holds both values.

3. **Buckets.** Under the limit line, list every bucket that has Issues, in the order `issue-pool.mjs` printed them, each Issue as `#<n> <title>` (a `ready` Issue with a parent as `#<n> <title>（母單 <parent>）`, the parent copied as printed); keep the `ready` order as printed, since it is the pick order. A `LANDED_COUNT <count> <branch>` line stands for the whole `landed` bucket: list it in that bucket's place as `<count> Issues landed on <branch>`, with no Issue lines. Mark each `ready` Issue with a `PREREQ` line with its prerequisite: check the environment or open a gate before it is dispatched, since a worker would stop at its preflight. List the `NO_CATEGORY` Issues after the buckets as Issues missing a category label. Done when every line of step 1 appears once.

4. **Stale.** For each `stale` Issue, read its comments and show under it the claimant (the machine and session of its latest `認領：<machine>／<session>` comment, or the assignee login when it has none), when that claim was made, and its last comment (author, time, first line). Releasing or keeping a stale claim is the human's call: never reclaim it, never unassign it, and never run `issue-pool.mjs claim` on it. When the human says to release one, remove the assignee with the adapter's tracker write and say so in the report. Done when each `stale` Issue shows its claimant and last comment.

5. **Refine.** Go through the `needs-triage` and `unlabeled` Issues, the `blocked` Issues whose line shows `needs-triage` or `unlabeled` (a blocker does not stop triage), and the `needs-info` Issues that gained a comment after their last triage note, one at a time. For each, follow the `triage` skill's rules for its state transitions and its brief as published: it is user-invoked, so read `~/.claude/skills/triage/SKILL.md` (its "Triage a specific issue" steps) and the `AGENT-BRIEF.md` beside it directly, with the adapter's Readiness section and its triage conventions on top. Recommend a category and state with the reasoning and a draft of what triage would write: the agent brief for `ready-for-agent`, the same brief plus why it cannot be delegated for `ready-for-human`, the needs-info template for `needs-info`, and triage's `wontfix` handling for `wontfix`. Write nothing until the human confirms that Issue: ask, and only on a yes apply the labels and post the comment, so this skill moves an Issue to `ready-for-agent` or `ready-for-human` only on the human's confirmation. When no human answers (an unattended `/loop` wake), list the recommendations in the report and change nothing. Done when each of these Issues was confirmed and written, declined, or listed as a pending recommendation.

6. **Parent hints.** Unless the adapter's Issue queue section has `Parent hints: off` (then skip this step and step 7), run `node scripts/parent-hints.mjs` when the repo has it: it checks every open parent and prints one line per parent and hint kind, nothing when a parent has no hint (exit 0; on any other exit, report its stderr and check by reading). Without the script, check each `parent` Issue by reading its children with the tracker (on GitHub `gh api repos/<owner>/<repo>/issues/<n>/sub_issues`, and each child's `gh api repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by`) and write one hint line per finding. The five kinds, which the script's lines name:
   - `PARENT_ALL_CLOSED`: every child is closed but the parent is still open;
   - `PARENT_TRIAGE_LABEL`: the parent carries a triage state label (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`);
   - `PARENT_PROSE_DEPS`: an open child's body names a dependency that is still open and not in its `blocked_by`, by the rule of `proseDeps` in `scripts/pilot-probe.mjs` (#94: each same-repo `#m` in a `依賴` clause up to the end of its sentence, not `不依賴` or `無依賴`; the script imports it, so never write a `prose-deps.mjs` of your own);
   - `PARENT_NO_ACCEPTANCE`: an open child has no `## 驗收` heading (`## 驗收條件` counts);
   - `PARENT_DECISIONS_MISSING`: a decision number listed in the parent's confirmed-decisions section (such as `R2-Q5`; headers and source lines elsewhere in the body do not count) appears in no child body. A range in one round counts as every number in it (`R2-Q1～R2-Q4` or `R2-Q1～Q4` is Q1 through Q4 of round 2), and a list that drops the round takes the one before it (`R2-Q1、Q2`), on either side; a range across rounds cannot be expanded, so it gets its own `PARENT_DECISION_RANGE` line asking the human to list it. A decision the parent's line sends to another Issue (`→ #88`, "見 #13", "#13 的內文補充"; a line that only mentions an Issue does not send it) is covered when that Issue's body names it, child or not.
   The hints are prompts for the human and never block anything: do not relabel, reopen, close, or edit an Issue because of one. Done when every parent was checked and each finding has a line.

7. **Review parents.** Then present one parent at a time: its title, its children with their states, its hint lines, and the question whether any detail or boundary from the parent was lost in the split. Write nothing on your own; when the human asks for a change (a child to add, a `blocked_by` to set, a heading to add), make it with the adapter's tracker writes (several writes in one go through the tracker doc's batch command when it names one) and say which Issue it touched. Done when the human answered for each parent, or, with no human answering, each parent is in the report with its hints.

8. **Report.** In the user's language: the limit line first, then the buckets with the stale details, the refine results (confirmed, declined, pending), the parent hints per parent, and every tracker write this run made with its Issue. Under `/loop`, only the human ends the loop.
